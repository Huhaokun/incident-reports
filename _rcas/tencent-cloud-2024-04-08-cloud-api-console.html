问题陈述

Problem
2024-04-08，腾讯云 API 处于异常状态，客户登录不上控制台。云 API 是云上统一的开放接口，控制台通过组合这些接口提供网页功能。新版本接口协议变化后，对旧版本前端数据的处理异常，生成一条错误配置，并扩散到全网地域。 官方事实
Impact
官方称故障近 87 分钟，共有 1957 个客户报障。报障数是报障客户数，受影响客户总数：报告未说明。依赖云 API 的部分服务不可用，原文举例云函数、文字识别、微服务平台、音频内容安全、验证码。已经配置好的服务器等 IaaS 资源，以及已经部署运行的业务，不受这次云 API 异常影响。不以云 API 方式提供的 PaaS 和 SaaS 保持正常。当天全产品进出流量没有明显变化。用 API 提供的存储服务调用有明显下滑和波动，售后协助部分客户做了容灾调度。收入影响、数据损坏：报告未说明 官方事实
When
15:23 收到云 API 异常告警，同时工单、售后群和微博出现控制台登录不上的反馈。15:47 版本回滚没有完全恢复。15:57 定位到配置数据错误。16:02 起全地域修复。16:05 除上海外的地域 API 已恢复。16:25 决定把上海流量调度到其他地域。16:45 上海恢复，控制台流量剧增并按九倍容量扩容。16:50 控制台全部恢复。17:45 观察一小时后处理完毕。原文未标注时区，公告面向中国客户，页面不再做一次换算。异常是否早于 15:23：报告未说明 官方事实
Where
云 API 与云控制台，错误配置扩散到全网地域。16:05 之后仍异常的是上海。承载 API 的容器平台依赖 API 才能调度。错误配置的具体字段：报告未说明 官方事实
Frequency
这篇说明写的是 4 月 8 日这一次。同类兼容问题或灰度问题此前是否发生过：报告未说明

层级问题回答证据
Why 1 为何客户登录不上控制台，一批产品也不可用？ 控制台和这些产品都依赖云 API。云 API 异常后，云函数、文字识别、微服务平台、音频内容安全、验证码等不可用。已运行的 IaaS 数据面不在这条影响里。 官方事实
Why 2 为何云 API 整体异常？ 一条错误配置快速扩散到了全网地域。 官方事实
Why 3 为何会生成这条配置？ 升级后的接口协议变了。后台新版本对旧版本前端传来的数据处理异常。 官方事实
Why 4 为何一条错误配置能到全网？ 配置数据的灰度机制不足。 官方事实
Why 5 为何发布前没有拦住协议变化？ 版本变更过程中没有有效执行沙箱验证和预案演练。缺了哪些用例：报告未说明。停止。 官方事实

Root Cause A：云 API 新版本对旧前端数据的处理缺少向前兼容，生成一条错误配置；灰度不足以把这条配置限制在小范围。沙箱验证和预案演练没有有效执行，这个变更进入了全网。

Validation：Specific 部分，机制有官方表述，配置字段未知 · Systemic 是，兼容、灰度和发布验证是同一条变更链 · Controllable 是，修复配置已经做完，灰度、沙箱和熔断在计划中 · Chain Valid 是，在用例清单处停止。

Chain B · 为何回滚没有自己走完

层级问题回答证据
Why 1 为何 15:47 的版本回滚没有完全恢复？ 根因在配置数据。只回滚版本不够，15:57 才定位到配置错误，16:02 开始全地域数据修复。 官方事实
Why 2 为何服务不能按标准方案自动回到旧版本？ 标准方案是服务后台和配置一起回滚，并重启 API。容器平台的调度依赖 API，形成循环依赖，服务无法自动拉起，改为运维手工启动。 官方事实
Why 3 为何上海比其他地域更晚？ 16:05 其他地域已经恢复。16:25 定位到上海的技术组件存在 API 循环依赖，改为把流量调度到其他地域，16:45 上海恢复。 官方事实

Root Cause B：API 所在的容器平台依赖云 API 才能调度，标准回滚无法自动把服务拉起。上海的恢复因此改成流量调度。这条链延长了恢复，不生成那条错误配置。

Validation：Specific 部分，知道有循环依赖，不知道调用链 · Systemic 是 · Controllable 是，当时用手工启动和流量调度，事后计划去掉循环依赖并提供逃生通道 · Chain Valid 是，在 Why 4 停止。
