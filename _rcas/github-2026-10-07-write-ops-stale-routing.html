问题陈述

Problem
常规维护替换运行内部写路由服务的机器时，一台新机器带着仍列出已退役数据库服务器的过时记录上线，并错误改写了路由配置，把写请求送到已经不存在的服务器。第一段结束后设置的暂停没有被自动化维护遵守，同一台机器再次成为负责节点。 官方事实
Impact
两段写操作中断合计约 19 分钟。第一段 2026-10-07 15:06–15:16 UTC，约 10 分钟：web 和 API 请求 5.6% 失败，峰值 8.9%，超过 12,000 个组织；Git 认证失败最高 26%；17% 的 Actions workflow runs 因基础设施错误失败。第二段 16:52–17:01 UTC，约 9 分钟：web 和 API 6.2% 失败，峰值 9.3%，超过 11,000 个组织；Git 认证最高 25%；19% 的 Actions workflow runs 失败。读操作大体不受影响。没有数据库数据丢失，恢复后重试成功。百分比分母和工单或收入影响：报告未说明。错误写入：不适用。 官方事实
When
15:06 UTC 第一段开始。15:14:45 UTC 出现第一条状态页，文案是 investigating reports，不能据此确认发现渠道。15:16 UTC 正确配置的既有机器成为 quorum leader 后第一段结束。16:23:44 UTC 的状态更新称根因已定位、缓解正在应用。16:52 UTC 未遵守暂停的自动化任务把问题机器再次推到负责位置。17:01 UTC 第二段结束。17:02 UTC 关闭该机器，之后已移除。 官方事实
Where
GitHub 用来跟踪哪些数据库服务器应接收写请求的内部服务。谁成为 quorum leader，谁就下发路由配置。该服务的名称、实现和 quorum 算法：报告未说明。故障在写路由，不在数据库丢失数据。 官方事实
Frequency
同一根因两段窗口，间隔里他们已经定位到机器并设置暂停。第二段是暂停未被遵守后的复发，不是另一起独立事故。过时记录此前是否造成过可见故障：报告未说明 官方事实

Why 1 为何 Git 操作、PR、Issues、Actions、API 和登录等写操作失败？ 写请求被路由到不存在的数据库服务器。读数据大体不受影响，没有数据库数据丢失。 官方事实
Why 2 为何写请求会走到不存在的服务器？ 一台新上线的机器用仍列出已退役数据库的过时记录改写了路由。 官方事实
Why 3 为何这份记录会成为生效配置？ 机器在常规维护替换中带着过时副本启动，并处于 quorum leader 的位置。 官方事实
Why 4 为何没有被校验挡住？ 事后才计划拒绝指向不存在服务器的配置并保留 LKG。事发时的校验形态，以及副本从何而来：停止。 由整改项回推

Root Cause A：维护替换让仍含已退役目标的过时记录上线，系统又允许这份配置被 leader 下发，写请求因此打到不存在的服务器。

Chain C · 为何没有在复发前把机器拿下

层级问题回答证据

Root Cause C，部分确认：第一段后的缓解是暂停，不是立即把机器移出服务。暂停失效后才出现第二段。更快的下线手段是整改项，证据弱于 A 和 B。

根因总结

#根因5S 类别来源已验证优先级
RC-1 新机器带着过时记录上线并改写写路由，把请求送到已退役、已不存在的数据库 Systems / Surroundings Fishbone + 5 Whys A 是。副本来源和校验形态未知 High
RC-2 Puppet 基础设施更新使自动化维护不遵守暂停，同一台机器再次成为 leader Surroundings / Systems Fishbone + 5 Whys B 是。更新细节未知。自动化现已遵守暂停 High
RC-3 未检查的新机器可以下发配置；指向不存在服务器的配置没有被拒绝 Safety Fishbone + 5 Whys A 配置已经生效是事实。缺口本身是回推 High
RC-4 秒级告警和更快下线当时没有挡住复发 Skills / Safety 5 Whys C 部分。不升格为已证实的独立根因 Medium

客户可见的故障是两段合计约 19 分钟的写失败，读大体不受影响，数据库没有丢数据。主因是一次维护替换把错误的路由配置下发了出去，所以配置/变更错误是主要标签。未拒绝非法目标，以及 Puppet 更新让暂停失效，是软件缺陷，作为次要标签。维护替换是导火索；第二段的直接触发是没有遵守暂停的自动化任务。
