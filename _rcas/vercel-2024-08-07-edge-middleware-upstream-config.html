问题陈述

Problem
2024-08-07，Vercel 的 Edge Middleware 和 Edge Functions 出现显著中断。一部分计算基础设施的上游专用提供商进入全局错误配置，没有尊重 Vercel 的全球流量配置，意外拦截了大部分 Vercel 请求。提供商名称：报告未说明 官方事实
Impact
使用 Edge Middleware 和 Edge Functions 的客户遇到高错误率。事件影响全部 invocations 的 61%。影响随项目用量和客户端 user agent 而不同。受影响客户数、错误码分布、收入：报告未说明。没有被 Edge Middleware 挡在前面的 Serverless Functions、Static Files 和 ISR 不受影响，因为这套边缘计算用的是另一家专用提供商。数据损坏：报告未说明 官方事实
When
活跃中断合计 26 分钟，分成 19:13–19:23 UTC 与 19:26–19:42 UTC。当日 UTC+8，即 2024-08-08 03:13–03:23 与 03:26–03:42 Asia/Shanghai。两段之间的三分钟原文没有解释。19:41 UTC（03:41 Asia/Shanghai）发起 config override，19:42 UTC（03:42 Asia/Shanghai）恢复到期望状态。错误配置进入全局状态的时刻：报告未说明。监控发现错误升高后告警，并开了最高优先级内部调查。是否有客户更早报障：报告未说明 官方事实
Where
故障在 Edge Middleware 与 Edge Functions 这条计算路径。上游进入的是全局错误配置。Vercel 工程按 runbook 结论：Vercel 环境里没有服务或配置变更。错误配置的字段和发布链路：报告未说明。区域故障转移有没有被逐区试过，原文没有写。 官方事实
Frequency
正文写的是 8 月 7 日这一次，里面有两段活跃中断。该提供商此前是否进入过同样的全局错误配置：报告未说明

Systems（系统）

潜在原因证据可能性状态标签
Edge Middleware 和 Edge Functions 依赖一家专用计算提供商，和平台上其他服务不是同一套计算 原文用来解释为什么没被 Edge Middleware 前置的 Serverless、Static、ISR 不受影响。 High 已确认 官方事实
这条路径当时没有备份算力。备份方案此前已经在做，事故时还不能接流量 事后动作是加速开发 Edge Middleware 和 Edge Functions 的 backup option，并写明该工作已经在进行。 High 已确认 官方事实

Skills（技能）

不适用。原文写工程按 runbook 排除了己方变更并联系上游，没有写培训或人员技能缺口。

Suppliers（上游）

潜在原因证据可能性状态标签
上游专用计算提供商进入全局错误配置，没有尊重 Vercel 的全球流量配置，拦截了大部分请求 Initial findings 的原句。厂商名称、配置字段、变更审核：报告未说明 High 已确认 官方事实
触发中断的默认流量限额没有按 Vercel 的规模配置；厂商 fail-safe 与流量规模不匹配 事后写明 default traffic limits that triggered the service disruption 已经按规模调整，并在 19:42 UTC 由上游实施了与流量相称的 fail-safe。 High 已确认 官方事实

Safety（防护）

潜在原因证据可能性状态标签

Why 1 为何 Edge Middleware 和 Edge Functions 高错误？ 两段窗口合计 26 分钟，61% 的 invocations 受影响。未被 Edge Middleware 前置的 Serverless、Static、ISR 不在这个比例里。 官方事实

Why 3 为何会拦截？ 该提供商进入全局错误配置，没有尊重 Vercel 的全球流量配置。 官方事实
Why 4 错误配置和哪条保护有关？ 触发中断的是默认流量限额。上游随后实施了与 Vercel 流量规模相称的 fail-safe，限额也已按规模调整。 官方事实

Root Cause A：专用计算提供商在全局错误配置下没有尊重 Vercel 的全球流量配置，默认流量限额触发了对大部分 Vercel 请求的拦截。
