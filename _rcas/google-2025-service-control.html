问题陈述

Problem
2025-06-12，Service Control 里一条新的 quota 检查碰到策略中的意外空字段，发生 null pointer，各区域二进制进入 crash loop。外部 API 因此出现 503。该代码 5 月 29 日已按区域发布，但失败路径要等策略变更才会执行；策略数据却在数秒内复制到全球。 官方事实
Impact
Google Cloud、Google Workspace 与 Google Security Operations 的外部 API 请求 503 升高。客户在受影响服务的 API 和界面上间歇性访问失败。已有的流式操作和 IaaS 资源没有被直接打到。页头列出一大批 Cloud 产品与区域，Mini 报告另有一份产品名单，两份不完全相同，本文不把它们数成一个总数。精确用户比例、收入影响、数据是否损坏：报告未说明。大区域恢复被 Spanner 上的重启惊群拖慢，正式报告举例 us-central-1。Mini 报告写作 us-central1。 官方事实
When
页面声明时钟为 US/Pacific。2025-06-12 处于美国夏令时，按 PDT = UTC-7，Asia/Shanghai = PDT+15 小时。三套起止不要合成一个数。页头：10:51–18:18 PDT，即 2025-06-13 01:51–09:18 Asia/Shanghai。正式报告：策略变更约 10:45 PDT（01:45）。Mini 报告：10:49 开始（01:49），除 us-central1 外 12:48（03:48）缓解，13:49（04:49）结束，自标 Duration 3 hours，并写主因缓解后若干产品还有最多约 1 小时的中等残留，少数更晚。页头结束与 18:18 PDT Vertex AI Online Prediction 恢复对齐。正式报告以「事故开始」为基准：约 2 分钟 SRE 开始分诊，约 10 分钟定位并开始放红按钮，约 25 分钟红按钮可推出，约 40 分钟红按钮推完并从小区域开始恢复。这个「开始」对应 10:45、10:49 还是 10:51：报告未说明。us-central-1 完全恢复最多约 2 小时 40 分。首条对外报告约在崩溃开始 1 小时后。 官方事实
Where
Service Control 是区域服务，从区域数据存储读取 quota 与策略。策略写入它使用的区域 Spanner 表，并因 quota 的全球性在数秒内复制到全球。每个区域部署都触发了崩溃。页面把地点写成 Global，并列出众多区域与多区域。Mini 报告称配额策略数据库在 us-central1 过载。 官方事实
Frequency
这是一次已公开的故障。新检查自 2025-05-29 的区域二进制发布后处于未执行状态，直到 6 月 12 日的策略变更。空字段以前是否进入过这条路径：报告未说明。正式报告没有把策略变更写成自动化；Mini 报告的初步分析写过 invalid automated quota update，并声明该信息可能随调查改变。两句不合并。 官方事实

层级问题回答证据
Why 1 为何大量外部 API 返回 503？ API 管理与控制面中的 Service Control 负责授权、策略和 quota 检查。它的二进制崩溃后，请求过不了这些检查。 官方事实
Why 2 为何二进制崩溃？ 各区域对策略做 quota 检查时读到空字段，走进 5 月 29 日加入的新路径，null pointer 导致 crash loop。 官方事实
Why 3 为何空字段会打死进程？ 这条变更没有适当的错误处理，也没有 feature flag。红按钮只能在事后关掉这条策略服务路径。 官方事实
Why 4 为何区域灰度没有把问题留在一个区域或 staging？ 发布时这条路径从未执行，因为它要等策略变更。6 月 12 日的策略数秒内复制到全球，每个区域部署都被点亮。官方称如果有 flag，会在 staging 抓住。 官方事实
Why 5 空字段是如何被写进策略的？ 停止。正式报告只写 unintended blank fields。不把 Mini 报告的 automated quota update 补进这一步。 报告未说明

Root Cause A：新的 quota 检查没有错误处理，也没有默认关闭的 feature flag；按区域发布的二进制没有执行过这条路径，而带空字段的策略数据近乎即时地全球生效，于是每个区域的 Service Control 都进入 crash loop。

Validation：Specific 是，空字段来源除外 · Systemic 是，代码灰度与数据复制的半径不一致 · Controllable 是，flag、错误处理和渐进复制都已列入计划 · Chain Valid 是，Why 5 停止。

层级问题回答证据
Why 1 为何红按钮推完后，Service Control 没有马上在所有区域恢复？ 小区域先恢复。大区域里，任务重启对所依赖的 Spanner 形成惊群。 官方事实
Why 2 为何重启会打满数据库？ 没有实现适当的随机指数退避。恢复时只好节流建任务，并把流量转到多区域数据库。 官方事实
Why 3 为何事先没有这种退避？ 停止。原文只确认当时没有适当实现，没有写设计或测试记录。 报告未说明

Root Cause B：Service Control 的任务重启缺少随机指数退避，红按钮关闭坏路径之后，大区域的恢复仍被 Spanner 惊群拖长。正式报告写 us-central-1 最多约 2 小时 40 分。

Validation：Specific 是 · Systemic 是，恢复路径自身会放大故障 · Controllable 是，事故中已节流和分流，退避被列入计划 · Chain Valid 是，Why 3 停止。

Why 2 为何状态通道自己不可用？ 正式报告写 Cloud Service Health 基础设施因这次故障宕机。一部分客户跑在 Google Cloud 上的监控也失败了。 官方事实

Root Cause C：对外状态和一部分监控与故障中的 Google Cloud 基础设施绑在一起，客户晚约 1 小时才看到第一条事件报告。页面后部对 Cloud Service Health 是否可用的说法没有对齐。

用户可见的 503 来自 Service Control 在全球各区域 crash loop。可修复的缺陷是新检查既不能容忍空字段，又没有用默认关闭的 flag 限制激活；按区域发二进制并没有限制半径，因为真正点亮路径的是近乎即时的全球策略复制。红按钮关掉了坏路径，大区域随后又被没有退避的重启惊群拖住。页头 10:51–18:18 PDT 是含下游残留的窗口，Mini 报告的 3 小时不是全部恢复时间。

纠正措施（CAPA）

正式报告把恢复后的冻结和七项将要完成的工作分开。Mini 报告更早的三条措施与这七项方向相同，不另算成第二套承诺。Immediate / Corrective / Preventive / Systemic 是按本方法归类。

Immediate / Containment

#行动针对状态来源
1 用变更时已经备好的红按钮，关闭出问题的策略服务路径。约 40 分钟完成推出，小区域先恢复 RC-1、RC-2 已做 官方事实
2 节流 Service Control 任务创建，并把流量转到多区域数据库，以减轻 Spanner 负载 RC-3 已做 官方事实
3 恢复后冻结 Service Control 的全部变更和手工策略推送，直到完成整改 RC-1、RC-4 已做。冻结何时解除：报告未说明 官方事实

Corrective

#行动针对状态来源
4 把 Service Control 模块化，使功能隔离并 fail open。某项检查失败时仍能服务 API 请求 RC-1 计划中 官方事实
5 改进静态分析与测试，使错误被正确处理，必要时 fail open。Mini 报告的「无效或损坏数据不应打垮 API 管理平台」并入这项 RC-1 计划中 官方事实

Preventive

#行动针对状态来源
6 关键二进制的变更必须有 feature flag，并且默认关闭 RC-2 计划中 官方事实
7 审计所有消费全球复制数据的系统。即使业务需要近乎即时的全球一致，复制也要渐进进行，并留出验证和发现的时间。Mini 报告「元数据不得在没有保护、测试和监控时全球传播」并入这项 RC-2、RC-4 计划中 官方事实
8 审计并确保系统采用随机指数退避 RC-3 计划中 官方事实

Systemic

#行动针对状态来源
9 改进自动与人工的对外沟通，让客户尽快拿到可以用来反应的信息 RC-5 计划中 官方事实
10 监控和沟通基础设施在 Google Cloud 及主要监控产品宕机时仍然可用 RC-5 计划中 官方事实
