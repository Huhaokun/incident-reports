问题陈述

Problem
这是一组运维发现，不是一次 Stripe 支付事故。文章写的是把原有分布式 cron 从 Chronos 迁到自己搭建的 Kubernetes，并用压测、读代码、etcd 演练、渐进迁移和 game day 建立信心。下面这些机制彼此独立：节点与 API 失联时 node controller 可以驱逐 Pod；etcd 某一节点 fsync 慢会触发持续选主；cron 名称超过 52 个字符会静默不调度；调度器大约每 3 小时崩溃，作者另说调度器的缓存有时会带来缺陷、回退和崩溃；Pod 会永久停在 Pending；Flannel hostgw 不替换过期路由；etcd 切换后 API server 有时要重启才停止超时；拆掉 API server 再拉起需要人工介入；有一次该告警的情况没有告警。不能收成同一次故障。开篇另举过一次由 Kubernetes 缺陷引起的一小时中断作例子，没有说明那是哪一家，也没有把它写成 Stripe 的支付事故。 官方事实
Impact
客户可见的支付中断：不适用。原文把「迁移不应造成任何客户可见事故」写成目标，没有报告发生了这样一次中断。技术现象按原文各自成立：测试早期，节点无响应时 node controller 可以终止集群里的 Pod，这件事在测试中发生过；game day 里切断 worker 与 API 的联系后，这些节点上的 Pod 被挪到其他节点。两句用词不同，本文不合并成同一次事件。etcd 单节点 fsync 延迟曾造成他们集群不可用，时长和是否影响到 cron 业务：报告未说明。一次计划外事件是某个周五早晨生产环境一台 etcd 不响应 ping，替换并加入集群后，Kubernetes 继续运行，原文写 without incident。名称过长、Pending、调度器崩溃、Flannel 路由，都出现在测试中发现并修复的缺陷列表里，没有各自的客户影响数字。 官方事实
When
本页的 incident_date 用文章日期 2017-12-20。正文没有把这一天写成一次事故的发生日，也没有给上述发现各自的日历时间。唯一的相对时间是「某个周五早晨」那台 etcd 不响应 ping，没有日期和时区，不换算。示例监控图写 Pending 在 11am 升高，时区：报告未说明。文末写从搭建到愿意跑生产 cron，用了 5 个月、3 名工程师全职；需求一节写项目上只有 2 人全职。两处都照录，原文没有解释差别。这是项目历时，不是中断时长。 官方事实
Where
他们自己用 Kubernetes The Hard Way 的方式从零搭建的集群，配置管理用 Puppet，没有用 kubeadm 或 kops。目标大约 500 种 cron、大约 20 台机器，期望大约每分钟 50 个 cron。压测是 3 节点集群、每分钟 1000 个只执行 echo 的 cron。etcd 三副本。当时 AWS 还没有托管 Kubernetes，所以托管服务不是选项。区域：报告未说明。他们依赖的 cronjob controller 当时是 alpha。 官方事实
Frequency
不是一次重复发生的事故。调度器崩溃被写成大约每 3 小时一次，并且已经修复，发生环境是测试中发现的缺陷，没有写成生产支付窗口。node controller 的意外行为是「每次用网络分区测试相关配置都会碰到意外」，次数未给。名称长度、Pending、Flannel 各是一条被修复的缺陷，没有发生次数。 官方事实

Systems（系统）

潜在原因证据可能性状态标签
node controller 在节点无响应时驱逐 Pod；若所有节点暂时都联系不上 API（网络或配置），可以终止集群中的全部 Pod 测试早期发生过。作者要求仔细读 node controller 文档并测试，例如 pod-eviction-timeout；每次用网络分区测试这类配置都会碰到意外。具体参数值和版本里的判定算法：报告未说明 High 已确认 官方事实
他们当时的 etcd 版本里，一个 fsync 延迟高的节点可以触发持续选主，使集群不可用 官方直接陈述。缓解是让每个节点的 IO 带宽高于 etcd 正在做的写入量。延迟多高、不可用多久：报告未说明 High 已确认 官方事实
cron 名称长于 52 个字符时，静默地不调度 测试中发现并修复。文章只给了问题和修复位置，没有写内部为何是 52。 High 已确认 官方事实
调度器大约每 3 小时崩溃；作者另写调度器使用缓存，有时会造成缺陷、回退和崩溃 3 小时崩溃在已修复列表里。缓存那句是总评，文章没有把这一次崩溃证明成某一个缓存键。实现根因：报告未说明 High 现象已确认，缓存因果部分 官方事实
Pod 有时永远停在 Pending 测试中发现并修复，文章给了两处修复位置，没有写两条各自的实现原因。 Medium 已确认 官方事实
Flannel 的 hostgw 后端不替换过期的路由表项 同一份已修复列表。实现细节只有修复位置。 Medium 已确认 官方事实
有时 etcd 切换之后，API server 一直超时，直到把它重启 game day 之后列出的观察。为何超时：报告未说明 Medium 已确认 官方事实

etcd 切换后 API 超时：他们提交了 bug，同时改了自己的监控和配置 game day 一节：improved monitoring, fixed configuration issues, and filed bugs。这条超时是否已在上游关闭：报告未说明 Medium 部分确认 官方事实

Surroundings（环境）

潜在原因证据可能性状态标签
3 节点压测顶不住每分钟 1000 个 cron：每个节点最多每秒启动 1 个 Pod，每分钟 200 个可以稳定跑 目标大约每分钟 50 个，所以他们判定不是阻塞项。这是当时那套测试集群的数字，不是一条通用容量定律。 Low 已确认，且未当成生产事故 官方事实
game day 在工作时间、事先警告的前提下，在生产集群里主动制造 API server 消失、etcd 节点消失、worker 与 API 隔离 切断 worker 后，那些节点上的 Pod 被挪到其他节点。全部 API server 拆掉再拉起，原文写出乎意料地工作得很好。 Medium 已确认，作为发现条件 官方事实
某个周五早晨一台生产 etcd 不响应 ping 有告警，摘除、拉起新节点、加入集群，期间 Kubernetes 继续运行且 without incident。节点为何不响应 ping：报告未说明 Low 已确认，且没有变成客户事故 官方事实

层级问题回答证据
Why 1 为何测试里 Pod 会被终止，或在另一次演练里被挪到别的节点？ node controller 负责在节点无响应时驱逐 Pod，并把它们放到别的节点。测试早期发生过终止集群内全部 Pod。game day 切断 worker 与 API 后，那些节点上的 Pod 被挪走。两句不合并。 官方事实
Why 2 为何会判成无响应？ 所有节点都可能暂时联系不上 API server。 官方事实
Why 3 何种失联会触发？ 原文举例是网络或配置问题。他们用网络分区测试 pod-eviction-timeout 一类设置，每次都有意外。 官方事实
Why 4 参数的具体取值和版本算法是什么？ 停止。 报告未说明

Root Cause A：node controller 会把「节点暂时联系不上 API」放大成驱逐或终止 Pod；所有节点一起失联时，可以终止集群中的全部 Pod。这是测试和演练里的机制，不是一篇支付事故的根因。参数值：报告未说明

Chain B · etcd 的 fsync 与选主

层级问题回答证据
Why 1 为何 etcd 会让他们的集群不可用？ 一个 fsync 延迟高的节点会触发持续的 leader 选举。 官方事实
Why 2 他们如何让它停下来？ 保证所有节点的 IO 带宽高于 etcd 正在执行的写入量。 官方事实
Why 3 etcd 内部为何一个慢节点就能迫使持续选主？ 停止。原文只点到他们使用的版本有这个问题。 报告未说明

Root Cause B：当时使用的 etcd 上，单节点 fsync 延迟高会触发持续选主并造成集群不可用。缓解条件是 IO 带宽要盖过写入量。这与周五那台 ping 不通的 etcd 不是同一件事；后者替换后集群继续运行，原文写没有酿成事故。

Validation：Specific 部分，触发条件明确，阈值不明 · Systemic 是 · Controllable 是，带宽措施已经写出 · Chain Valid 是，在版本内部机制处停止。

单一根因不适用。这篇文章是一次 cron 迁移里的可靠性建设记录：SLO、三副本 etcd、可回退的迁移和 game day 把多条独立问题暴露在测试或受控演练里，而不是一篇支付宕机复盘。优先级按原文强调的爆炸半径来排：失联可以清掉全部 Pod，etcd 选主可以让集群不可用，静默丢掉一次 cron 违反他们自己的 SLO，调度器又被用得很重。Pending、Flannel、告警和 API 重建是并列发现，客户支付影响不适用。
