问题陈述

Problem
美团到店事业群某系统在常规上线时，按 Plus 的提示把 inf-bom 从 1.3.9.6 升到 1.4.2.1，MyBatis 被间接从 3.2.3 升到 3.4.6。上线后，更新系统交互日志的辅助 SQL 在设置参数时抛出 ClassCastException：java.time.LocalDateTime cannot be cast to java.lang.String。Mapper 的 parameterType 写成了 java.lang.String，方法实参却是 long、String 和 LocalDateTime。3.2.4 起，非动态 SQL 会在启动阶段按这份声明绑定参数。 官方事实
Impact
失败的是更新开票请求返回日志一类的辅助流程。作者写明失败不影响主流程。定位期间频繁报警会干扰排查。受影响用户数、失败次数、持续时长：报告未说明。不能把这次报警写成美团全站宕机。没有主流程受损或跨系统级联的描述。数据损坏：报告未说明。原文写的是参数绑定失败，没有写已提交数据被改坏。 官方事实
When
原文只写「某天晚上」的常规上线，没有日历日，也没有钟点，因此没有可换算的 Asia/Shanghai 时刻，也不编故障窗口。文章发布于 2020-06-18，本页 incident_date 用的是发布日，不是事件发生日。报警通道名称和 MTTD：报告未说明。回滚到历史 inf-bom 之后报警消失，精确恢复钟点：报告未说明 官方事实
Where
发生在该系统上线后的线上辅助 SQL。方法是 updateResponse，XML 的 id 同名，语句更新 invoice_log 的 response 与 update_time。业务代码本身这次没有改这段历史 Mapper。示例里用学生查询说明 3.2.3 与 3.2.4 的差异，那是原理示例，不是线上这条发票日志 SQL。 官方事实
Frequency
上线后陆续出现报警，回滚后消失。错误声明在 3.2.3 及更早被忽略，所以这段历史功能此前可以正常运行。3.2.4 之前是否已经有人碰过同一条 XML：报告未说明 官方事实

Systems（系统）

潜在原因证据可能性状态标签
updateResponse 的 XML 把 parameterType 写成 java.lang.String，方法实参是 long、String、LocalDateTime 文章给出了方法签名和 update 语句。异常栈里 updateTime 的 ParameterMapping 为 javaType=class java.lang.String。 High 已确认 官方事实
3.2.3 忽略 parameterType，执行时按真实参数对象选择 TypeHandler；3.2.4 起非动态 SQL 在启动时用 parameterType 构建绑定 作者引用 3.2.4 Release Log：Previous versions ignored the parameterType attribute and used the actual parameter to calculate bindings. 并对比两版 SqlSource：3.2.4 在非动态 SQL 时把 parameterType 传入构造。线上类型因此在初始化阶段就变成 String，运行时选中 StringTypeHandler，LocalDateTime 被按 String 强转。 High 已确认 官方事实
3.2.3 的运行路径会先得到 UnknownTypeHandler，再按实际值解析具体 TypeHandler 作者用 int 参数的示例走读。示例里的强转对象是 Integer，用来说明同一机制；线上失败的类型是 LocalDateTime。问题不是「新版本不支持时间类型」。 High 已确认 官方事实

Skills（技能）

不适用。作者后来说版本二分会更快，那是定位效率，不是报警的原因；原文没有写培训或评审技能缺口。

Suppliers（上游）

潜在原因证据可能性状态标签
Plus 提示升级 inf-bom，MyBatis 作为传递依赖从 3.2.3 升到 3.4.6 作者给出升级前后的版本对比。业务 diff 没有改这段历史 Mapper。MyBatis 的行为变化写在 Release Log 里，是声明开始生效，不是时间类型被删掉。 High 已确认，作为触发条件 官方事实

Surroundings（环境）

潜在原因证据可能性状态标签
旧版本长期忽略错误的 parameterType，历史功能一直正常，错误声明因此留到了这次升级 作者写这段逻辑在上线前可以正常运行，而且这次业务改动没有碰它。声明是什么时候写错的：报告未说明 High 已确认，作为潜伏条件 官方事实

Safety（防护）

潜在原因证据可能性状态标签
这条 parameterType 与实参不一致的用法，在上线之后才由报警发现 上线前业务代码可运行。作者事后建议升级 inf-bom 时做线下全面回归。原文没有说团队此前没有回归或没有 SOP，不能从建议回推成「从无测试」。 Medium 已确认未被这次上线前拦住；测试制度未知 官方事实
频繁的辅助报警干扰了定位 作者写这是回滚的原因之一。报警没有扩大成主流程故障。 Low 已确认，作为排查时的干扰 官方事实

按 Evidence、Frequency、Correlation、Control 筛选进入验证的原因。版本升级是触发，错误声明才是被激活的缺陷。

原因EvidenceFrequencyCorrelationControl
parameterType 为 String，实参含 LocalDateTime 方法签名、XML 和异常栈里的 javaType 上线后陆续报警，直到回滚 与 updateTime 这一个参数的强转失败直接对应 作者建议改成匹配类型，或去掉 parameterType。是否已在所有系统改完：未知
3.2.4 起启动期按 parameterType 绑定，非动态 SQL 选中 StringTypeHandler Release Log，加两版 SqlSource 的源码对比；UT 从 3.4.6 往下降 3.2.3 可用，3.2.4 起失败 与「业务代码没改、只有依赖版本变了」相符 回滚 inf-bom 已让报警消失。留在 3.4.6 就必须改 XML
inf-bom 间接升级，旧版本又长期容忍错误声明 Plus 提示和版本表；上线前这段历史功能正常 一次发布激活长期存在的声明 只看业务 diff 看不到传递依赖的语义变化 回滚有效。升级前如何检查 Mapper，作者给出了建议，没有完成证明

根因验证

原因验证方法结果确认
错误的 parameterType 在 3.2.4 开始生效 回滚 inf-bom 直到报警消失；再用 UT 把 MyBatis 从 3.4.6 往下降；对照 3.2.4 Release Log 和两版源码 3.2.3 可用，从 3.2.4 起不兼容当前写法。Release Log 写明旧版本忽略该属性、新版本在启动时使用它。示例路径上的强转是 Integer，线上是 LocalDateTime，机制相同 是 官方事实
不是新版本取消了对时间类型的支持 同一篇源码走读：类型来自 parameterType，而不是 LocalDateTime 缺少 TypeHandler StringTypeHandler 是因为声明写成了 String。作者明确建议修正或删除该属性，让 MyBatis 按实参计算 是 官方事实
传递依赖升级是触发条件 对照 Plus 提示、inf-bom 版本和 MyBatis 版本表；业务 diff 不含这段 Mapper 回滚历史 inf-bom 后报警消失。上线批次和流量比例未知 是，作为触发 官方事实
上线前的检查没有拦住这条用法 只能确认它到达了线上报警。作者建议全面回归 这次没被拦住是事实。团队是否已有回归套件、套件为什么没覆盖：未知。不把建议写成「此前没有任何测试」 部分 官方事实

层级问题回答证据
Why 1 为什么更新开票日志会报警？ 设置 updateTime 时，LocalDateTime 不能按 String 强转，TypeException 包住了 ClassCastException。 官方事实
Why 2 为什么会选用 String 的 TypeHandler？ ParameterMapping 的 javaType 已经是 String。3.2.4 对非动态 SQL 在框架初始化时就按 parameterType 做好绑定。 官方事实
Why 3 为什么绑定结果是 String？ XML 写了 parameterType="java.lang.String"，而方法的三个实参并不是单一的 String。 官方事实
Why 4 为什么以前能跑？ 3.2.3 及更早忽略 parameterType，执行时按真实参数选择 UnknownTypeHandler，再解析成实际类型的处理器。UT 确认 3.2.3 通过、3.2.4 失败。 官方事实
Why 5 为什么这次会走到 3.2.4 之后的语义？ inf-bom 升级把 MyBatis 从 3.2.3 带到 3.4.6。错误声明是何时写入的：报告未说明。停止。 官方事实

Root Cause A：Mapper 把 parameterType 错写成 String。MyBatis 3.2.3 忽略它，3.2.4 起在启动时用它绑定非动态 SQL，LocalDateTime 因此被 StringTypeHandler 强转。升级只是把这份潜伏声明激活了。

Validation：Specific 是，XML、异常 javaType、版本边界和 Release Log 都对得上 · Systemic 是，作者建议检查所有 3.2.4 以下系统里的同类声明 · Controllable 是，修正或删除 parameterType 即可 · Chain Valid 是，声明的写入时间处停止。

Chain B · 为什么业务 diff 里看不到这次变化

层级问题回答证据
Why 1 为什么一次常规上线会改变这段没改过的 SQL？ 发布系统 Plus 提示 inf-bom 需要升级，团队从 1.3.9.6 升到 1.4.2.1。 官方事实
Why 2 为什么 BOM 升级会改变 MyBatis 的绑定时机？ MyBatis 由 inf-bom 引入，版本从 3.2.3 变为 3.4.6，跨过了 3.2.4 的语义变化。 官方事实
Why 3 为什么升级前没有对上 Release Log？ 作者写当时先按「跨了两个大版本、历史功能不再被兼容」去猜，再用 UT 缩小到 3.2.4，然后才读 Release Log。审批、灰度和是否有人读过发布说明：报告未说明。停止。 官方事实

Root Cause B：行为变化来自传递依赖，不在业务 diff 里。3.2.4 的 Release Log 已经写了 parameterType 开始生效，但这次是上线报警之后才对照到的。

Validation：Specific 是，版本号和发布说明都有 · Systemic 是，任何由 BOM 带入的框架都可能这样 · Controllable 部分，回滚已经做到，升级前的检查是否成了制度未知 · Chain Valid 是，在审批细节处停止。

#根因5S 类别来源已验证优先级
RC-1 parameterType 写成 String，与 long、String、LocalDateTime 的实参不一致 Systems Fishbone + 5 Whys A 是。签名、XML 和异常 javaType 一致 High

RC-4 这条不兼容用法在上线后才报警。是否已有回归套件：未知 Safety Fishbone 部分。只确认这次没有被提前拦住 Medium

线上报警是辅助开票日志更新失败，不影响主流程，也没有可引用的起止钟点。可修复的缺陷是错误的 parameterType；MyBatis 3.2.4 把这份声明从「忽略」改成「启动时绑定」，inf-bom 升级则是触发条件。回滚已经让报警消失。修正 XML、升级前回归和阅读 Release Log 是作者的建议，文章没有给出各系统已经改完的证明。
