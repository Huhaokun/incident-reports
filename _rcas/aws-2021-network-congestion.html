问题陈述

Problem
2021-12-07，US-EAST-1 主网络上一项自动扩容，触发了内部网络里大量客户端此前没出现过的行为，连接活动洪峰打满内部网络与主网络之间的网络设备。延迟和错误又带来更多连接和重试，拥塞因此持续。这些客户端本有经过测试的请求退避，但一条潜伏问题让它们在这次事件里不能充分退避。该代码路径已在生产运行多年。说明发布于 2021-12-10。 官方事实
Impact
内部网络承载监控、内部 DNS、认证，以及一部分 EC2 控制面。主网络和客户应用本身没有被这次内部网络问题直接打中；受影响的是使用这些控制面能力的客户。已在运行的 EC2 实例未受影响，EC2 API 从 7:33 AM PST（12-07 23:33 Asia/Shanghai）起错误率和延迟升高，1:15 PM PST（12-08 05:15）起开始好转，新实例启动到 2:40 PM PST（06:40）才恢复，因此 RDS、EMR、Workspaces 在此期间不能创建新资源。已有 ELB 保持健康，新建 ELB 变慢，把实例注册进已有 ELB 变慢。Route 53 API 从 7:30 AM PST（12-07 23:30）到 2:30 PM PST（12-08 06:30）受损，已有 DNS 记录和查询应答未受影响。该区域控制台登录失败，2:22 PM PST（06:22）完全恢复。STS 为 OIDC 第三方身份提供方发凭证时延迟升高，依赖 STS 的服务（如 Redshift）登录失败，STS 在 4:28 PM PST（08:28）才完全恢复。CloudWatch 全程延迟，少量监控数据可能缺失。直接访问 S3 和 DynamoDB 未受影响，经 VPC Endpoint 的访问受损。Lambda 的 API 和调用全程正常；API Gateway 错误率升高，许多服务器进入必须替换的状态，而自动回收要等 EC2 API 恢复，1:35 PM PST（05:35）开始看到恢复，4:37 PM PST（08:37）大体恢复，之后数小时仍可能有低水平错误和限流。EventBridge 在 12:35 PM PST（04:35）到 2:35 PM PST（06:35）被操作员关闭投递以降低设备负载，投递延迟持续到 6:40 PM PST（10:40）。Fargate、ECS、EKS 的 API 受损；已有任务或 Pod 继续运行，一旦退出就不能拉起。容器相关 API 大多在 1:35 PM PST（05:35）回到正常，Fargate 在 5:00 PM PST（09:00）起错误率开始回落，部分客户在「4 vCPU」规格上又看到数小时的容量不足错误，结束时刻：报告未说明。Connect 的电话、聊天和任务失败率升高，4:41 PM PST（08:41）随受影响的 API Gateway 恢复。精确客户数和失败比例：报告未说明。 官方事实
When
2021 年美国夏令时于 11 月 7 日结束，12 月 7 日为 PST（UTC-8）。加 16 小时为 Asia/Shanghai。7:30 与 7:33 仍在 12 月 7 日晚，8:00 AM PST 起进入 12 月 8 日。自动扩容触发于 7:30 AM PST（12-07 23:30）。内部实时监控立即不可用，操作员改看日志，先看到内部 DNS 错误升高。9:28 AM PST（12-08 01:28）DNS 解析错误恢复，拥塞未消失，监控数据仍然看不见。1:34 PM PST（05:34）拥塞明显改善，2:22 PM PST（06:22）全部网络设备恢复。支持工单创建从 7:33 AM PST（12-07 23:33）受损到 2:25 PM PST（12-08 06:25）。SHD 在 8:22 AM PST（12-08 00:22）起可以更新；拥塞曾使 SHD 工具不能正常故障转移到备用区域。首条内部告警的名称：报告未说明。 官方事实
Where
拥塞在 US-EAST-1 内部网络与主 AWS 网络之间的网络设备上。这些设备做额外路由和地址转换，并且是地理隔离的多套设备，容量也预先做大。触发扩容的那个主网络服务叫什么、客户端的哪条代码路径：报告未说明。 官方事实
Frequency
退避失效的代码路径已在生产多年，自动扩容这次触发了此前没有观察到的行为。同类拥塞是否发生过：报告未说明。 官方事实

层级问题回答证据
Why 1 为何内部网络和主网络之间的设备持续拥塞？ 通信变慢、错误变多之后，连接尝试和重试进一步增加。 官方事实
Why 2 为何重试没有退下去？ 客户端没有充分退避。这些客户端平时有经过测试的退避，就是为了从这类拥塞里恢复。 官方事实
Why 3 为何测试过的退避没有生效？ 一条潜伏问题阻止了充分退避。这条路径已经在生产多年。 官方事实
Why 4 为何多年之后这次才出现？ 主网络某个服务的自动扩容，触发了内部网络大量客户端此前没有观察到的行为，形成连接洪峰。哪个服务、行为的具体差异：报告未说明。停止。 官方事实

Root Cause A：内部网络客户端里一条在生产多年的潜伏问题，使本应生效的请求退避在这次事件中没有充分退让；主网络某服务的自动扩容触发了此前未见的客户端行为，连接洪峰打满两网之间的设备，重试把拥塞维持住。

Chain B · 为何从发现到设备恢复用了约七小时

层级问题回答证据
Why 1 为何 7:30 AM 的触发要到 2:22 PM PST 设备才全部恢复？ 减载动作推进得很慢：先迁 DNS，再隔离高流量源、关闭部分大流量服务、给网络设备加容量。 官方事实
Why 2 为何这些动作慢？ 实时监控立即不可用；内部部署系统也受内部网络影响；同时许多主网络服务和客户应用仍正常，变更必须很谨慎。初期对 DNS 的处理没有结束拥塞。 官方事实
Why 3 监控和部署为什么会一起失效？ 监控数据、内部部署系统和两网之间的这条连接绑在一起。SHD 的备用区域故障转移也被同一拥塞挡住，支持中心同样依赖内部网络。备用路径的设计细节：报告未说明。停止。 官方事实

Root Cause B：定位拥塞和施行减载所依赖的实时监控、内部部署，以及对外的 SHD 故障转移和支持工单，都走这条正在拥塞的内部网络，恢复工具和故障点绑在一起。

Validation：Specific 部分，没有指标名和备用路径图 · Systemic 是 · Controllable 部分，沟通架构有计划，监控与部署的单独改造原文未写 · Chain Valid 是。

Chain C · API Gateway 为何在网络设备恢复后仍延长

层级问题回答证据
Why 1 为何 API Gateway 到 4:37 PM PST 才大体恢复？ 早期连不上内部网络之后，许多服务器进入必须替换才能正常服务的状态。自动回收积压要等 EC2 API 恢复。 官方事实
Why 2 为何内部网络不可用会把网关留在坏状态？ 停止。原文没有写状态机细节，只写团队正在做缓解，让内部网络不可用时网关仍然健康，并加快回收。 报告未说明

Root Cause C：API Gateway 把内部网络错误积累成必须替换实例的状态，而替换又依赖同一事件里受损的 EC2 API。这解释的是网关和 Connect 的尾部影响，不是两网设备拥塞的起点。

Validation：Specific 部分 · Systemic 是，恢复路径依赖另一个受损控制面 · Controllable 是，缓解已在进行 · Chain Valid 部分，机制停在官方描述的现象。

根因总结

#根因5S 类别来源已验证优先级
RC-1 生产多年的潜伏问题使客户端退避失效，重试把两网设备的拥塞维持住 Systems Fishbone + 5 Whys A 是。代码细节未知 High
RC-2 主网络某服务的自动扩容触发了未见的客户端行为，形成连接洪峰 Surroundings Fishbone + 5 Whys A 是，作为触发。服务名未知 High
RC-3 实时监控、内部部署、SHD 故障转移和支持工单与这条内部网络绑在一起 Safety Fishbone + 5 Whys B 是 High
RC-4 API Gateway 进入必须替换的坏状态，回收依赖受损的 EC2 API Systems Fishbone + 5 Whys C 是，作为尾部放大器 Medium

设备拥塞的起点是一次自动扩容触发了内部网络客户端未见的连接行为；拥塞没能自己消退，是因为一条多年潜伏问题让本应退避的客户端继续重试。内部 DNS 错误是操作员先看到的现象，迁走之后拥塞仍在，所以它不是根因。恢复被拉长，是因为监控、部署和对外状态页的故障转移都依赖这条内部网络。已在跑的 EC2、直接访问的 S3 和 DynamoDB、以及 Lambda 调用本身保持可用；客户影响集中在控制面、VPC Endpoint、API Gateway 及其下游。地理冗余是否没能隔开共享过载，只是推断。
