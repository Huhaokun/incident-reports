问题陈述

Problem
2021-07-13 夜间，B 站在线业务主机房的七层 SLB（OpenResty）worker CPU 被打满，无法处理用户请求，APP 和网页打不开。次日线下复现确认：某种只在生产使用的发布模式会把容器权重短暂变成字符串「0」，注册中心把这个字符串交给 lua-resty-balancer 的 _gcd。_gcd 不校验类型；字符串「0」不等于数字 0，取模得到 nan，函数陷入 _gcd(nan, nan) 的死循环。文章发布于 2022-07-12。 官方事实
Impact
22:52 SRE 收到大量接入层不可用报警，客服和内部同学同时反馈 B 站无法使用，APP 首页也打不开，事后登上全网热搜。23:23 左右做了多活的核心功能基本恢复，成功率回到 50% 以上，包括 APP 推荐、播放、评论和弹幕拉取、动态、追番、影视；写功能当时没有多活，未恢复。非多活服务要等新 SLB 集群。直播移动端首页虽然做了多活，但没配多机房调度，主机房 SLB 不可用时首页仍然打不开；直播流量 01:18 切到新集群后恢复。主站、电商、漫画、支付等在 01:40 陆续恢复，01:50 在线业务基本全部恢复。精确用户比例：报告未说明。数据损坏：原文没有写。 官方事实
When
原文没有标注时区。下列时钟都按原文引用，不另做换算。22:52 报警，22:55 远程同学登录不了内网鉴权，22:57 在公司的 SRE 确认主机房七层 SLB CPU 100%，23:07 得知绿色通道，23:17 七层 SLB、四层 LB、CDN 的核心同学到位。23:20 Reload 和冷重启都没有恢复。23:23 多活核心恢复。00:00 决定新建 SLB 集群，01:00 CDN 开始切量，01:50 在线业务基本恢复。01:39 到 01:58 的调试日志看到 _gcd 返回 nan，以及某个容器 IP 的 weight 为 0。02:07 关闭 JIT 并分批重启后 CPU 恢复；次日 11:40 线下复现证明关闭 JIT 仍然有这个 bug。诱因发布在 1:45 完成，权重为 0 的条件已经消失，所以当晚重启能恢复。13:24 发布平台禁止该模式，14:06 起 SLB 忽略注册中心权重，15:00 到 20:00 生产集群灰度到全量。发现渠道是接入层报警加上客服和内部反馈。 官方事实
Where
故障点是在线业务主机房、基于 OpenResty 的七层 SLB。选路使用 lua-resty-balancer，数据来自自研注册中心同步到 Nginx 共享内存的 IP、端口和权重。B 站 2019 年 9 月从 Tengine 迁到 OpenResty，到故障时已稳定运行近两年。动态调权大约在故障前两个月灰度上线。当时一个机房一套 SLB 承接全部在线业务。多活机房的 SLB 在开始阶段也因回源重试超时，CPU 并未过载。 官方事实
Frequency
这种发布模式只有生产环境会用，频率极低，SLB 动态调权的灰度期间没有碰上。字符串权重 0 因此没有在上线前被打到。_gcd 在整数 0 上会走 b == 0 分支，不会死循环。此前是否有过同样的 nan 循环：报告未说明。 官方事实

Systems（系统）

潜在原因证据可能性状态标签
_gcd 不校验类型。入参可以是字符串「0」。因为「0」不等于数字 0，不会走进 b == 0，算术把除零变成 nan，随后 _gcd(nan, nan) 死循环，worker CPU 100% 次日 11:40 线下复现。Lua 会把数字字符串转成数字，数学运算 n % 0 的结果是 nan。整数 0 不会死循环。火焰图热点在 lua-resty-balancer。 High 已确认 官方事实
一个机房一套 SLB 承接全部在线业务，故障域不能按业务切开 故障前的架构事实。改进方向是按业务部门拆集群，核心部门独立 SLB 和公网 IP，并把动态权重这类非必备能力下沉到 API Gateway。 High 已确认 官方事实
近期 WAF、balance 重试或 HTTP/2 变更导致 CPU 打满 23:25 到 23:55 分别回滚或去掉这些配置后重启，SLB 都没有恢复。 Low 已排除 官方事实
JIT 编译器 bug 导致死循环 当晚的怀疑。02:07 关 JIT 后 CPU 恢复，但诱因发布已在 1:45 结束。次日关闭 JIT 仍能复现。 Low 已排除 官方事实

Skills（技能）

潜在原因证据可能性状态标签
组件自测后就灰度，没有专业测试团队对 SLB 输入做异常测试；团队没有资深 Nginx 组件或 C/C++ 开发 优化改进里的自述。他们因此要引入基础组件测试，并招专业做 LB 的人。测试缺失是发布动态调权时的条件，不是当晚某个人的误操作。 High 已确认 官方事实
SLB 团队当时只有一位平台开发和一位组件运维，核心变更不能并行 这解释了为何回滚无效之后才新建源站，而不是两件事同时做。其他同学在协助，但核心变更仍要这位组件运维执行或 review。 High 已确认，作为恢复路径约束 官方事实

Suppliers（上游）

潜在原因证据可能性状态标签
lua-resty-balancer 的 _gcd 接受未校验的入参，字符串「0」能把循环带进 nan 模块从 OpenResty 选路路径被调用。权重是 SLB 自己从共享内存传进去的。社区是否已有补丁：报告未说明 High 已确认 官方事实

Surroundings（环境）

潜在原因证据可能性状态标签
某种特殊发布模式把实例权重短暂调成 0，注册中心返回字符串「0」；该模式只有生产使用，频率极低，灰度没触发 诱因小节。动态调权是故障前两个月为了更细的灰度才上线的。1:45 该应用发布完成，诱因消失。 High 已确认，作为触发条件 官方事实
多活 SLB 被 CDN 回源重试和用户重试打到过载：流量 4 倍以上，连接数约 100 倍、到 1000 万一级 多活 SLB 的 CPU 没有过载，表现是大量超时。晚高峰 CPU 大约 30%，剩余缓冲不到 2 倍。流量下降并重启后恢复。23:23 成功率回到 50% 以上。 High 已确认 官方事实

Safety（防护）

潜在原因证据可能性状态标签
内网登录要在多个域名下种 Cookie，其中一个域名由故障 SLB 代理，远程同学因此登录失败 22:55 的现象。在公司、不需要再登录鉴权的 SRE 仍能看到监控。事后把办公网链路和用户链路隔开。 High 已确认 官方事实
新建源站只演练过 SLB 机器和配置初始化，没有和四层 LB 公网 IP、CDN 切量做过全链路演练，平台之间元信息也不联动 00:00 决定新建，01:00 才开始切量，01:50 基本恢复。三个团队串行。文章写作时，新集群创建、初始化和四层公网 IP 已经能压到 5 分钟以内。 High 已确认 官方事实
没有独立的故障指挥官，重大事故的通报和协同都压在正在处理的 SRE 身上；事件平台不能按组件查询权重变化 应急响应小节的自述。当晚根因是靠火焰图和调试日志找到的，不是靠这个事件平台。它是定位诱因的缺口，不是 CPU 死循环的机制。 Medium 已确认，作为响应条件 官方事实

第一条链是 CPU 死循环，停在语言和库的行为，不再猜测社区为何写成这样。第二条链是字符串「0」从哪来。第三条链是多活和排查为何没有立刻把全站拉起来。

层级问题回答证据
Why 1 为何接入层不能处理用户请求？ 主机房七层 SLB 的 OpenResty worker CPU 100%。Reload 和拒绝流量后的冷重启都没有恢复。其他基础设施反馈没有出问题，SLB 以下的业务层被排除。 官方事实
Why 2 为何 CPU 打满？ 火焰图热点在 lua-resty-balancer。_gcd 返回 nan 之后，worker 进入死循环。WAF、重试和 HTTP/2 的回滚没有改变这个现象。 官方事实
Why 3 为何会出现 nan 并一直循环？ Lua 把数字字符串用于算术时会转成数字。n % 0 得到 nan。入参 b 为字符串「0」时，第一次返回 _gcd("0", nan)，再执行变成 _gcd(nan, nan)。 官方事实
Why 4 为何整数 0 不会，字符串「0」会？ _gcd 不做类型校验。「0」不等于 0，所以进不了 b == 0 的退出分支。关闭 JIT 仍然复现，所以不是编译器把正确的函数编错。社区为何不校验类型：报告未说明。停止。 官方事实

Root Cause A：lua-resty-balancer 的 _gcd 允许字符串「0」进入取模。字符串不等于数字 0，函数不会退出，nan 使 worker 死循环，OpenResty CPU 被打满。

Validation：Specific 是，复现到了函数和 nan · Systemic 是，选路在每台 SLB worker 上 · Controllable 是，忽略权重、禁止该发布模式、补类型校验都是原文给出的控制 · Chain Valid 是，JIT 假设已被复现否定。

Chain B · 字符串「0」为何进了生产 SLB

层级问题回答证据
Why 1 为何 _gcd 会收到字符串「0」？ balance 阶段把共享内存里的 IP、端口、权重传给 lua-resty-balancer。注册中心返回的权重是字符串「0」。 官方事实
Why 2 为何注册中心会返回这个值？ 某种特殊发布模式会把实例权重短暂调成 0。故障前两个月上线的动态调权让 SLB 开始使用这份权重。 官方事实
Why 3 为何灰度没有发现？ 这个发布模式只有生产使用，频率极低，灰度期间没有触发。组件是自测后灰度，没有专业测试团队做输入异常测试。测试用例清单：报告未说明。停止。 官方事实

Root Cause B：动态调权上线后，一条只在生产、很少使用的发布模式会写出字符串权重 0，灰度没有覆盖这条路径，SLB 也没有在把权重送进 _gcd 之前做类型和合法性校验。

Validation：Specific 是 · Systemic 是，发布模式和选路输入是两条系统路径 · Controllable 是，模式已禁止，权重已改为强制指定 · Chain Valid 是，在用例清单处停止。

Chain C · 为何多活和排查没有立刻恢复全站

层级问题回答证据
Why 1 为何 22:57 已经确认是 SLB，全站还是要到 01:50 才基本恢复？ 主机房 SLB 冷重启无效。多活在 23:23 只拉起已做多活且调度正确的核心读功能。新建源站然后切 CDN 用到了 01:50。 官方事实
Why 2 为何多活没有立刻覆盖全部在线业务？ 多活 SLB 被重试打到流量 4 倍以上、连接约 1000 万，缓冲不到晚高峰的 2 倍。写功能当时没有多活。直播首页没配多机房调度。多活元信息和切量依赖人工通知 CDN，不能一键编排。 官方事实
Why 3 为何新建源站和远程排查都慢？ 远程登录被故障 SLB 上的鉴权域名挡住，绿色通道 23:07 才明确，核心同学 23:17 到齐。团队只有一名组件运维能执行核心变更，回滚和新建不能并行。预案没有演练过 SLB、四层公网 IP 和 CDN 的全链路。指挥官和权重变更查询的细节如何拖慢了这一夜：报告未说明。停止。 官方事实

Root Cause C：多活容量缓冲不足、一部分业务只做了不完整的多活，加上办公网走用户 SLB、核心变更不能并行、新建源站没有全链路演练，使「切走主机房」没有在确认故障点之后马上完成。

Validation：Specific 是，倍数、人数和演练范围都有原文 · Systemic 是 · Controllable 是，文中给出了容量、平台切量和演练方向，其中办公网隔离和 5 分钟初始化在文章写作时已经落地 · Chain Valid 是，指挥官对这一夜的分钟级影响处停止。
