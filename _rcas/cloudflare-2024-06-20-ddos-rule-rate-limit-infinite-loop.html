问题陈述

Problem
2024-06-20，两起相互独立的事件让 Internet properties 和 Cloudflare 服务的延迟与错误率升高，官方称持续 114 分钟。影响更大的一件，是 14:14–17:06 UTC 全球部署的新 DDoS 规则触发了限流组件里的潜伏缺陷：带有混合有效与无效 cookie 的 HTTP 请求让处理进程进入死循环，进程永久吃满 CPU。另一件是 17:33–17:50 UTC 的骨干拥塞。原文写没有理由认为可疑流量是在故意利用这个缺陷，也没有任何入侵证据。 官方事实
Impact
许多数据中心可见影响。峰值约 30 分钟内，1.4–2.1% 指向 CDN 的 HTTP 请求收到通用错误页，p99 TTFB 约升到 3 倍。这 30 分钟的起止钟点：报告未说明。眼球 HTTP 错误先到约 0.5%，后来 service unavailable 最高 2.1%；含源站在内的 5xx 最高 3.45%。19:11 UTC 降到约 1% / 1.96%，19:27 UTC 回到基线。约 18:09 UTC 的描述里，西欧约 10% 的 HTTP 处理容量已经没有，东欧约 4%，且正值这些时区的高峰。数据损坏或入侵：不适用。原文明确没有 breach。 官方事实
When
下文钟点都是 UTC，并给出 Asia/Shanghai（UTC+8）。部署 14:14–17:06（22:14 至 6 月 21 日 01:06）。骨干拥塞 17:33–17:50（01:33–01:50）。第一个中毒进程 17:47（01:47）。18:04（02:04）因 CPU 持续偏高自动宣告事件。19:27（03:27）错误率回到基线。20:16（04:16）响应结束。客户是否更早报障、精确 MTTD：报告未说明 官方事实
Where
请求路径在用 Lua 写的 HTTP 处理进程里，新 DDoS 规则复用了遗留限流组件。边缘负载均衡是 Unimog，全局调配是 Traffic Manager。每台服务器有数十个这类进程。骨干拥塞是同一天的另一条网络路径，不是这个死循环的上游。 官方事实
Frequency
这是一次公开事件，由两起独立事件叠在同一时段。限流缺陷被写成 latent bug，引入日期：报告未说明。Traffic Manager 在事件条件里也触发了自己的潜伏缺陷，18:17 UTC 第一次，18:35–18:57 多次。 官方事实

Systems（系统）

潜在原因证据可能性状态标签
新 DDoS 规则把 cookie 和限流接到遗留组件，键生成函数在一条路径上调用自己 规则按设计工作：没有有效 cookie 就返回错误页；有有效 cookie 就加一条稍后计算的限流。生成的限流规则使用内部 API 的方式超出原先设想，parent 键生成器指回 get_cookie_key 自己。 High 已确认 官方事实
第二次 cookie 校验与第一次不一致 限流规则只在已经认为 cookie 有效之后才加上，第二次本应相同。文中的 has_valid_cookie_broken 是另一个函数，客户同时送出有效和无效 cookie 时两者可以意见相反，于是走进调用自己的分支。 High 已确认 官方事实
Lua 的 proper tail call 让死循环不涨栈、不崩溃，进程一直 100% CPU 尾调用替换栈顶而不是压栈。进程一旦处理一条该动作适用、且 cookie 有好有坏的请求，就再也不能处理后续请求。原文把这叫做 process poisoning。 High 已确认 官方事实
遗留限流缺少客户规则那套更新引擎里的保护 DDoS 模块用的是 legacy component。客户为自己的站点配置的限流走更新的引擎。缺陷何时写进遗留组件：报告未说明 High 已确认 官方事实
Traffic Manager 另有一个潜伏缺陷，触发后优雅重启并停止发新的调度动作 18:17 UTC 第一次触发，18:35–18:57 多次。其中 18:35–18:52 和 18:56–19:05 没有发出新的路由动作。已恢复的机房仍几乎被绕开。流量团队在 19:05 前写出、测试并部署了修复。 High 已确认 官方事实

Surroundings（环境）

潜在原因证据可能性状态标签
存在混合了有效 cookie 和无效 cookie 的 HTTP 请求 这是走进死循环的请求形状。官方不认为是故意利用。请求量、来源和是否来自同一客户：报告未说明 High 已确认，作为触发条件 官方事实
自动化网络监控发现性能下降后，按当时的逻辑做了次优重路由，17:33–17:50 UTC 造成骨干拥塞 官方列为两起事件中的第一起，并写系统后来自动缓解了拥塞。和死循环是独立的。次优体现在哪一条路径计算：报告未说明 Medium 已确认，独立事件 官方事实
骨干事件占用了值班注意力，早期一度把 CPU 和网络拥塞当成相关 许多响应人员已经在处理骨干事件。后来发现 CPU 最高的地方流量反而最低，调查才离开网络触发这个假设。 Medium 已确认，作为排查干扰 官方事实

Safety（防护）

潜在原因证据可能性状态标签
新规则先在少数生产机房验证，几小时后就全球生效，没有在生产规模撞上这条 cookie 路径 原文对这次首次启用方式的说明，并写将继续加强 staging 和 rollout。验证时的流量是否包含混合 cookie：报告未说明 High 已确认 官方事实
Unimog 和 Traffic Manager 把流量从高 CPU 挪走，被挪走的流量里包含会下毒的请求 单进程中毒影响有限。CPU 升高后 Unimog 少给这台机器新连接；机房 CPU 升高后 Traffic Manager 把流量调到别的机房。目标侧开始同样失败。调度有安全上限，也会考虑目的地负载，所以不能无限搬。 High 已确认 官方事实

5 Whys

第一条链停在潜伏缺陷的引入日期。第二条链包含扩散和 Traffic Manager 停摆。骨干单独成链，避免被并进同一种软件缺陷。

Chain A · 一个请求把进程打进死循环

层级问题回答证据
Why 1 为何出现通用错误页和更高的 TTFB？ 一部分 HTTP 处理进程不再接受新工作。剩下的进程顶不住，就返回精简的 HTTP 错误。单进程中毒本身影响不大，中毒变多之后才明显。 官方事实
Why 2 为何进程会一直 100% CPU 还不崩溃？ 请求处理逻辑进入不结束的循环。语言的栈深限制没有生效，因为栈没有变深。 官方事实
Why 3 为何栈不变深？ Lua 对 proper tail call 的优化会用新调用替换栈顶。函数的最后一个动作是调用下一个函数时，不会留下返回帧。 官方事实
Why 4 为何会调用到自己？ DDoS 逻辑生成的限流规则把 parent 键生成器指回 get_cookie_key。校验函数认为 cookie 无效时，就走这个分支。 官方事实
Why 5 为何第二次校验会失败？ 它和前面的校验不是同一个实现。同一请求里既有有效 cookie 又有无效 cookie 时，两者可以不一致。缺陷写进遗留组件的日期，以及内部 API 为何允许这种指回：停止。 报告未说明

Root Cause A：新 DDoS 规则复用遗留限流时，损坏的 cookie 校验在混合 cookie 上与前一次校验不一致，键生成函数因此尾调用自己。循环不涨栈，进程被永久打满，不能再处理请求。

Validation：Specific 是，路径在官方说明里是具体的 · Systemic 是，所有跑这段 Lua 的 HTTP 进程共享该路径 · Controllable 是，规则已回滚，并写明校验修好前不重新启用 · Chain Valid 是，Why 5 在引入史上停止。

Chain B · 为何从少数进程变成多机房

层级问题回答证据
Why 1 为何一个中毒进程会波及其它机器？ Unimog 按 CPU 把新连接从高负载服务器挪走。Traffic Manager 再按机房 CPU、延迟和带宽把流量调到别的数据中心。被调走的流量里包含会下毒的请求。 官方事实
Why 2 为何安全上限没有把影响关在欧洲最初的几个机房？ 上限和目的地负载考虑都在，所以不能无限搬。但搬迁治不好已经中毒的进程，CPU 仍然高，于是继续搬，直到很难再找到有余量的机房。 官方事实
Why 3 为何重启了最严重的机房，流量仍绕开它们？ 事件条件触发了 Traffic Manager 的潜伏缺陷。它用优雅重启从异常里恢复，从而停止发出新动作。18:35–18:52 和 18:56–19:05 UTC 没有新路由。 官方事实
Why 4 这个调度缺陷为何会存在？ 停止。原文只写它是 latent bug，并写 19:05 前已修复上线。 报告未说明

Root Cause B：按 CPU 把流量挪到「更健康」目标的调度，会把能下毒的请求一起搬走；Traffic Manager 自己的潜伏缺陷又在两段时间里停止发出新的路由动作，使已经重启的机房仍被绕开。

Validation：Specific 是 · Systemic 是 · Controllable 部分，调度缺陷的修复已部署，识别有毒请求的调度原文没有写 · Chain Valid 是，Why 4 停止。

Chain C · 骨干拥塞

层级问题回答证据
Why 1 17:33–17:50 UTC 的额外损伤从哪来？ 骨干拥塞。官方把它写成与限流死循环独立的事件。 官方事实
Why 2 为何拥塞？ 自动化网络监控检测到性能下降后做了次优重路由。系统后来自动缓解了这次拥塞。 官方事实
Why 3 次优的具体计算是什么？ 停止。原文只写将让缓解逻辑使用备选路径上更多的可用容量信息，没有给出当时的错误规则。 报告未说明

Root Cause C：自动化网络监控在性能下降后按当时的逻辑做了次优重路由，17:33–17:50 UTC 造成骨干拥塞。它不是 cookie 死循环的原因。算法细节：报告未说明

Validation：Specific 否，没有路径或阈值 · Systemic 是 · Controllable 部分，容量和路径信息的改进事故前已经在做，完成度未知 · Chain Valid 部分，链在 Why 3 停止，只确认到「次优重路由」这句。

根因总结

#根因5S 类别来源已验证优先级
RC-1 混合 cookie 让两次校验不一致，遗留限流的键函数尾调用自己，进程永久 100% CPU Systems Fishbone + 5 Whys A 是。机制说明，以及重启可恢复 High
RC-2 Unimog 和 Traffic Manager 把含有毒请求的流量迁到更低 CPU 的机器和机房 Safety / Systems 5 Whys B 是。官方对扩散过程的描述 High
RC-3 Traffic Manager 的潜伏缺陷在两段时间停止发出新路由 Systems 5 Whys B 是。空窗时间，以及 19:05 前部署的修复 High
RC-4 规则在少数机房验证后数小时全球铺开，未在生产规模暴露该路径 Safety Fishbone 是。首次启用方式已写出。验证流量里有没有混合 cookie：未知 Medium
