问题陈述

Problem
给上游 HTTP 接口的实现类加上 @Service 之后，测试环境调用抛出异常，请求 URL 被拼成 null 前缀。堆上同时存在两个 QueryPartnerImpl：父容器里那份属性已注入，DispatcherServlet 的子容器里那份 url 等属性为 null。DispatcherServlet 优先用自己的 Bean，于是用到了未注入的那一份。 官方事实
Impact
测试环境一调用就失败。异常是 ClientProtocolException，原因是 Target host is not specified；日志里的 URL 为 nullmt/api/test/v1/query?id=123456，因为 url 属性是 null，又被拼上了路径。本地单元测试可以通过。生产客户影响：不适用。原文是测试环境的装配失败，不是生产中断，没有生产客户或流量损失的描述。堆转储里的客户端密钥字段不在这里复述。 官方事实
When
没有故障窗口。文章发布日是 2016-09-30，本页 incident_date 用的是这个发布日，不能把它当成故障开始。文中启动日志示例是 2015-12-21 16:28:47.078，错误日志示例是 2015-12-21 16:29:00.905，时区报告未说明，不换算 Asia/Shanghai，也不根据这两行日志推定排查一共持续了多久。 官方事实 报告未说明
Where
美团点评行程相关工程里的 Spring MVC 应用。web.xml 中 ContextLoaderListener 创建 root WebApplicationContext，DispatcherServlet 再创建子上下文并把 parent 指到 root。两份配置都从 com.meituan.trip.mobile.hermes 做组件扫描。父容器另外用 XML 覆盖了 queryPartnerImpl 并注入 URL 等属性；子容器的 spring-servlet.xml 只扫到注解，后面没有再定义这个 Bean。报警系统与 MTTD：不适用。原文是测试时即失败，没有生产报警链路。 官方事实
Frequency
保留 @Service 就能复现，去掉则测试环境恢复正常。这是可重复的测试失败，不是一次计时的生产窗口。其他环境是否同样扫描重叠：报告未说明 官方事实

Systems（系统）

潜在原因证据可能性状态标签
父子 WebApplicationContext 都从同一个大包扫描，@Service 让两个容器各创建一个 QueryPartnerImpl jmap -histo:live 看到该类 2 个实例。启动日志里的 Overriding bean definition 只发生在父容器内部：注解定义被 sal/service-outer.xml 替换。子容器没有这段 XML，所以不会被替换成一份。 High 已确认 官方事实
子容器里的实例没有 XML 属性注入，url、clientId、超时等保持 null 或 0；DispatcherServlet 找到自己的 Bean 就不再用父容器那份 jhat 对比两个实例的字段。引用链分别落到 ContextLoaderListener 持有的 XmlWebApplicationContext，以及 DispatcherServlet 持有的另一个 XmlWebApplicationContext。作者对照 Spring 的父子查找规则：子容器能找到就直接用。 High 已确认 官方事实
Spring 的 singleton 是每个容器一份，不是整个进程一份 两个容器各有一个同名 Bean。这是作者读源码和堆引用之后的结论，不是 Spring 丢了单例。 High 已确认 官方事实

Skills（技能）

潜在原因证据可能性状态标签
把「Spring 默认单例」理解成进程里只会有一个实例，所以两个对象一开始对不上预期 作者写这和当时的认知不符。这解释了排查为什么要走到 jmap，不是 URL 为空的机制本身。 Medium 已确认，作为认知缺口 官方事实

Suppliers（上游）

不适用。原文没有上游服务故障。父子容器和「子容器优先」是 Spring MVC 的既定行为，缺陷在本项目的扫描范围。

Surroundings（环境）

潜在原因证据可能性状态标签
失败出现在带有父子容器的测试部署里；本地单测的装配和这个部署不一样 作者写本地单测通过后部署到测试环境，一测就报错。没有写生产流量或发布窗口。 High 已确认 官方事实

Safety（防护）

潜在原因证据可能性状态标签
本地单元测试只加载一个配置文件，容器里只有一个实例，所以通过并不能证明部署配置正确 作者在总结里直接写了单测能通过的原因。测试环境则把缺陷挡了下来。不能据此说项目没有测试。 High 已确认 官方事实

原因排序

按 Evidence、Frequency、Correlation、Control 筛选进入验证的原因。

原因EvidenceFrequencyCorrelationControl
父子容器重复扫描，子容器的未注入 Bean 遮蔽父容器 两个实例、两套字段、两条引用链，加上增删 @Service 的复现 保留注解即复现，去掉即恢复 空 url 与 null 前缀的请求同时出现 作者给出扫描隔离。删除注解能消掉现象，但作者认为治标
XML 注入只写在父容器，注解实例用字段默认值 父实例有 URL 和超时，子实例对应字段为 null 或 0 与上面是同一次装配 业务每次拿到的是子容器那份 作者建议注解注入就连属性也用注解，或让子容器不要创建这颗 Bean
单测只加载一个配置，覆盖不了双容器 作者对「单测能通过」的解释 这次本地通过、测试环境失败 单容器不会出现第二份半成品 测试环境实际上发现了问题。正式的集成测试要求原文没有写成已有制度

根因验证

原因验证方法结果确认
两个容器各有一个实例，请求用的是空属性那份 增删 @Service 复现；jmap 计数；jmap dump 后用 jhat 与 MAT 看字段和传入引用 2 个实例。完整的一份归 ContextLoaderListener，空的一份归 DispatcherServlet。子容器里的业务对象引用空属性实例，父容器里另有同名对象引用完整实例。作者写请求路径用到的是空的那份 是 官方事实
子容器优先，父容器里的 XML 覆盖帮不上请求路径 作者对照 Spring 源码里 ContextLoaderListener 与 DispatcherServlet 的上下文关系，并对照两份 XML 的扫描配置 与「子容器找到就不再找父容器」一致。启动日志的 Bean 替换只解释父容器内部 是 官方事实
单测装配与部署装配不同 同一实现，本地单测通过，测试环境失败 作者说明单测只加载一个配置文件。没有给出那份单测的文件名清单 是 官方事实

层级问题回答证据
Why 1 为什么测试环境报 Target host is not specified？ 发出的 URL 以 null 开头，使用的 QueryPartnerImpl.url 没有被注入。 官方事实
Why 2 为什么用的是空的那份，而堆里还有一份注入成功的？ DispatcherServlet 使用自己的 WebApplicationContext。那里能找到 Bean，就不会再找父容器。 官方事实
Why 3 为什么子容器里的属性是空的？ 子容器只靠 @Service 创建实例。URL 等属性写在父容器的 XML 里，子容器后面没有再定义这个 Bean，也不会发生替换。 官方事实
Why 4 为什么会有两份？ root 与 servlet 两份配置都从 com.meituan.trip.mobile.hermes 扫描。加上 @Service 之后，两个容器各实例化一次。Spring 的单例范围是容器，不是进程。 官方事实
Why 5 为什么扫描范围会重叠到这个包？ 停止。原文给出了两份配置的事实，没有写这个大包扫描是在哪次需求里加上的。 报告未说明

Root Cause A：父子容器扫描了同一大包，@Service 使子容器得到一个没有 XML 注入的 QueryPartnerImpl；DispatcherServlet 优先使用它，遮蔽了父容器里属性完整的那份，测试请求因此带上 null 主机名。

Validation：Specific 是，实例个数、字段和容器所有权都有堆证据 · Systemic 是，作者把问题归结为扫描范围和注解用法，而不是这一次请求 · Controllable 是，扫描过滤可以直接改配置 · Chain Valid 是，Why 5 在扫描范围的引入历史处停止。

Chain B · 为什么本地单测通过

层级问题回答证据
Why 1 为什么本地单元测试没有发现 null URL？ 单测可以通过，测试环境一跑就失败。 官方事实
Why 2 为什么同一个类在单测里是好的？ 单测一般只加载一个配置文件，容器里只有一个实例，不会出现子容器遮蔽。 官方事实
Why 3 项目里有没有加载真实父子上下文的集成测试？ 停止。原文没有写现有测试套件的范围，只说明了这次单测为什么通过。测试环境本身发现了问题，不能写成测试全部失效。 报告未说明

Root Cause B：本地单测的装配只有一个配置文件，覆盖不了部署时的父子容器，所以通过并不代表 URL 已注入。这是发现路径上的缺口，测试环境仍然把失败暴露了出来。

Validation：Specific 是 · Systemic 部分，只证明了这一类单测 · Controllable 是，可以改测试去加载真实父子上下文 · Chain Valid 是，在 Why 3 停止。

根因总结

#根因5S 类别来源已验证优先级
RC-1 父子容器扫描同一大包，子容器的注解 Bean 没有 XML 注入，并遮蔽父容器里完整的 queryPartnerImpl Systems Fishbone + 5 Whys A 是。复现、实例计数和引用链一致 High
RC-2 DispatcherServlet 在自己的上下文能找到 Bean 就不再使用父容器 Systems Fishbone + 5 Whys A 是。这是框架行为，缺陷在于子容器不该拥有这颗半成品 High
RC-3 本地单测只加载一个配置，发现不了双容器遮蔽 Safety Fishbone + 5 Whys B 是。测试环境仍发现了失败 Medium
RC-4 把 singleton 理解成全进程唯一，延后了对第二份实例的判断 Skills Fishbone 是，作为排查时的认知缺口，不是 URL 为空的机制 Low

测试环境的请求失败，是因为 @Service 让 DispatcherServlet 的子容器创建了第二份 QueryPartnerImpl，属性停留在默认值，请求不再使用父容器里已经注入 URL 的那份。生产客户影响不适用。可改的是扫描边界：子容器不要再实例化这颗需要 XML 属性的 Bean。删掉注解能让现象消失，作者明确说那是治标。
