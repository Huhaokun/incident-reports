问题陈述

Problem
2019-07-02 13:42 UTC（21:42 Asia/Shanghai）起，一条新的 WAF Managed Rules 规则把全球处理 HTTP/HTTPS 的 CPU 打满。客户访问任何 Cloudflare 域名会看到 502。官方称服务中断 27 分钟。这不是攻击流量；14:00 UTC 已排除攻击。 官方事实
Impact
核心代理、CDN 和 WAF 受影响。502 由仍有 CPU 的前置 Web 服务器生成，因为它们连不上处理 HTTP/HTTPS 的进程。图中一个 PoP 的 HTTP/HTTPS CPU 接近 100%。事故中解决方案工程负责人告知已损失 80% 流量，这是当时的口头反馈，不是文中另一张事后审计表。其余防护机制继续运行。客户数：报告未说明。数据损坏：不适用。原文写的是 CPU 耗尽和 502，没有写数据损坏。 官方事实
When
13:31 UTC（21:31）合并，13:37（21:37）构建并通过测试，13:42（21:42）开始全球部署。约 3 分钟后，即约 13:45 UTC（21:45），外部 WAF 合成测试触发第一张 PagerDuty。14:00（22:00）确认是 WAF 并排除攻击。14:07（22:07）全局关闭 WAF，14:09（22:09）流量和 CPU 回到预期。14:52（22:52）全球重新启用 WAF。13:42 到 14:09 的间隔是 27 分钟，与官方所说的中断时长一致。 官方事实
Where
Cloudflare 全球处理 HTTP/HTTPS 的 CPU 核心。规则经 Quicksilver 在秒级推到当时 180 个以上城市。WAF 实现是 Lua，正则引擎是 PCRE。软件发布本来走 DOG、PIG、Canary，这条规则按 WAF 的 SOP 直接全球发布。 官方事实
Frequency
这是一次全球中断。官方称此前六年没有全球性中断。过去 60 天 WAF Managed Rules 有 476 次变更，大约每 3 小时一次；那些变更没有这次的后果。Quicksilver 平均约每秒 350 次变更，一次变更到全球每台机器的 p99 是 2.29 秒。 官方事实

Systems（系统）

潜在原因证据可能性状态标签
一条 XSS 规则里的正则会剧烈回溯，吃满处理请求的 CPU 官方给出的表达式是 (?:(?:\"|'|\]|\}|\\|\d|(?:nan|infinity|true|false|null|undefined|symbol|math)|\`|\-|\+)+[)]*;?((?:\s|-|~|!|{}|\|\||\+)*.*(?:.*=.*)))。关键片段是 .*(?:.*=.*)，可看成 .*.*=.*。模拟模式不拦截，但规则仍会执行。 High 已确认 官方事实
Lua WAF 使用的 PCRE 靠回溯匹配，没有复杂度保证 原文对引擎的直接说明。附录用逐步匹配说明输入变长时步数超线性增长，并对照 Thompson 的线性 NFA。换引擎是后续动作，事故当时仍是 PCRE。 High 已确认 官方事实
数周前一次旨在降低 CPU 的重构，误删了能拦住正则过量 CPU 的保护 官方列为同时成立的漏洞之一。误删发生在这次发布之前，不是这次规则作者在发布当场删的。 High 已确认 官方事实
Quicksilver 把规则秒级推到全球，单条规则因此打到所有 HTTP/HTTPS 核心 WAF 规则为了应对新威胁走 Quicksilver。平均 p99 2.29 秒到全球每台机器。这次速度让规则在几秒内全球生效。 High 已确认 官方事实

Skills（技能）

潜在原因证据可能性状态标签
内部系统的旁路不常用，事故中不够熟练 Access 失效后进不了控制台、Jira 和构建系统，要走不常用的旁路。官方把「旁路流程没有训练好」列为漏洞，并写事后要演练。这不是「有人写错正则」的终点。 High 已确认 官方事实
有工程师写出了容易剧烈回溯的正则 官方把它列为漏洞之一。评审、测试和发布流程都按当时的 SOP 走完了。再归因到个人熟练度：报告未说明 Medium 已确认，作为规则内容，不是链的终点 官方事实

Suppliers（上游）

不适用。没有外部供应商中断；PCRE 是 WAF 自己选用的引擎，放在 Systems。

Surroundings（环境）

潜在原因证据可能性状态标签
未见过的攻击打满了 CPU 出事头几分钟有过这种推测。14:00 UTC 性能团队的线上 CPU、另一人的 strace、以及 WAF 错误日志把原因定为 WAF，攻击被排除。 Low 已排除 官方事实
规则针对的 XSS 威胁近年增多，所以规则发布被设计成可以很快 这是 SOP 允许全球推送的背景，不是 7 月 2 日当天的流量突变。当天执行的是非紧急变更。 Medium 已确认，作为流程背景，不是触发流量 官方事实

Safety（防护）

潜在原因证据可能性状态标签
CI 只验证拦截和误报，不看失控 CPU 测试含大量单测和 HTTP 请求，区分该拦和不该拦。官方写它没有测试 WAF 的 runaway CPU。以前的构建日志里，这条规则也没有拉长测试时间。 High 已确认 官方事实
规则 SOP 允许非紧急变更不经 DOG、PIG、Canary 直接全球发布 变更有部署计划、回滚计划和 SOP 链接。软件发布要先内部 PoP、再少量非付费客户、再三个 Canary。WAF 规则按设计不走这条，以便快速应对威胁。这次到上线前的步骤都被认为做对了。 High 已确认 官方事实
回滚计划要完整构建两次 WAF，太慢 官方原句。所以先用 global terminate 关掉整个 WAF，而不是等构建回滚。 High 已确认 官方事实
全球流量下降告警偏慢；状态页更新也不够快 官方把这两条单独列为漏洞。第一张有用的页面来自外部 WAF 合成测试，大约 3 分钟。流量下降告警的实际延迟数字：报告未说明 Medium 已确认 官方事实
控制台、API、Jira、构建系统走自己的边缘；部分 SRE 凭证因长期不用被安全策略关掉 Access 中断后无法登录。客户也进不了 Dashboard 和 API。旁路最终有人在 14:07 执行了全局关闭。 High 已确认 官方事实

根因验证

原因验证方法结果确认
这条正则和 PCRE 回溯打满 CPU 线上 CPU 数据、strace、WAF 错误日志；单城市先做负向测试再做正向测试，并把付费客户流量移出该城市 14:00 UTC 确认是 WAF。14:52 他们写已 100% 确认原因并有修复，然后全球重新启用。附录给出超线性步数。本稿没有重跑该正则 是 官方事实
CPU 保护被误删，测试不覆盖失控 CPU 对照官方对重构和测试套件的说明；看旧构建日志的耗时 测试通过，且套件耗时没有上升。保护缺失是官方陈述，不是从「后来加回去」单独推断的 是 官方事实
全球秒级发布把爆炸半径放到最大 对照 SOP 与 Quicksilver 的设计说明，以及关闭 WAF 后的恢复 14:07 全局 terminate 后，14:09 流量和 CPU 恢复。这支持「问题在已全球生效的 WAF 规则」，也说明 kill switch 有效 是 官方事实
响应被自身边缘和慢回滚拖住 对照时间线和访问受阻的陈述 从确认到执行关闭约 7 分钟。凭证超时和旁路不熟是官方陈述。全球流量下降告警慢了多少分钟：没有数字 是，告警延迟数字 报告未说明

层级问题回答证据
Why 1 为何客户看到 502？ 前置服务器仍有 CPU，但连不上处理 HTTP/HTTPS 的进程。那些进程所在核心接近 100%。 官方事实
Why 2 为何 CPU 被打满？ 一条新的 XSS 托管规则含有会剧烈回溯的正则。模拟模式仍会执行规则。14:00 的 CPU、strace 和错误日志指向 WAF。 官方事实
Why 3 为何这条正则能跑这么久？ PCRE 用回溯，没有复杂度保证。形如「任意内容后再跟任意内容」的片段会超线性回溯。 官方事实
Why 4 为何没有运行时保护把它停掉？ 数周前为了降低 WAF CPU 的重构误删了过量 CPU 保护。 官方事实
Why 5 为何它在绿灯之后到达每一台机器？ CI 不测 runaway CPU，旧日志里测试时间也没变长。规则 SOP 允许非紧急变更全球发布，Quicksilver 秒级送达。个人为何写出这个表达式：停止，不再追到熟练度。 官方事实

Root Cause A：一条会剧烈回溯的正则跑在没有复杂度保证的 PCRE 上；过量 CPU 保护已在数周前被误删；测试不看 CPU，非紧急规则又按 SOP 经 Quicksilver 秒级全球生效。

Validation：Specific 是，规则、引擎和误删都有原文 · Systemic 是，同一条路径适用于当时全部 HTTP/HTTPS 核心 · Controllable 是，保护已恢复，发布流程和引擎都有后续动作 · Chain Valid 是，没有把个人失误写成终点。

Chain B · 为何知道是 WAF 之后还要几分钟才恢复

层级问题回答证据
Why 1 为何 14:00 已经确认，流量 14:09 才回来？ 要用 global terminate 关掉整个 WAF。按规则回滚要完整构建两次，太慢。 官方事实
Why 2 为何执行这个开关也不顺？ 他们使用自己的 Access。控制台不可用，部分人的凭证因长期不登录被关掉。Jira 和构建系统要走不常用、也没训练好的旁路。 官方事实
Why 3 为何内部工具和客户控制台都在这条边缘上？ 原文写他们使用自己的产品，Dashboard 和 API 经过 Cloudflare 边缘。这个依赖何时形成、还有哪些系统同样没有旁路：停止。 报告未说明

Root Cause B：规则回滚太慢，而执行全球开关所依赖的内部访问又跑在已经故障的边缘上，旁路不熟，部分凭证还因安全策略超时失效。

Validation：Specific 是 · Systemic 是，客户 Dashboard 和 API 同样经过边缘 · Controllable 是，文中已列紧急把 Dashboard 和 API 移出边缘、自动状态页和旁路演练 · Chain Valid 是，Why 3 在设计史处停止。

根因总结

#根因5S 类别来源已验证优先级
RC-1 回溯正则跑在没有复杂度保证的 PCRE 上，打满 HTTP/HTTPS CPU Systems Fishbone + 5 Whys A 是。CPU、strace、单城市正负测试和附录 High
RC-2 过量 CPU 保护数周前被误删，CI 又不检测 runaway CPU Systems / Safety Fishbone + 5 Whys A 是。官方陈述；测试耗时没有预警 High
RC-3 非紧急规则的 SOP 允许跳过软件那套分阶段，Quicksilver 秒级全球生效 Safety / Systems Fishbone + 5 Whys A 是。SOP 与发布时间线 High
RC-4 回滚要两次完整构建；内控和客户入口都依赖边缘，旁路不熟 Safety / Skills 5 Whys B 是。时间线和访问受阻的陈述 High
RC-5 全球流量下降告警偏慢，状态页更新也不够快 Safety Fishbone 部分。官方列为漏洞，没有给出延迟数字 Medium

502 是因为一条 WAF 规则的正则在 PCRE 上剧烈回溯，把处理 HTTP/HTTPS 的 CPU 打满。保护本可以拦住过量 CPU，但在数周前的重构里被误删；测试只看拦截和误报。发布按当时的规则 SOP 做对了，而那份 SOP 允许非紧急规则秒级全球生效。恢复依赖全球关掉 WAF，但回滚构建太慢，内部访问又被同一起边缘故障挡住。攻击在 14:00 UTC 被排除。
