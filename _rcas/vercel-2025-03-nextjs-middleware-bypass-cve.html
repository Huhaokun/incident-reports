问题陈述

Problem
Next.js 存在严重漏洞 CVE-2025-29927。内部请求头 x-middleware-subrequest 用来防止递归，并在 Middleware 已经跑过时跳过再次执行。这个头缺少充分校验时，可以从外部传入，从而跳过 Middleware。复盘没有写构造细节，这里也不展开构造方法。 官方事实
Impact
自托管、使用 next start 或 output: 'standalone' 的应用受影响。Static export 不受影响，因为没有服务端运行时就没有 Middleware。Vercel 托管上的路由逻辑在另一套全球分布的系统里，偶然不受影响。Netlify 和 Cloudflare Workers 因同样的路由解耦，被确认从未受影响。一些应用只用 Middleware 检查 cookie 做乐观鉴权或拦截路由，跳过 Middleware 就会暴露本来想保护的路由。官方明确不建议把 Middleware 当作保护路由的唯一方法。在野利用规模、受影响应用数：报告未说明。这不是一篇带生产错误率的中断报告。 官方事实
When
私报于 2025-02-27 06:03:00 GMT（14:03 Asia/Shanghai），经 GitHub private reporting，研究者同时写了 security@vercel.com。2025-03-01 02:00:00 GMT（10:00 Asia/Shanghai）另一线程把范围扩大到更新的版本。2025-03-14 17:18:00 GMT（2025-03-15 01:18 Asia/Shanghai）升到 Next.js 团队并确认有效。补丁合并于 2025-03-17 20:56:00 GMT（2025-03-18 04:56 Asia/Shanghai）。CVE 于 2025-03-21 10:17:00 GMT（18:17 Asia/Shanghai）公开。GMT 与 UTC 相同。没有单独的生产故障钟点。前置日期用的是 2025-03。 官方事实
Where
缺陷在 Next.js Middleware 与页面渲染分进程时使用的内部头。受影响的运行方式是自托管的 next start 和 standalone。完整受影响版本区间：报告未说明。已发布的修复版本见纠正措施。 官方事实
Frequency
这是一次潜伏缺陷的负责任披露，不是反复发生的生产中断。初报只覆盖 12.x，后来范围扩大。客户环境是否先于私报发现：报告未说明 官方事实

Systems（系统）

潜在原因证据可能性状态标签
x-middleware-subrequest 是内部头，用来检测并防止递归，同时跳过 Middleware 的再次执行 技术分析的原句。Middleware 在缓存和路由之前运行，并且和页面渲染分进程。从 Middleware 内部 fetch 应用时，要用这个头告诉路由进程 Middleware 已经跑过。 High 已确认 官方事实
这个头未写入文档，传入时没有充分校验，外部请求因此可以让 Middleware 被跳过 修复是：头传入时做校验，校验失败就滤掉。不能升级的应用可以在到达 Next.js 之前滤掉该头。后续还要文档化这些内部头，或换成正式 API。 High 已确认 官方事实

Suppliers（上游）

Surroundings（环境）

潜在原因证据可能性状态标签
一部分应用只用 Middleware 检查鉴权 cookie，并据此提前跳转或拦截路由。跳过 Middleware 时，这些路由失去这层检查 官方描述了这种模式，并写明不建议把它当作保护路由的唯一方法。有多少应用这样做：报告未说明 High 已确认，作为危害被放大的用法 官方事实

5 Whys

主链解释自托管为何能跳过 Middleware。分诊和公开沟通是两条独立的过程链。

层级问题回答证据
Why 1 为何自托管应用的 Middleware 可以被绕过？ 外部请求可以传入 x-middleware-subrequest。工程团队确认这对 next start 和 standalone 有效。Static export 没有 Middleware。Vercel、Netlify、Cloudflare Workers 的路由不走这条受影响路径。 官方事实
Why 2 为何这个头能让 Middleware 不执行？ 它的用途就是检测并防止递归，并跳过 Middleware 的执行。 官方事实
Why 3 为何需要这样一个头？ Middleware 和页面渲染分进程。从 Middleware 里 fetch 应用时，要告诉路由进程 Middleware 已经跑过。 官方事实
Why 4 为何外部请求也能用它？ 传入时没有充分校验，这个头也没有文档。修复就是校验，失败则滤掉。 官方事实
Why 5 为何跳过之后危害变大？ 一部分应用只用 Middleware 做鉴权或拦截。官方本来就不建议这种唯一边界。报文级构造：报告未说明。停止，不补研究员文章里的细节。 官方事实

Root Cause A：分进程的 Middleware 用未文档化的 x-middleware-subrequest 向路由进程声明「已经执行过」。外部请求在缺少校验时可以传入这个头，自托管的 next start 和 standalone 会因此跳过 Middleware。

Validation：Specific 是，头的用途和补丁点都写了，构造字节未写 · Systemic 是，信任边界放在了外部可见的头上 · Controllable 是，校验补丁和前置过滤已经给出 · Chain Valid 是，在构造细节处停止。

根因总结

#根因5S 类别来源已验证优先级
RC-1 未文档化的 x-middleware-subrequest 可跳过 Middleware，传入时缺少充分校验 Systems Fishbone + 5 Whys A 是。工程确认，补丁是校验并滤掉。构造细节不在本复盘 High
RC-2 只把 Middleware 当作鉴权或拦截的应用，在 Middleware 被跳过时失去这层检查 Surroundings Fishbone + 5 Whys A 是，作为官方描述的用法，不是漏洞的引入点 High
RC-3 旧版本范围被降优先级，多入口使分诊延迟到 3 月 14 日才确认 Safety Fishbone + 5 Whys B 是。解释响应时间 Medium
RC-4 CVE 公开时影响矩阵不足，changelog 模板造成混淆，伙伴未提前获知 Safety Fishbone + 5 Whys C 是。解释沟通，不解释漏洞机制 Medium

可修复的缺陷是分进程信号用了一个外部可见、又没有充分校验的内部头，自托管的 next start 和 standalone 会因此跳过 Middleware。Vercel 托管以及 Netlify、Cloudflare Workers 因路由解耦不在受影响面上。只把 Middleware 当唯一鉴权的用法会放大危害，这是官方已经不建议的模式。分诊入口和公开沟通是另外两条过程链，分别拖慢了确认、并在公开日留下了影响面空白。
