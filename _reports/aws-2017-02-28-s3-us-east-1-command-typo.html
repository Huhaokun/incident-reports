Summary of the Amazon S3 Service Disruption in the Northern Virginia (US-EAST-1) Region

元信息

  • 公司: AWS
  • 标题: Summary of the Amazon S3 Service Disruption in the Northern Virginia (US-EAST-1) Region
  • 日期: 2017-02-28
  • URL: https://aws.amazon.com/message/41926/
  • 原文路径: raw/aws-2017-02-28-s3-us-east-1-command-typo.md
  • 严重度 / 时长: US-EAST-1 S3 及依赖服务数小时；约 12:26 PST GET/LIST/DELETE 可用，约 1:54 PST 全 API（原文未给精确开始时刻）
  • 原文完整度: 中（触发、机制、依赖影响与改进清楚；检测渠道与精确开始时间缺失）

1. 影响（Impact）

  • US-EAST-1 S3 在索引/放置子系统重启期间无法正常服务请求。
  • 依赖服务受影响：S3 控制台、EC2 启动、从快照建 EBS、Lambda 等。
  • Service Health Dashboard 管理控制台依赖单区域 S3，事故期间状态页自身无法更新。
  • 约 12:26 PST GET/LIST/DELETE 恢复；约 1:54 PST 全 API。精确用户数/%：报告未量化。

2. 导火索（Trigger）

排查 S3 计费子系统缓慢时，授权工程师按既有 playbook 执行「小规模移除容量」命令，但输入错误。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 命令输入错误，实际移除的服务器集合远大于意图，包含 S3 索引子系统 与 放置（placement）子系统 所需容量。
  • 两子系统被迫 全量重启；重启期间 S3 无法正常服务。

3.2 促成因素（Contributing）

  • 运维工具缺少「不得低于最低容量」硬闸与输入安全校验。
  • 索引/放置是数据路径核心；同区大量服务依赖 S3。
  • SHD 管理依赖单区 S3，沟通面受损。
  • 核心子系统恢复路径是全量重启，规模大则 RTO 长。

3.3 为何防护没挡住 / 为何潜伏

  • Playbook 存在，但工具层允许错误输入越界执行（控制设计不足，非「未执行 playbook」）。
  • 报告未写该工具此前是否有过类似接近事故。

3.4 证据与未知

  • 证据：官方对命令意图 vs 实际效果、子系统重启、依赖服务列表、恢复时刻、后续工具改动的描述。
  • 未知：首次发现渠道；精确影响开始时刻；用户可见百分比。

4. 检测（Detection）

  • 报告未说明首次发现渠道（监控告警 / 操作员即时察觉 / 客户报障等）。
  • 仅描述重启期间无法服务及依赖服务受影响。

5. 止血（Mitigation）与修复（Fix）

  • 临时止血 / 恢复: 完成索引与放置子系统全量重启并等待容量恢复（12:26 / 1:54 PST 里程碑）。
  • 永久修复: 工具更慢移除容量并加最低容量硬闸；审计其他工具；索引进一步 cell 分区；SHD 多区域（见第 8 节）。

6. 影响为何被扩大（Amplifiers）

  • 子系统规模大导致重启恢复慢。
  • 同区依赖服务连带受损。
  • SHD 管理依赖单区 S3，状态页无法更新，放大客户不确定性。

7. 既有防护与 SOP

  • 存在的控制: 既有 playbook（容量移除）；授权工程师操作。
  • 缺口或失效模式: 工具缺少最低容量硬闸与安全输入校验——SOP/playbook 被执行，但工具设计不足以防止越界（执行了但挡不住）。

8. 后续改进措施（Action Items）

（原文未标 Type/Owner；归档侧归类，owner：原文未指定）

Prevent

  • 工具改为更慢地移除容量，并增加防护，禁止降到最低容量以下。
  • 审计其他运维工具是否缺少同类检查。

Mitigate / Blast-radius

  • 优先推进索引子系统进一步 cell 分区，以加快恢复。
  • SHD 管理控制台不再依赖单区域 S3（改为多区域）。

9. 教训（Lessons）

  • Poorly（归档摘要）: 危险运维工具必须有硬闸与慢速执行；状态页依赖面不能与被监控服务同命运。
  • Well / Lucky: 报告未分项说明。
