背景知识

术语说明
区域后端服务（regional backend service）该区域在处理 Azure OpenAI 及相关 Azure AI 请求时，用来读取账户资源元数据与配置的后端。它会访问一层缓存和一层数据库。本次约 20 倍流量打的就是这个后端，随后把它到缓存层的请求也打满。
内部服务本地缓存 / 缓存未命中（cache miss）其他调用该后端的内部服务会自己缓存一份上述信息，以减轻后端负载。本次一项内部服务在计划部署中清空了自己的缓存，又赶上区域高峰，产生大量缓存未命中。
缓存读取缺陷 / 缓存绕过官方称该内部服务读取自身缓存的方式另有两项缺陷，放大了清缓存的效果，导致大多数查找绕过缓存、直接回源打到后端。
连接容量耗尽（connection exhaustion）基础设施节点实例上的网络连接容量被用尽，无法再建立到缓存层和数据库层的新出站连接。更高延迟会让已有连接被更长时间占用，客户端重试再叠加新请求，是走到这一步的关键路径。
依赖远端连通性的健康检查 / 重启循环每个后端实例的自动健康检查，取决于能否成功连接到数据库层。连不上就判定不健康并按设计自动重启。连接耗尽时会形成重启循环：在服健康实例变少，依赖方重试再打到剩下的实例，从而显著延长故障。
部署模型（Global / Data Zone / Regional）官方补充说明 Azure OpenAI 可按所选部署模型在规定地理边界内跨区域路由请求，静态数据仍留在所选区域。这是理解影响范围的背景，原文并未据此给出本次各模型下的实际分流结果。

1. 影响

  • 官方事实：2026-09-29 10:03–15:58 UTC（18:03–23:58 Asia/Shanghai），Sweden Central 的平台问题影响了 Azure OpenAI Service、Foundry Agent Service、Foundry Models 和 Azure AI services。受影响客户在向托管于该区域的受影响模型与数据面 API 提交请求时，出现间歇性请求失败、延迟升高，和/或 HTTP 500、503。
  • 官方注明：上述时间是整起事故的完整时长，并非针对单个客户；服务可用性的实际影响因客户和资源而异。
  • 官方同时说明：Azure OpenAI Service 通过部署在多个 Azure 区域的模型引擎处理请求，并有流量路由系统支持；按 Global、Data Zone 或 Regional 部署模型，请求可能在规定地理边界内跨区域路由，客户静态数据仍存储在所选区域。本次是否因此减少了部分客户的可见影响：报告未说明，不能据此推断某类部署一定幸免或一定失败。

2. 导火索

  • 官方事实：约 09:38 UTC（17:38 Asia/Shanghai），Sweden Central 一项内部服务的计划部署开始。作为该部署的一部分，该内部服务的缓存被清空；又因为部署正赶上该区域高峰时段，产生了大量缓存未命中。两项缓存读取缺陷放大了这一效果（见根因），到约 10:00 UTC（18:00 Asia/Shanghai）时，打到后端服务的流量已升至约 20 倍正常水平。官方时间线在 10:00 UTC 的表述是“流量开始急剧上升”，与正文“By approximately 10:00 UTC … approximately 20 times its normal level”一并记录，不把两者写成互相矛盾的精确时刻。
  • 官方把这次流量激增称为 trigger，并写明故障被显著延长的主因是后端实例如何判定健康（健康检查依赖数据库连通性，见第 3、6 节）。部署为何安排在高峰、为何部署过程必须清空缓存：报告未说明。
  • 导火索类型：代码发布/升级（归类由本站根据分析归纳，非原报告表述）。依据：原文写明约 09:38 UTC 一项内部服务的计划部署在 Sweden Central 开始，作为该部署的一部分缓存被清空，又因为赶上区域高峰产生大量缓存未命中。计划部署及随之而来的清缓存，是把既有缺陷打到临界点的起始事件。
  • 次要标签：潜伏缺陷被条件触发（同样为本站归纳）。依据：两项缓存读取缺陷，以及健康检查依赖远端数据库连通性，都是部署前已存在的问题；在高峰清缓存后才把后端打到约 20 倍流量，并在连接耗尽时把自动重启变成重启循环。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 打到区域后端的流量升至约 20 倍正常水平后，后端向其缓存层的请求急剧增加，缓存层达到满负荷，延迟上升。
  • 更高延迟使连接被更长时间占用，客户端重试又叠加入新请求，基础设施节点实例上的网络连接容量被耗尽，无法再建立到缓存层和数据库层的新出站连接。
  • 10:03 UTC（18:03 Asia/Shanghai）起，因服务实例不稳定，客户开始看到间歇失败、延迟升高和/或 HTTP 500、503。
  • 上述均为官方对客户可见故障如何发生的直接表述。故障为何久拖不愈，见健康检查重启循环（3.2）。

3.2 促成因素（Contributing）

  1. 两项缓存读取缺陷（官方）：该内部服务读取自身缓存的方式有两项缺陷，放大了清缓存的效果，导致大多数查找绕过缓存、直接调用后端。这是约 20 倍流量能够形成的关键放大器。
  2. 计划部署在高峰清空缓存（官方）：部署本身清掉了本地缓存，又赶上区域高峰，先产生大量缓存未命中。这是导火索，也是负载被突然抬起的条件。
  3. 缓存层打满与连接被拖住（官方）：缓存层 full utilization 推高延迟，连接持有时间变长，相当于在请求量已经很高时进一步占用连接容量。
  4. 客户端与依赖方重试（官方）：客户端重试进一步增加请求；重启循环出现后，依赖服务的重试又把负载打到剩余健康实例上。重试策略的具体实现（是否有指数退避、抖动或重试预算）：报告未说明。
  5. 健康检查依赖数据库连通性并自动重启（官方）：官方明确写道，虽然流量激增是 trigger，“the extended duration of the incident was primarily caused by how the backend service determined whether its instances were healthy”。连不上数据库就失败并按设计自动重启；进入重启循环的实例越多，能服务请求的健康实例越少。
  6. 诊断指标未能指示连接耗尽（官方）：既有网络指标和诊断指标在这一场景下没有有效指示连接耗尽，关联到这一具体原因花了很长时间，因此包括调整实例规模、增加计算和内存在内的多次缓解都无法结束故障，直到健康检查问题被定位并处理。
  7. 单靠扩容无法打破重启循环（官方，亦由事中操作回推）：13:55 UTC 起的规模调整、15:00 UTC 的加计算资源和提高资源限制，以及重启实例，都没有成为转折点；15:40 UTC 将健康检查改为不再依赖远端连通性后，重启循环才停止，可用性才开始恢复。

3.3 因果链 / Five Whys（归档侧整理，依据原文）

  1. 为何客户看到间歇失败、延迟升高和 HTTP 500/503？→ Sweden Central 托管的模型与数据面 API 出现服务实例不稳定。
  2. 为何实例不稳定？→ 节点出站连接容量耗尽，无法新建到缓存层和数据库层的连接；随后健康检查失败并自动重启，在服健康实例变少。
  3. 为何连接容量被耗尽？→ 缓存层被打满导致延迟上升，连接被更长时间占用，客户端重试再叠加请求。
  4. 为何缓存层被打满、后端流量约 20 倍？→ 计划部署在高峰清空了内部服务缓存，产生大量未命中；两项缓存读取缺陷又使大多数查找绕过缓存、直打后端，后端再把压力转到自己的缓存层。
  5. 为何故障持续近 6 小时，而不是在流量冲击后较快收敛？→ 健康检查依赖数据库连通性，连接耗尽时触发自动重启循环；依赖方重试继续打剩余实例。既有指标又没有有效指示连接耗尽，扩容和加资源无法止血，直到 15:40 UTC 改掉健康检查。
  6. 为何健康检查要依赖远端数据库、部署要在高峰清缓存、以及那两项读取缺陷此前为何未暴露：报告未说明（缺陷形态、引入时间、变更窗口与预热要求均未写）。

根因类别：软件缺陷（主）+ 容量/资源耗尽（次）。归类由本站根据分析归纳，非原报告表述。依据：官方把大多数查找绕过缓存归到两项缓存读取缺陷，并把故障被延长的主因写成健康检查依赖数据库连通性、失败后自动重启形成重启循环。这两处都是可修复的设计/代码问题。缓存层打满、节点出站连接耗尽是客户可见故障的直接表现，但是清缓存加缺陷之后的后果，故只作次要标签，不以容量为唯一根因，也不把计划部署本身当作根因。

  • 官方事实：10:17 UTC（18:17 Asia/Shanghai），服务监控检测到该区域 Azure OpenAI Service 请求失败率升高，并向工程团队告警。10:28 UTC（18:28 Asia/Shanghai）工程师介入并开始调查。

6. 影响为何扩大

  • 缓存绕过放大冲击（官方）：高峰清缓存本就会产生大量未命中，两项读取缺陷使大多数查找绕过缓存，后端在约 10:00 UTC 已被打到约 20 倍正常流量。
  • 延迟—占连接—重试的正反馈（官方可直接支持）：缓存层满负荷推高延迟，连接被更长时间占用，客户端重试再增加请求，直到节点出站连接容量耗尽，缓存和数据库都连不上。
  • 健康检查重启循环是延长故障的主因（官方原意）：官方写明 extended duration primarily caused by 实例如何判定健康。按设计自动重启后，健康实例减少，依赖服务重试进一步打到剩余实例。原文没有使用“死亡螺旋”一词，以上为机制整理。
  • 错误的缓解杠杆与过慢的定位（官方）：指标没有有效指示连接耗尽，花费很长时间才关联到这一场景；在定位健康检查问题之前，调实例规模、加计算和内存都无法结束故障。流量来源与部署的关联甚至发生在客户影响已经缓解之后。
  • 影响范围官方限定在 Sweden Central 托管的模型与数据面 API；是否存在跨区域隔离不足、或 Global/Data Zone 路由是否实际带走部分流量：报告未说明，不臆测。
  • 客户端或内部依赖方的重试是否缺少退避：报告未说明具体实现；官方事后建议客户审查带指数退避的重试模式，但未把内部重试缺失写成已证实的原因。

8. 后续改进措施

原文按“How are we making incidents like this less likely or less impactful?”列出已完成与计划项，并另有对客户的建议。以下类型标签由本站归类，非原报告标签。

Prevent

  • 重新配置后端自动健康检查，不再依赖到数据库层的连通性，避免依赖出问题时实例被不必要重启（已完成；亦是事中止血点）。
  • 跨区域提高后端所使用缓存层的资源容量（计划中，预计 2026 年 10 月完成）。
  • 更长期将缓存层分区，以提高吞吐（计划中，预计 2026 年 12 月完成）。
  • 为后端增加额外的节流和限流，以抵御流量突然上升（计划中，预计 2026 年 10 月完成；同时具有 Mitigate 效果）。
  • 两项缓存读取缺陷本身是否已修复、是否增加防缓存绕过的回归测试：报告未说明，官方清单未单独列出该项。

Detect

  • 为后端使用的缓存层增加负载与延迟的监控和告警（已完成）。
  • 改进诊断指标和自动检测，以便更快识别此类问题（计划中，预计 2026 年 10 月完成）。

Mitigate / Blast-radius

  • 事中将健康检查改为不再依赖远端连通性，停止重启循环，服务随后恢复。

Process

  • 更新连接耗尽场景的排障与操作指南（已完成）。
  • Owner、跟踪单、比“预计某月完成”更精确的截止日期：报告未说明。原文未列出发布门禁、高峰变更限制或缓存预热流程的更新。

9. Lessons

官方未使用 well / poorly / lucky 分栏。以下为归档侧解读。

  • 做得好：书面 PIR 把“高峰清缓存 + 缓存绕过 → 约 20 倍流量 → 缓存打满、连接被拖住、重试 → 出站连接耗尽”和“健康检查重启循环延长故障”分开写，机制可验证；给出了从发现、介入、误判杠杆到真正止血的完整时间线；14 分钟内由失败率监控告警；最终改的是健康检查而不是继续只扩容；已完成健康检查解耦、缓存层负载/延迟告警和排障指南；并如实写出既有指标未能指示连接耗尽、规模调整没有显著效果。对客户影响窗口也做了“整段时长 ≠ 每个客户同等受损”的限定。
  • 做得差：计划部署在高峰清空缓存；两项缓存读取缺陷使大多数查找绕过缓存，而事后清单未明确宣布修复它们；健康检查依赖远端数据库这一经典反模式，把一次流量冲击拉长到近 6 小时；连接耗尽在现有指标里不可见，导致数小时加资源和调规模无效；流量来源与部署的关联发生在客户影响结束之后。
  • 运气：报告未说明是否有更糟的持久损坏或数据问题。数据库层在 13:55 UTC 被确认是健康的，影响官方限定在 Sweden Central，但原文并未把这些写成运气。
  • 我们的建议（非官方承诺）：把“健康检查是否耦合远端依赖”和“发布是否清空缓存、是否赶高峰”做成发布与架构门禁；为缓存命中率骤降和出站连接耗尽设独立告警，使值班不必先靠推断才能放弃扩容；内部服务之间的重试必须有预算。这些不是官方承诺。
