Next.js Middleware 旁路漏洞 CVE-2025-29927 安全事故复盘（自托管受影响；Vercel 托管偶然不受影响）

元信息

  • 公司：Vercel / Next.js
  • 标题：Postmortem on Next.js Middleware bypass
  • 事故日期：披露 2025-02-27；公开 CVE 2025-03-21；复盘发布 2025-03-25（利用窗口与规模：报告未量化）
  • 原文：https://vercel.com/blog/postmortem-on-next-js-middleware-bypass
  • 原文路径：raw/vercel-2025-03-nextjs-middleware-bypass-cve.md（同名 .html 为完整源页面）
  • 发现线索：用户要求收录 Vercel 故障；官方 Security 博文（Ty Sbano）
  • 类别：事故复盘（安全事件 postmortem；学习价值高）
  • 严重度/时长：CVE 标为 critical；从首次私报（02-27）到补丁合并（03-17）约 18 天；到公开（03-21）约 22 天
  • 原文完整度：中高（时间线与托管面影响矩阵清楚；技术机制点到内部头 x-middleware-subrequest，完整利用细节指向研究员原文；无被利用事件量化）

背景知识（术语）

术语说明
MiddlewareNext.js 在缓存与路由之前运行的请求拦截层，可 redirect/rewrite/改请求
x-middleware-subrequestNext.js 内部头，用于防止 Middleware 递归，并在子请求中标记“Middleware 已跑过”，从而绕过再次执行 Middleware
next start / output: 'standalone'自托管常见运行方式；本次确认受影响
Static export无服务器运行时则无 Middleware，本次排除
LTS policy事后发布的长期支持策略；曾计划把 11.x/12.x 移出安全补丁支持，后因社区反馈对 12.3.5 等做了例外 backport
Deployment adapters把 Next.js 部署到 Netlify/Cloudflare 等平台的适配层；路由解耦者不受影响

1. 影响（Impact）

  • 漏洞：攻击者可借助内部头机制绕过 Middleware 执行。许多应用用 Middleware 做基于 cookie 的乐观鉴权/拦路由——绕过可能导致未授权访问（原文强调不建议仅靠 Middleware 作为唯一防护）。
  • 受影响：自托管 next start 与 output: 'standalone'。
  • 不受影响：Static exports；Vercel 托管（路由逻辑解耦、独立全球系统，偶然不受影响）；Netlify 与 Cloudflare Workers 适配（同样因路由解耦，确认从未受影响）。
  • 是否发生大规模在野利用 / 受影响应用数：报告未说明。
  • Vercel 平台自身生产流量事故：无（本篇是框架安全复盘，不是平台宕机）。

2. 导火索（Trigger）

  • 安全研究员经 GitHub private reporting（及邮件 security@vercel.com）披露；后续邮件扩大受影响版本范围。
  • 本站归纳 trigger_types：潜伏缺陷被条件触发（本站归纳）。证据：内部头设计长期存在，经外部披露与可利用条件被确认；非一次配置推送导致的运行时宕机。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • Middleware 与页面渲染分进程；为防止递归并在 Middleware 内 fetch 应用时告知“已执行”，引入内部头 x-middleware-subrequest。
  • 该头可被外部构造时，足以跳过 Middleware，使依赖 Middleware 做鉴权/拦截的应用暴露受保护路由。
  • 修复方向：对传入的该头做校验，失败则过滤；无法升级者可在到达 Next.js 前剥离该头。

3.2 促成因素（Contributing）

  1. 内部头未文档化且缺少严格校验，可被外部滥用（改进项 deployment adapters / 文档化或替换 API 即证）。
  2. 常见但不被官方推荐的模式：仅用 Middleware 做鉴权边界，放大了漏洞业务危害。
  3. 分进程架构迫使引入跨进程信号，增加了信任边界。
  4. 分流披露与版本范围判断失误：初报仅 12.x → 低优先级；多线程邮件与内部讨论拖慢；到 03-14 才确认有效。
  5. 对外沟通缺口：公开 CVE 初期未说清 Vercel/Netlify/Cloudflare 是否受影响；changelog 套用 Firewall 模板造成误解。

3.3 Five Whys（归档侧整理）

  1. 为何能绕过鉴权中间件？→ 可伪造/滥用 x-middleware-subrequest 使 Middleware 被跳过。
  2. 为何存在该头？→ 分进程 Middleware 需要防递归与子请求信号。
  3. 为何外部可滥用？→ 缺少充分校验；内部头未作为公开可信边界加固。
  4. 为何响应偏慢？→ 初报版本旧被降优先；多渠道报告与内部沟通延迟。
  5. 为何社区一度恐慌 Vercel 是否中招？→ CVE/changelog 未及时、清晰说明托管面矩阵。

3.4 证据与未知

  • 证据：完整披露→补丁→CVE→backport 时间线；托管面四类结论；修复策略与 workaround。
  • 未知：完整利用 PoC（指向研究员）；在野利用数据；哪些鉴权伙伴产品受间接影响。

本站归纳 root_categories：软件缺陷 + 安全/攻击（本站归纳）。证据：框架缺陷导致可绕过安全边界的 critical CVE。

4. 检测（Detection）

  • 外部负责任披露（GitHub private reporting + 邮件），非生产监控发现。
  • 03-14 Next.js 工程确认漏洞有效；此前分流与优先级问题造成延迟。
  • 是否有客户环境告警先发现：报告未说明。

5. 止血（Mitigation）与修复（Fix）

  • 临时/缓解：无法升级的应用可在请求到达 Next.js 之前过滤 x-middleware-subrequest。
  • 永久：校验该头，失败则过滤；补丁发布：

- 14.2.25（03-17）、15.2.3（03-18）

- backport 13.5.9（03-22）、12.3.5（03-23，LTS 例外）

  • Vercel 托管：架构上本不受影响；03-22 发 changelog 澄清客户受保护（但模板提及 Firewall，沟通质量差）。

6. 影响为何被扩大（Amplifiers）

  • 初报版本范围误判 → 分诊延迟。
  • CVE 公开时细节不足 + 未主动协同告知 Netlify/Cloudflare/鉴权伙伴 → 生态不确定与沟通债务。
  • Changelog 模板不当放大误解。
  • 仅依赖 Middleware 鉴权的应用模式放大潜在安全影响面（非平台宕机放大器，而是危害放大器）。

8. 后续改进措施（Action Items）

Prevent

  • 发布 LTS 政策，明确安全补丁支持范围。
  • 推进官方 deployment adapters API；文档化或替换内部头。
  • 继续评估 Middleware 其他安全加固点；后续问题走新 CVE 流程。

Detect / Process

  • 合并报告入口，仅用 GitHub private vulnerability reporting for Next.js。
  • 改进披露响应与 Next.js 漏洞 runbook；理顺安全工程与框架团队协作。
  • 开通 partners@nextjs.org 伙伴邮件列表，主动协同基础设施与鉴权伙伴。

Mitigate

  • 已提供升级补丁与前置过滤 workaround。
  • Owner/日期：报告未说明。

9. Lessons（归档侧解读）

  • 做得好：最终给出清晰托管面矩阵；补丁与多版本 backport（含 LTS 例外）；公开承认沟通失误；奖励负责任披露。
  • 做得差：初报优先级与多渠道分流；CVE/changelog 沟通不足；内部头信任边界设计。
  • 运气：Vercel/Netlify/Cloudflare 因路由解耦偶然不受影响，缩小了最大平台爆炸半径。
  • 我们的建议（非官方承诺）：鉴权必须在 Middleware 之后的应用层再强制一次；任何“内部”请求头默认不可信；安全复盘应在公开当日同步发布影响矩阵。
