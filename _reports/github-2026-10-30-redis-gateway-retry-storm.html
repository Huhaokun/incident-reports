背景知识

  • 连接风暴：依赖短暂不可用时，客户端在没有重试预算或抖动退避的情况下密集重连，把中间网关的连接容量打满，连共享同一路径的其他服务也被拖垮。
  • 重试预算：限制重试的次数、速率或并发，避免恢复期的重试本身成为新的故障源。

1. 影响

Actions workflow 处理、Pages 部署和 webhook 投递出现延迟，code search 和实时更新返回错误。缓解后部分 Actions 队列仍需额外时间排空。共享同一网络路径的其他服务也降级。

2. 导火索

一次云网络网关维护。该网关连接 GitHub 数据中心里的某套 Actions 服务，和位于 Azure Central US 的 Redis 集群。

3. 根因

直接原因

维护期间，该服务的 Redis 客户端激进重试并重新拨号，形成连接风暴，把网关打满，约 90% 的连接尝试失败。

促成因素

其他服务走同一网络路径，一并降级。重试没有足够的抖动退避、更短的连接超时和重试预算（这些是事后才加强的）。

防护为何没挡住

网关维护时，客户端重试没有被限制在网关可承受的范围内；受影响资源也没有更快地从轮转中摘除。

4. 怎么发现

书面 RCA 未写内部检出渠道。状态页 17:50:54 UTC（01:50 Asia/Shanghai，10-31）创建，与主窗口开始时刻几乎同一时间。

5. 止血与修复

临时：把受影响资源移出轮转，连接风暴停止，网关恢复。

永久（官方）：已经减少该服务的连接重试次数；还在用带抖动的退避、更短连接超时和重试预算进一步改进重试行为；并与基础设施团队一起提高对网关维护的承受力。后两项未写完成态。

6. 影响为何扩大

共享网关路径的服务被同一场连接风暴波及。Actions 队列在网关恢复后仍要排空，关闭时间晚于主窗口。

7. 既有防护与 SOP

防护或 SOP是否存在本次表现
将故障资源移出轮转存在（事中用了）生效，风暴随即停止
Redis 客户端重试预算 / 抖动退避当时不足，事后加强激进重试放大了维护影响
对网关维护的弹性事后改进未挡住这次维护窗口

8. 后续改进措施

  • Prevent / Mitigate：已减少连接重试次数；继续加抖动退避、短超时和重试预算；提高对网关维护的承受力（后两项进行中）。

9. 教训

  • 做得好：摘除故障资源后风暴迅速停止；事后先减了重试次数。
  • 做得差：维护窗口里没有重试预算，客户端把一条受损路径打成全局饱和。
