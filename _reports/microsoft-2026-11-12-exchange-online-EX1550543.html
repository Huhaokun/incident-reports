背景知识

  • Exchange Online：微软 Microsoft 365 里的托管邮件与日历服务，Outlook 各端都连它取信、发信和读日历。本次受影响的是用户连到自己邮箱这一步。
  • Outlook on the web / MAPI / EAS / REST：四种连接邮箱的方式：网页版 Outlook、桌面版 Outlook 用的 MAPI 协议、手机常用的 Exchange ActiveSync，以及第三方应用和 Microsoft Graph 用的 REST 接口。官方列出这四种都可能连不上，说明故障在它们共用的接入层，而不是某一个客户端。
  • Service Health 事件编号（EX / MO / TM）：管理中心里每条事件有一个编号，前缀代表服务：EX 是 Exchange Online，MO 是 Microsoft 365 整体，TM 是 Teams。本次主事件是 EX1550543，跨服务影响另记在 MO1550821。
  • 接收并处理用户访问请求的基础设施：官方 17:45 UTC 对出问题那一层的说法（infrastructure which receives and processes users' access requests）。对外未给内部名字；昆士兰大学转述为 Microsoft 365 的 network gateway（二手）。
  • 自动健康检查与摘除：负载均衡定期探测每台服务器，探测失败就把它移出服务，不再给它分流量。本次大量服务器探测失败被摘除，剩下的服务器被迫接住全部流量。
  • 负责建立安全连接的进程：01:06 UTC 的说法（a process ... responsible for establishing secure connections）。HTTPS 这一步通常是 TLS 握手，CPU 开销较大。公告没有点名组件。
  • 级联故障（容量雪崩）：一部分服务器倒下，流量压到剩下的服务器上，它们也被压垮，再被摘除。这里用它概括公告里的“服务器不可用 → 剩余设施负载升高”。

  • 范围从美洲扩到全球。17:54 UTC @MSFT365Status 首帖写的是“in the Americas”；18:07 UTC 改称“may affect Microsoft 365 service connectivity for users in any region”。

2. 导火索

  • 截至快照，导火索未被官方确认。
  • 时间顺序：18:27 UTC 在核查“an unexpected increase in a specific type of service traffic”是否推高负载；18:57 UTC 在查升高的流量是真实请求增长，还是流量在基础设施中路由方式的变化；19:18 UTC 结论是负载升高不是总流量增长，而是大量服务器意外不可用。
  • 19:43 UTC 称服务器自动健康检查失败“may be related to a recent change to a component involved in processing those checks”；19:57 UTC 又称“we haven't identified any recent changes that correlate with the start of impact”；20:56 UTC 称近期变更审查找到“a small number of configuration updates”作为可能的促成因素；21:31 UTC 在评估回滚这些配置更新；01:06 UTC 称已开始回滚“a recent network configuration change that correlates with the start of impact”，并在观察它是否有助恢复。
  • 可能的导火索是那项与影响开始时间相关的近期网络配置变更。时间相关还不是因果确认，变更内容与范围没有写出。导火索类型仍是无法判断。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • Exchange Online 中“receives and processes users' access requests”的那部分基础设施出现连接错误（17:45 UTC）。
  • 大量服务器意外不可用，负载转移到剩余基础设施上，造成多区域负载升高（19:18 UTC）。服务器之所以不可用，是因为自动健康检查失败（19:43 UTC），且服务器在处理请求时处理器占用升高（19:57 UTC）。
  • 受影响服务器上的一个核心进程被压垮，服务器停止响应，造成容量损失（22:03 UTC）；后续明确为“a process on the affected servers responsible for establishing secure connections becomes overwhelmed, causing the servers to stop processing requests”（01:06 UTC）。
  • 已恢复的服务器开始接流量后可能再次无响应（23:59 UTC）。

3.2 促成因素（Contributing）

  1. 健康检查失败会把服务器移出服务，19:57 UTC 起阻止继续摘除。摘除后剩余服务器更忙、再失败、再摘除，可能形成正反馈。
  2. 处理健康检查的组件可能本身有问题：19:43 UTC 称可能与该组件近期变更有关；19:57 UTC 部署绕过它的定向变更；20:56 UTC 换用替代健康检查后，一部分服务器回到服务。
  3. 建立安全连接的进程被压垮后，服务器停止处理请求。当时在部分服务器上验证一项针对它的配置变更。
  4. 近期网络配置变更与影响开始时间相关，作用未确认。01:06 UTC 起回滚，效果在观察。
  5. MO1550821 列出的十几项服务都因依赖 Exchange Online 而受影响。
  6. 恢复的服务器接流量后可能再次无响应。公告随后限制可进入的流量类型，并写容量恢复后客户端会逐步重连。集中重连可能再次压垮刚恢复的容量。

3.3 因果链

  1. 为何用户连不上邮箱？→ 负责接收和处理用户访问请求的基础设施出现连接错误，容量不足。
  2. 为何容量不足？→ 不是总流量增长，而是大量服务器意外不可用，负载压到剩余设施上。
  3. 为何服务器不可用？→ 自动健康检查失败被移出服务；负责建立安全连接的进程被压垮，服务器停止处理请求。
  4. 为何该进程会被压垮？→ 当时在验证两条线：回滚一项时间相关的网络配置变更，以及针对该进程的配置变更。再往下没有公开证据。
  5. 为何恢复稳不住？→ 恢复的服务器一接流量就可能再次无响应，所以要隔离、限流、按流量类型分批放回。

仍待确认

  • 那项网络配置变更改了什么、推到多大范围，以及它是不是导火索。
  • 建立安全连接的进程是哪个组件、为何被压垮。
  • 健康检查一次能摘除多少容量；“specific type of service traffic”具体是什么。
  • 受影响用户数、失败比例、邮件有没有丢失。
  • 哪一项事中动作是最终修复，以及事后整改清单。

4. 检测

  • EX1550543 在 Service Health 上的开始时间是 16:17 UTC（00:17 Asia/Shanghai），第一条更新在 16:20 UTC（00:20）发出：“We're investigating a potential issue and checking for impact to your organization”。
  • 17:45 UTC（01:45）定位到连接错误发生在接收并处理用户访问请求的那部分基础设施；17:54 UTC（01:54）@MSFT365Status 首次公开发帖，此时距开始时间约 1 小时 37 分钟。
  • 二手：The Verge 称从美东时间周四下午 1 点前后（约 18:00 UTC）开始有大量用户报告。
  • 从 Service Health 开始时间到首条公告约 3 分钟；到 @MSFT365Status 首帖约 1 小时 37 分钟。
  • 从开始到确认“不是流量增长，而是服务器不可用”用了约 3 小时（16:17 → 19:18 UTC）；到确认“建立安全连接的进程被压垮”用了约 8 小时 50 分钟（→ 01:06 UTC）。

5. 止血与修复

事中止血

  1. 18:19–18:29 UTC（02:19–02:29）：重启和修复受影响设施；把一部分流量从美国的受影响设施切走。
  2. 18:43–18:57 UTC（02:43–02:57）：把 Outlook 连接流量重新分配到全球更大范围的设施上，可能带来一定延迟；随后完成重新分配并继续迁出流量、重启服务器。

6. 影响为何扩大

  • 服务器检查失败被移出服务，负载转到剩余设施；19:57 UTC 才阻止继续摘除。摘除可能形成正反馈。
  • Copilot、Graph、Purview、Defender、Teams 日历等都要走 Exchange Online，邮箱连不上会扩成十几项服务降级。
  • 18:27–18:57 UTC 在查某类流量增长和路由变化，19:18 UTC 才确定是服务器不可用。
  • 跨区域重新分配只带来 “limited recovery in some regions”，可能把同样的压力搬到其他区域。
  • 恢复后的服务器再次无响应，因此改为隔离、限流、按流量类型分批放回。
  • 20:38 UTC 称很多服务器无响应，定向变更是否有效当时确认不了。
  • 19:57 UTC 称没有相关变更，01:06 UTC 才开始回滚。若它是导火索，从开始到回滚约 8 小时 50 分钟。

8. 后续改进措施

事中动作按 Prevent / Detect / Mitigate / Process 列出。标成「建议」的不是微软承诺。

Prevent

  • 回滚一项与影响开始时间相关的近期网络配置变更（01:06 UTC 开始，效果在观察）。
  • 针对“建立安全连接的进程”的配置变更，先在部分服务器验证再推广（01:06 UTC）。
  • 用之前的软件配置重建一部分服务器，看能否防止它们再次无响应（23:59 UTC）。
  • 建议：健康检查一次能摘除的服务器比例要有上限；处理健康检查的组件与业务进程的资源要隔离。

Detect

  • 建议：对“被健康检查摘除的服务器比例”和“建立安全连接的进程的资源占用”单独告警。

Mitigate / Blast-radius

  • 跨区域重新分配流量、隔离部分设施后逐步放回、保护性流量管理、按流量类型限流、替代健康检查、自动检测并重启无响应服务器（见第 5 节）。
  • 22:03 UTC 在评估按区域隔离流量。
  • 建议：接入层按区域或单元分批推配置；恢复时控制客户端重连速度。

Process

  • 19:06 UTC 暂停全部部署和配置变更。
  • 建议：把“时间上与影响开始相关”的网络配置变更列为首批回滚候选。本次从“未发现相关变更”到开始回滚相隔约 5 小时。

9. Lessons

做得好

  • 沟通频率高：16:20 UTC 起约每 30–60 分钟更新一次，管理中心打不开时给出公开状态页。
  • 19:06 UTC 暂停全部部署和配置变更。
  • 明确写出“不是流量增长，而是服务器不可用”。

做得差

  • 健康检查摘除把局部故障变成容量雪崩，事中才阻止进一步摘除。
  • 前几个小时排查方向在流量增长上；“未发现相关变更”的结论后来被修正。
  • 恢复的服务器接流量后会再次倒下，恢复只能分批推进。截至快照已超过 10 小时。

运气

  • Teams 核心消息与在线会议、直接访问 SharePoint 文件基本可用。
  • 公告只写邮件投递可能延迟，没有写丢信；昆士兰大学转述称排队邮件预计会送达（二手）。
  • 学习价值：健康检查是保护机制，但当所有服务器同时“生病”时，它会把容量一次摘光。摘除要有比例上限，健康检查本身也不能和业务抢同一份资源。
  • 学习价值：多项服务共用的接入层，故障面等于所有上层服务之和。Copilot、Graph、Purview 跟着邮箱一起降级，说明“邮件”在 Microsoft 365 里是许多功能的底座。
  • 学习价值：“与影响开始时间相关的变更”应该尽早回滚验证，而不是等其他手段都失败。
