背景知识

  • 网络网关（networking gateway）：Microsoft 365 里承接用户连接、再转到 Exchange 等服务的前端。这次故障发生在这一层。Microsoft 365 有两套相互独立、异构的网关，许多服务可以在两套之间切换。
  • 锁竞争：多个线程或进程等待同一把锁，把 CPU 和内存耗尽，机器不再响应。初步 PIR 写这发生在一个内部 Windows 进程中，而且在核心数更多、硬件更新的机器上更严重。
  • Capacity unit / 隔板：网关容量按单元和区域切片，用来限制爆炸半径。这次由于另一个问题，隔板没有挡住全球级联。
  • 安全部署（safe deployment）：分阶段把变更铺到全球。这次从 7 月起铺了数周，之后三个多月看起来正常，仍然漏掉了只在特定负载和硬件上出现的锁竞争。
  • 连接处理代码：网关上负责建立连接的那条路径。07:20 UTC 起生效的缓解，是把这条路径撤回到先前已知良好的状态。

1. 影响

  • 最严重的是 Exchange Online。多数用户无法通过 Outlook 或其他邮件客户端访问邮箱，很多人邮件投递延迟。
  • 依赖 Exchange 的功能受影响，这些产品的其余部分大多仍可访问。初步 PIR 列出 Exchange、Copilot、Teams、SharePoint、OneDrive、Defender、Purview、Fabric、Intune、Planner、Power Apps、To Do、Power BI、Universal Print。
  • Teams、OneDrive、SharePoint 和 Office 应用把流量切离了出问题的网关，所以更早部分恢复。聊天和会议在大部分时间可用。Exchange Online 因规模不能切离。
  • 严重程度随地区、连接方式和时间变化，期间有过部分或间歇恢复。最低点超过 80% 的网关服务器无响应。
  • 初步 PIR 写到第三方故障上报站点出现用户报告，没有给出 Downdetector 计数或租户数。BBC 曾引述 Outlook 问题报告峰值近 14 万（二手），不写入官方影响。

2. 导火索

  • 11-12 01:07 UTC（09:07 Asia/Shanghai），自动化故障转移把 Teams 从另一套网关切到与 Exchange Online 共用的主网关。这是日常韧性操作。
  • 之后约 15 小时，负载逐渐上升。部分地区出现孤立的服务器故障，自动化缓解介入过。美国高峰到来时，7 月的潜伏缺陷被打出。
  • 同一时段，约 14% 的网关服务器容量因前一日的无关问题不在服务中，本来会按例行维护和健康流程加回来。官方写明服务有足够余量，这次容量下降本身不会造成故障。
  • 导火索类型是自动化/定时任务（本站归纳）。14% 的缺口不单独立为导火索。
  • 此前事中口径「早先网络容量升级，经近期网络变更暴露」已被初步 PIR 取代。那是当时的对外说法。初步 PIR 的直接原因是 7 月的网关专用 Windows 修复。

3. 根因

3.1 直接原因

  • 一处潜伏缺陷让 Windows 服务器在特定负载下不再响应。内部 Windows 进程发生锁竞争，CPU 和内存被耗尽。
  • 缺陷来自专门为 Microsoft 365 网络网关准备的一处修复，不影响更广泛的 Windows 部署。行为变化从当年 7 月开始部署，经过安全部署，数周内铺到全球，之后三个多月没有观察到问题。
  • 常规负载测试没有发现它。实验室的流量组合和 SKU 与生产不同。锁竞争在核心数更多、硬件更新的机器上更严重，负载测试却更常用核心更少的弱机器。
  • 调查把用户侧的大面积失败定位到连接协商：负责建立连接的进程被压垮。撤回的就是这条连接处理代码。

3.2 促成因素

  1. Teams 切到主网关之后，负载升高，流量形态改变。
  2. 约 14% 的网关容量暂不可用。单凭这一点不会出问题。
  3. 流量管理按设计把用户从失联节点转到其余端点。缺陷跟负载相关时，同样的负载集中到更少的服务器上，不到两小时就在整个机群触发同一缺陷。
  4. 网关由大量 capacity unit 组成，再按区域组织，本应有隔板。由于另一个问题，隔板没有挡住级联，影响扩到全球。隔板为何失效：未知。
  5. Exchange 不能像 Teams 等服务那样切离该网关。

3.3 因果链

  1. 用户连不上邮箱，是因为网关停止响应，连接建不起来。
  2. 网关停止响应，是因为锁竞争耗尽了 CPU 和内存。
  3. 锁竞争来自 7 月那项网关专用修复，被「Teams 自动切流 + 约 14% 容量缺口 + 美国高峰」打出。
  4. 它变成全球故障，是因为自动导流继续把负载堆过去，隔板又没有挡住。
  5. 恢复用了很久，是因为机器一接流量就再次倒下，而且数月前的变更撤不掉。分批撤回连接处理代码之后才稳住。

3.4 为何没挡住

  • 安全部署和三个多月的平静，没有覆盖生产高峰、新硬件、更高核心数，以及 Teams 切流后的流量组合。
  • 常规回滚、flighting 和 feature flag 无法快速撤掉几个月前的变更。
  • 自动恢复流程不是为「大范围服务器无响应，刚恢复又被等待流量打回」设计的。

已被取代的说法：事中曾把机制写成建立安全连接的进程被压垮，并回滚一项与开始时间相关的近期网络配置。初步 PIR 保留了「建立连接的进程被压垮」这一调查结论，把根因写成 7 月的锁竞争；07:20 UTC 生效的是撤回连接处理代码，不是那项事中的网络配置回滚。

4. 怎么发现

  • 16:03 UTC（00:03，11-13）连通性异常检测发现终端用户连通问题增加。
  • 16:17 UTC 自动化开始把流量转到其他端点。
  • 16:20 UTC 高优先级告警显示 Exchange Online 受影响，Service Health 以 EX1550543 对外通报。初步 PIR 把 16:20 UTC 记为事故开始。
  • 16:25 UTC 确认 Outlook、Outlook on the web、Exchange ActiveSync，以及 Messaging 和 REST API 都有问题。
  • 16:33 UTC 出现与此事件相关的首个支持工单。

5. 止血与修复

当天后半夜到次日早晨，多次重启、修理、改健康检查、关自动导流、加容量、调协议和封禁流量，都只能换来部分或短暂恢复。刚回到服务的服务器一接到流量又无响应。有的机器卡在坏状态，变更同步不进去。

11-13 00:30–01:00 UTC，调查把广泛的接入失败定位到连接协商，认定负责建立连接的进程被压垮。07:20 UTC 找到有效缓解：把有问题的变更撤回到先前已知良好的连接处理代码，先应用到一部分容量。08:00 UTC 确认这批机器稳定，然后按区域分批处理——把一组服务器下线、打上这处更新、重启，再接回流量。一批可以是某区域一半以上的机器，并优先正处于或即将进入高峰的地区。

  • 10:00 UTC：服务开始稳定，容量尚未回到正常。
  • 11:00 UTC：亚太一部分恢复，邮箱访问和邮件处理好转。
  • 11:35 UTC：欧洲回到健康水平。
  • 14:17–14:44 UTC：全球 webmail 可用性回到预期，并在继续观察下保持稳定。
  • 15:54 UTC：多数主要接入方式回到正常流量。
  • 16:10 UTC：确认客户不再有活跃影响，转入延长观察和积压邮件处理。邮件投递窗口被延长，以免排队中的邮件被退回。
  • 11-14 04:15 UTC：延长观察确认稳定后，发布 EX1550543 和 MO1550821 的最终客户更新。这是客户通报的收尾，不是最终 PIR。

初步 PIR 表里标为已完成的，是上面这次代码撤回、延长投递窗口并处理排队邮件、为恢复加的容量、对导流模式和连接处理健康的监控，以及避免级联的流量分配护栏。完整修复清单留到最终 PIR，日期写的是 2026-11-20。截至 2026-11-20 上午还没有在公开渠道读到那份清单，这里不把它写成已经发布。

6. 影响为何扩大

  • 自动把流量从失联节点转到其余节点，在缺陷跟负载相关时会制造级联。不到两小时扩完整台机群。
  • 隔板失效，故障穿过区域。为何失效：未知。
  • Exchange 不能切离该网关，邮箱恢复最慢。能切走的服务，聊天和会议大部分时间还在。
  • 恢复阶段的等待流量再次打满刚回来的服务器。自动化恢复扛不住这种广度。

8. 后续改进措施

初步 PIR 标为已完成

  • 把连接处理代码撤回到先前已知良好状态。
  • 延长邮件投递窗口，避免排队邮件被退回，并处理事件期间排队的邮件。

我们的建议（非官方承诺）

  • 打给网关的补丁，要用接近生产的流量组合，以及核心数更多、规格更高的硬件做负载测试。
  • 自动导流要能在同一缺陷于目标端点再现时刹停。
  • 隔板要在真实的级联里演练过。
  • 几个月前已经铺完的变更，也要能按批次撤回。
  • 恢复程序要能在机器刚回到服务、就被等待流量打满时限制接入。

9. 教训

做得好

  • 异常检测在 16:03 UTC 就看到连通问题。
  • 找到有效修复后按区域分批上线，并优先高峰地区。
  • Teams 等服务能切离故障网关。
  • 延长了邮件投递窗口。

做得差

  • 负载测试与生产的流量组合、硬件规格脱节。
  • 自动导流在负载型缺陷下变成放大机制。
  • 隔板失效。初步 PIR 未解释原因。
  • 数月前的变更无法快速回滚。07:20 UTC 之前的多种缓解几乎不能持久。

运气

  • 缺陷在全球铺开三个多月，才遇到 Teams 切流、14% 容量缺口和美国高峰叠在一起。这不是可依赖的防护。
