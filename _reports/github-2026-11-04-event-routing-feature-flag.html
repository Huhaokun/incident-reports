  • 归类由本站根据分析归纳，非原报告表述。

背景知识

  • Feature flag：用开关控制功能或路由是否生效。这次变更依赖的开关没有按预期设置，而服务把「开关不存在」处理成了停止投递。
  • 不完整回滚：只撤回配置、不撤回代码时，下一次部署仍会按有问题的代码跑起来。这是第二段故障的原因。

1. 影响

Actions、Pages、Webhooks、Code Scanning 和 Copilot coding agent 出现延迟。Actions workflow 和 job 状态更新最多晚 25 分钟；Pages 部署量降到约 4%；webhook 投递降到约 58%；Code Scanning 分析和 Copilot coding agent 会话也延迟。缓解后积压被处理。

2. 导火索

一次针对内部事件路由服务的配置变更。该变更依赖的 feature flag 没有按预期设置。第二次窗口的导火索是后续部署再次带上了未回滚的代码。

3. 根因

直接原因

配置变更让若干事件流的投递被意外暂停。服务在 flag 缺失或未正确注册时没有维持原有行为。

促成因素

第一次在 16:14 UTC（00:14 Asia/Shanghai，11-05）回滚了配置，但代码变更还在。随后一次部署把同一缺陷再带进生产，17:20 UTC 出现第二段影响，17:40 UTC 再次回滚后才稳住。

防护为何没挡住

缺失的 feature flag 没有预发布校验；路由服务把「flag 不存在」处理成了暂停投递，而不是保持原行为。回滚没有覆盖代码，等于只撤了一半。

4. 怎么发现

书面 RCA 未写内部检出渠道。状态页 16:05 UTC（00:05 Asia/Shanghai，11-05）创建，已在第一段窗口开始后约 16 分钟。

5. 止血与修复

临时：16:14 UTC 回滚配置，第一段缓解；17:40 UTC 再次回滚，然后处理排队事件、清空积压。

永久（官方计划）：flag 缺失时保持原有投递行为；增加预发布检查，确认每条路由 flag 存在且注册在正确的所属服务下；降低 flag 归属配错的可能；改进告警，更早发现投递被暂停。未写这些是否已经落地。

6. 影响为何扩大

同一路由层为 Actions、Pages、Webhooks 等多条流服务，一次暂停会同时打断它们。回滚不完整导致故障打了两轮。

7. 既有防护与 SOP

防护或 SOP是否存在本次表现
配置回滚存在第一段有效，但只回了配置、没回代码
flag 缺失时的默认行为当时不安全缺失即暂停投递
预发布检查 flag 是否存在且归属正确事后才加没拦住这次错误配置
投递暂停告警事后改进事发时是否已有未写

8. 后续改进措施

  • Prevent：缺失 flag 时保持原行为；预发布检查 flag 存在且归属正确；降低归属配置出错的可能（官方，未写完成态）。
  • Detect：更早发现投递被暂停的告警（官方，未写完成态）。

9. 教训

  • 做得好：第二次回滚后处理了积压，延迟事件最终被消化。
  • 做得差：回滚不完整会把同一缺陷送回生产；flag 缺失被实现成「停掉投递」而不是「维持原状」。
