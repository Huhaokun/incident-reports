[技术个案] PingCAP 诊断案例 case500：在线关闭 THP 后内核频繁 Hang，TiKV 无法服务

元信息

  • 公司：PingCAP（TiDB 厂商官方诊断案例库；客户/环境身份未披露）
  • 标题：tidb-map diagnose-case-study case500（原文无单独标题，现象为"内核频繁 Hang 住，TiKV 无法提供服务，强制重启机器后恢复"）
  • 日期：报告未说明（案例未标事件日期；环境为 TiDB 2.1.6 / CentOS 7.6 内核 3.10.0-957，属历史案例）
  • 原文：https://github.com/pingcap/tidb-map/blob/master/maps/diagnose-case-study/case500.md
  • 发现入口：PingCAP TiDB 问题导图 https://docs.pingcap.com/zh/tidb/stable/tidb-troubleshooting-map/
  • 原文路径：raw/pingcap-case500-thp-kernel-hang.md（逐字原文）；raw/pingcap-case500-thp-kernel-hang.html（GitHub 页面）；raw/pingcap-case500-resources/（6 张证据截图）
  • 类别：技术个案（数据库 + Linux 内核内存管理疑难排障；不是 PingCAP 自身服务事故）
  • 严重度/时长：报告未说明（只说"频繁 Hang"、需强制重启恢复）
  • 原文完整度：中高（原文已全文归档且含截图证据；但原文本身是短案例，无影响量化、无时间线、无后续是否复发的验证）

1. 影响（Impact）

  • 部署 TiKV 的机器内核反复 Hang 住，TiKV 无法提供服务，只能强制重启机器恢复。
  • 受影响节点数、业务影响、持续时长、Hang 频率：报告未说明。

2. 导火索（Trigger）

  • Hang 出现前约两周，在系统运行中在线关闭了 THP（Transparent Hugepage）。
  • 注意：回滚 THP 配置后 Hang 仍出现——说明"在线切换"已造成的内存状态（碎片）不随配置回滚消失（原文结论支持此解读）。
  • 持续的内存压力是触发 Hang 的必要条件（原文结论）。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 内存长期处于压力下，所有 NUMA node 的 Normal zone 剩余页都低于 min 水位线（vmcore 截图：Node 0 Normal zone NR_FREE_PAGES=10460，MIN=10932）。低于 min 后，所有从 Normal zone 申请内存的线程都必须先参与直接内存回收才能拿到内存。
  • 内核在缺页异常处理路径上卡住：hung task 截图显示 pd-0 线程处于 D 状态超过 120 秒，调用栈为 page_fault → do_page_fault → __do_page_fault → down_read → rwsem_down_read_failed → schedule，即在缺页时等待读写信号量（进程地址空间锁）。原文将其概括为"处理缺页异常时发生了信号量死锁，且引发条件和 alloc stall 有关"。
  • 用户态表现：TiKV 日志出现大量 channel overflow，无法及时写日志；top 显示 Load 很高但 CPU 利用率不高——典型的大量线程阻塞在不可中断睡眠（D 状态）。

3.2 根因机制（原文结论）

  • 在持续内存压力下动态开/关 THP，会触发大页与小页之间的转换（页面迁移、内存规整/compaction），导致内存碎片过多。
  • 碎片 + 持续压力 → 分配频繁失败、alloc stall/mem stall 持续升高、sar -B 的 pscand/s（直接回收扫描页数）持续偏高 → 跌破 min 水位 → 全员直接回收 → 缺页路径上的锁等待链拖死系统。

3.3 促成因素（Contributing）

  1. 在线修改 THP：运维变更直接在运行中切换内核内存特性，而原文建议的做法是开机即关或修改后重启。
  2. 脏页积累：原文建议"根据磁盘 IO 能力适当降低 dirty_ratio"，说明大量脏页拖慢回收、加重了内存压力（原文以建议形式给出，具体脏页数值未说明）。
  3. 长期高内存压力：业务内存使用与系统可回收余量之间缺少余量（原文未给出内存配置数值）。
  4. 回滚配置不等于回滚状态：THP 配置回滚后碎片状态仍在，导致"回滚无效"误导排查（归档侧推断，由"回滚后 Hang 仍出现"+"碎片"结论得出）。
  5. 旧内核：3.10 系列内核在内存规整/回收方面的行为（是否存在已知缺陷）原文未说明，不作结论。

3.4 Five Whys（归档侧整理）

  1. 为何 TiKV 不可用？→ 机器内核 Hang，线程卡在 D 状态。
  2. 为何内核 Hang？→ 缺页路径上等待地址空间信号量，且所有线程都在做直接回收。
  3. 为何都在直接回收？→ Normal zone 剩余内存低于 min 水位。
  4. 为何长期低于 min？→ 持续内存压力 + 在线切换 THP 造成严重碎片 + 脏页积累拖慢回收。
  5. 为何会在线切换 THP 且回滚无效？→ 缺少"内核内存参数变更须重启/须评估"的变更规范；回滚只改配置不清状态。

3.5 证据与未知

  • 证据（原文 + 截图）：TiKV channel overflow 日志、top 高 Load 低 CPU、mem stall/alloc stall 曲线持续升高、sar -B pscand/s 偏高、hung task 调用栈、kdump vmcore 中各 node Normal zone 低于 min 水位。dmesg 在 Hang 前未见异常（原文）。
  • 未知（报告未说明）：机器内存规格与 TiKV 内存配置；"信号量死锁"的持有者是谁（截图只显示等待方，未显示持锁方）；修复后是否再未复现；THP 在线关闭的具体方式（never 还是 madvise、是否同时关闭 defrag）。
  • 原文"死锁"一词是作者结论，截图本身能证明的是"缺页路径上长时间等待读写信号量"，归档时保留原表述并注明此点。

4. 检测（Detection）

  • 现象层面：内核 Hang、TiKV 无法服务被发现（具体告警渠道：报告未说明）。
  • 诊断路径（本案的主要学习点）：TiKV 日志 → top（高 Load/低 CPU 指向内核阻塞）→ Hang 前系统监控（mem stall、alloc stall）与 dmesg → sar -B → hung task 内核调用栈 → 开启 kdump 在 Hang 时抓 vmcore，分析各 zone 水位。

5. 止血（Mitigation）与修复（Fix）

  • 临时止血：强制重启机器。
  • 永久修复（原文建议，非验证结果）：

    • - 在系统启动时就关闭 THP；若已在线关闭，则重启系统。 - 根据磁盘 IO 能力适当降低 dirty_ratio，避免积累大量脏页、减缓回收压力。

  • 原文未说明实施后效果。

6. 影响为何被扩大（Amplifiers）

  • 低于 min 水位后"所有线程都参与直接回收"，把内存问题从个别分配扩散到全机所有需要内存的线程。
  • 缺页路径上的锁等待使大量线程进入 D 状态，Load 飙升，日志写不出（channel overflow），排障信息本身也受影响。
  • 回滚配置无效 → 问题反复出现。

7. 既有防护与 SOP

  • TiDB 部署文档历来建议关闭 THP（原文未引用，此处不作为本案事实）；本案问题不在"是否关闭"，而在"在线关闭"的方式。
  • 系统监控（mem stall/alloc stall）存在且事后可用于诊断，但 Hang 前是否有告警：报告未说明。
  • kdump 是事后开启的（"开启 kdump 在 Hang 时生成 vmcore"），说明此前未常开（推断）。
  • 变更规范 / SOP：报告未说明。

8. 后续改进措施（原文仅为规避建议，归档侧按类型整理）

Prevent

  • THP 在启动参数中关闭，或在线修改后重启（原文）。
  • 按磁盘 IO 能力调低 dirty_ratio（原文）。

Detect（归档侧建议，非原文）

  • 对 PSI memory stall、allocstall、pgscan_direct 设告警；对 Normal zone 剩余页与 min/low 水位的比值做监控。
  • 生产机常开 kdump 与 hung_task 检测，保证下次 Hang 有现场。

Process（归档侧建议，非原文）

  • 内核内存相关参数（THP、dirty_*、min_free_kbytes）变更纳入变更评审，明确"需重启生效"的项。

9. Lessons（归档侧解读）

  • 做得好：证据链完整——从应用日志一路下钻到 vmcore 水位，每一步都有截图。
  • 做得差：在线修改内核内存特性；回滚后仍出现时才意识到问题不在当前配置。
  • 运气：报告未说明。
  • 可迁移经验：① "高 Load + 低 CPU" 优先查 D 状态线程与内核栈；② 配置回滚无效时，要考虑配置已经改变了"状态"（碎片、缓存、连接池等）；③ 内存类 Hang 要提前准备 kdump，否则现场无法保留。

10. 关键时间线

  • 报告未给出具体日期/时刻。相对顺序：在线关闭 THP →（约两周后）内核开始频繁 Hang → 回滚 THP 配置，Hang 仍出现 → 依次收集日志/监控/调用栈 → 开启 kdump 抓 vmcore → 得出碎片 + 低于 min 水位结论 → 给出启动时关 THP / 重启、调低 dirty_ratio 的建议。

学习价值：中文数据库/内核疑难排障范例——从应用症状下钻到内核内存水位，说明"在线切换 THP 的后果不会随配置回滚消失"。
