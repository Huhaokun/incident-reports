Gen 2 Docker jobsCircleCI 上使用第二代 Docker executor 的作业。本次受影响的是这类作业的启动等待时间，不是作业运行中失败。
Resource class / 2xlarge客户为作业选择的 CPU/内存/存储规格。2xlarge 是更大规格；官方称本次等待在 2xlarge 上最长，其它规格后来也变慢。
Bin packing（装箱）把不同大小的作业装进一台已有云主机，使 CPU/内存/存储都放得下。官方称这是经典装箱问题：大规格比小规格更难找到合适空位，小规格可以更紧密地拼在一起。
Ranked instance types（实例类型排序与回退）按优先级列表向云厂商申请机型；首选供应不上就回退到列表中的下一个类型。
Minimum fleet size（最小机队规模）即使需求低也保持一定数量实例在跑，以免低谷时把容量退光；高于该下限后再按需求增加实例。
Queue until capacity没有足够容量执行时，作业排队等待，而不是直接失败。本次客户看到的主要是更长的排队，而不是官方所写的作业执行失败。

1. 影响

  • 官方事实：10 月 21 日 15:44–20:55 UTC，运行 Gen 2 Docker jobs 的客户看到作业启动等待时间升高。延迟在 2xlarge resource class 上最长，作业最多等约 20 分钟。
  • 19:25 UTC 时，2xlarge 等待已达 20 分钟，其它 resource class 的等待也已升高（官方原文）。
  • 20:41 UTC：95% 的 2xlarge 作业在 4 秒内启动；20:35 UTC 排队作业数回到正常水平；20:55 UTC 事件宣布解决。
  • 受影响客户数、作业总数、失败（非等待）比例、是否导致下游发布中断：报告未说明。原文描述的是等待时间升高，没有写作业执行失败或数据丢失。
  • 数据丢失：不适用——原文是调度/容量导致的启动延迟，未提及数据损坏。
  • 影响是否覆盖 Machine executor 或其它产品线：本篇只写 Gen 2 Docker jobs。讨论区相关帖还列出之后的 Oct 28（Gen 2 Docker + IP ranges）与 Nov 3（Linux machine 与 Remote Docker）等待时间报告，是否同一根因复发：本篇未说明，不据此扩写。

  • 官方事实：10 月 21 日 15:44 UTC 起，Gen 2 2xlarge resource class 的需求急剧上升，团队未能足够快地供应额外容量以跟上。
  • 需求为何突然上升（大客户、重试风暴、外部事件、产品发布等）：报告未说明。原文没有把它写成攻击或 DDoS。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 官方：事件由「为满足需求而配置的云实例供应有限」引起，尤其是 2xlarge 作业。
  • 需求上升后，扩容速度跟不上，作业按设计排队，等待时间升高；2xlarge 最严重（最长约 20 分钟）。

3.2 促成因素（Contributing）

  1. 装箱约束（官方）：每台云实例可跑多个隔离作业，但必须同时满足 CPU/内存/存储。2xlarge 这类大规格比小规格更难放入剩余空位。
  2. 已配置的实例类型集合不够（由事中动作回推）：系统本已用排序列表申请机型并在首选不足时回退，但工程团队仍须在 19:56 UTC 向 Gen 2 机队追加更多实例类型，19:59 UTC 才开始供应这些类型——说明既有回退列表未能在当时拿到足够容量。
  3. 最小机队规模偏紧（由整改项回推）：事故中提高了这些新集群的最小机队规模；事后又提高 Gen 2 最小机队以满足当前基线需求。官方未给出事发时的具体数字。
  4. 扩容速度不足（官方）：原文直接写未能足够快地增加容量。高于最小机队后本应按需求加实例，但本次没有及时跟上。
  5. 调度器未优先大规格（由整改项回推）：事后修改调度器，优先调度更大的 resource class，并更公平地平衡各规格等待、更高效装箱。这暗示事故前的调度在大规格争用时对 2xlarge 不利（归档侧回推；官方未用调度器有 bug 表述）。
  6. Docker 作业的可用云区域不足（由事后动作回推）：事件解决后为 Docker jobs 增加了更多云区域（官方称最近已为 Machine jobs 加过区域，现在同样为 Docker jobs 做了）。事故前 Docker 机队的区域范围：报告未给出清单。

3.3 因果链 / Five Whys（归档侧整理，依据原文）

  1. 为何客户要等很久才能开始跑 Gen 2 Docker 作业？→ 没有足够容量，作业按设计排队。
  2. 为何 2xlarge 最严重？→ 大规格更难装箱；本次需求尖峰也集中在 2xlarge。
  3. 为何没有足够容量？→ 已配置可申请的云实例供应有限，且没有足够快地跟上需求。
  4. 为何既有回退与最小机队没挡住？→ 排序回退只在已配置类型之间生效；类型集合、最小机队和区域范围在当时不够（由事中加类型、加集群、提高最小机队及事后加区域回推）。
  5. 需求为何在 15:44 UTC 急剧上升？→ 报告未说明。

根因类别：容量/资源耗尽。归类由本站根据分析归纳，非原报告表述。依据：原文把原因写成 limited availability of the cloud instances we had configured to meet demand, particularly for 2xlarge jobs，症状是排队等待而非软件抛错或外部依赖协议故障。不以「依赖故障」作主类：云实例供应是他们自己机队配置与扩容速度问题；原文没有写云厂商 API 故障。不以「软件缺陷」作主类：调度器事后有改进，但官方未把根因写成 scheduler bug。

6. 影响为何扩大

  • 装箱放大了大规格的脆弱性（官方）：2xlarge 更难放入剩余空位，同样的容量缺口下等待更长。
  • 扩容落后于需求（官方）：从 15:44 需求上升到 19:25 等待见顶，中间约 3 小时 41 分钟容量仍未跟上；其它 resource class 也在 19:25 前被拖慢——大规格排队可能占用或打乱了对其它规格可用的装箱空位（后半句为归档侧推断；官方只写其它规格等待 had increased as well）。
  • 既有实例类型与区域范围构成隐式上限：直到 19:56–20:11 才加入新类型和新集群，说明扩大供应面本身需要人工变更，不能在尖峰中自动打开（归档侧推断）。
  • 按设计排队而不是失败：避免了作业报错，但把影响表现为最长约 20 分钟的启动延迟，窗口被拉到容量补上为止。

9. Lessons

官方未使用 well / poorly / lucky 分栏。以下为归档侧解读。

  • 做得好：用装箱、排序回退、最小机队把调度模型讲清楚；给出 20 分钟与 95% 在 4 秒内启动等可核对数字；改进项直接对应类型集合、最小机队、集群、区域和调度优先级。
  • 做得差：需求尖峰后约 3 小时 41 分钟等待才见顶，说明扩容反馈偏慢；大规格与小规格共享装箱池时，大规格先受伤并拖累其它规格；Docker 机队的区域多样性明显落后于他们已为 Machine jobs 做过的扩展。
  • 运气：影响主要表现为等待而非作业失败或数据丢失（以原文为限）；20:11 加集群后约 24 分钟排队恢复、约 30 分钟 2xlarge 启动时间回到 4 秒量级。
  • 我们的建议（非官方承诺）：把已配置实例类型的供应上限当成明确的错误预算来监控；最小机队应按最难装箱的规格单独留头寸；扩容自动化应能在人工变更类型列表之前先跨区域要容量。
