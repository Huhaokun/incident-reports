背景知识

  • 磁盘读带宽：这次的直接限制在托管 Git 数据的存储服务器上。计划中的仓库迁移抬高读负载后，部分服务器达到磁盘读带宽上限。这些服务器上的一项磁盘配置让它们读入远多于必要的数据，可用带宽大约被砍掉一半。配置项名称：报告未说明。
  • 多副本写入：合并必须写到仓库的每一份副本。一台过载的存储服务器因此会拖慢它托管的所有仓库的 merge，而不是只影响写到那一台副本的请求。这是耐久性设计，也是单点带宽瓶颈被放大的路径。

1. 影响

  • 官方事实：11-16，部分 pull request 合并超时；由 PR 触发的部分 Actions workflow 延迟。push / fetch 等 Git 操作仍可用，但延迟升高。平均 2.9% 的 merge 尝试超时，峰值 7.1%。
  • 事中通报还给出过相对基线（约 0.2%）的即时比例：约 2–3%，一度到 4.75%，缓解前最后确认值为 2.5%。这些是事中数字，峰值 7.1% 以书面 RCA 为准。
  • 受影响仓库数量、用户数：报告未说明。
  • 11-13：同一原因，1.7% 的 merge 超时，窗口更短。该日状态页当时承诺另发详细 RCA，本轮仍未见单独成篇说明。

2. 导火索

  • 官方事实：读负载因计划中的、把仓库迁到新基础设施而增长，部分托管 Git 数据的存储服务器达到磁盘读带宽上限。同时，这些服务器上的一项磁盘配置让它们读入远多于必要的数据，可用带宽大约被砍掉一半。
  • 配置是什么、何时引入、为何在迁移前没被发现：报告未说明。

    • 依据：读负载增长来自计划中的仓库迁移。错误的磁盘配置事先存在，在负载上去之后才把带宽打满。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 部分存储服务器达到磁盘读带宽上限。合并必须写到仓库的每一份副本，所以一台过载的服务器会拖慢它托管的所有仓库的 merge。

3.2 促成因素（Contributing）

  1. 计划中的仓库迁移（官方）：这次迁移抬高了这些服务器的读负载。
  2. 错误的磁盘配置（官方）：配置让服务器读入远多于必要的数据，可用带宽大约减半。配置项名称、引入时间、为何迁移前没被发现：报告未说明。
  3. 合并路径没有把单副本过载隔离开（官方）：一台机器的带宽瓶颈会放大到它所持有的全部仓库。

3.3 为何没挡住

事中多次写已有缓解没有恢复正常性能，直到纠正该配置并迁走最忙服务器上的部分负载。说明在写修复之前，已有缓解没有触及带宽上限和错误配置。是否已有按服务器的磁盘带宽告警：RCA 把这项写成事后将要增加的内容，因此事发时至少没有能在客户受影响前拦住的同类告警。由整改项回推

3.4 证据与未知

  • 已知（官方）：机制和两次事件的数字来自 11-20 的 Resolved 说明。11-16 平均 2.9%、峰值 7.1%；11-13 为 1.7%。纠正配置并迁走热点负载后再出现改善。纠正后的配置已在整个存储机群永久生效。
  • 未知（报告未说明）：配置项名称与引入时间、受影响服务器和仓库的规模、内部检出时刻、两项缓解各自的完成时刻。

6. 影响为何扩大

  • 合并必须写到每一个副本，单台存储过载会拖住它所托管的全部仓库。
  • 错误配置把可用带宽砍半，使计划中的迁移负载更容易碰到上限。
  • 11-13 已经出现过同一机制，11-16 再次发生且峰值更高，说明第一次之后到第二次之前，配置纠正和带宽告警还没有就位。这是由再次发生回推的说明，原文没有单独给出这两天之间的内部变更时间表。
  • PR 触发的 Actions 因此被拖慢；push / fetch 仍可用但变慢。
