GitHub App s2s token 请求 404 升高（MySQL 跨集群表迁移与大规模清理任务重叠，gh-ost 复制延迟）

1. 影响（Impact）

  • 使用 GitHub App 服务器到服务器（s2s）token（不含 Actions token）认证的 API 与 git 请求失败率升高。
  • 认证 git 操作被错误地返回 404：平均 1.24%（基线的 2.6 倍），峰值 2.49%（5.3 倍）。
  • 原文明确排除 Actions token；其他认证方式是否受影响报告未说明（原文只描述 s2s token）。受影响 App/客户数：报告未说明。是否有数据丢失：报告未说明（推断：迁移中读新集群读到未复制的数据，属读一致性问题，不一定有写丢失）。

2. 导火索（Trigger）

  • 计划内维护：把 7 张表从 IAD 数据中心的 MySQL 集群迁移到 Azure Central US 的 MySQL 集群，其中一张存放 GitHub App s2s token 的 installation 记录。
  • 同时，该表上的定时清理任务在 04:44–06:17 UTC 删除了约 5900 万行。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 大批量删除产生的变更量使 gh-ost 迁移工具的跨集群复制延迟最高达 1 小时。
  • 06:55 UTC 开始把读切到新集群（07:21 UTC 读 100% 切完），此时新集群数据落后，查询 installation 记录时找不到（或状态不一致）→ token 验证失败 → 返回 404。影响一直持续到 08:01 UTC 写切换完成。
  • 注：原文没有逐行解释"复制滞后为何具体表现为 404"；上述"读不到记录导致 404"是根据原文因果顺序的归档侧推断（读切换开始即影响开始、写切换完成即结束）。

3.2 促成因素（Contributing）

  1. 两个计划内操作在同一张表上时间重叠，无互斥/协调机制（改进项"迁移前禁用重叠的清理任务"即证）。
  2. 读切换没有以复制延迟为门禁（改进项"复制延迟高时阻止读切换"即证）。
  3. 先切读、后切写的分阶段切换，在复制滞后时形成"读新、写旧"窗口，读到旧数据。
  4. 对切换过程的监控未覆盖该错误模式：原文明确"客户影响开始了，但未被发现"；404 是"看起来合法"的响应码，比 5xx 更难触发告警（推断）。
  5. 过往成功形成的信心：近几个月类似迁移多次无明显影响（原文），没有暴露"与大批量写重叠"这一组合。

3.3 Five Whys（归档侧整理）

  1. 为何 s2s 请求 404？→ 读路径切到了数据落后的新集群。
  2. 为何新集群落后？→ gh-ost 跨集群复制延迟最高 1 小时。
  3. 为何延迟这么高？→ 同表清理任务刚删除约 5900 万行，产生大量需复制的变更。
  4. 为何在延迟高时仍切读？→ 切换流程没有复制延迟门禁；清理任务与迁移没有协调。
  5. 为何未及时发现？→ 报告未说明具体原因，只说"未被检测到"。

3.4 证据与未知

  • 证据：原文给出了时刻、删除行数、复制延迟峰值、错误率与倍数、表数量与数据中心。
  • 未知（报告未说明）：如何最终发现的；为何没有中止切换；新旧集群的数据是否需要修复；s2s token 校验路径为何对缺失记录返回 404 而非重试主库。

4. 检测（Detection）

  • 原文："Customer impact began, but was not detected, throughout the read cutover"。即读切换期间未检测到影响；最终何时、通过什么渠道发现：报告未说明。
  • 事件是否在写切换完成后自然结束（而非被主动止血），原文表述倾向于"持续到写切换完成"，可能是自然结束（推断）。

5. 止血（Mitigation）与修复（Fix）

  • 临时止血：报告未说明任何主动止血动作；影响在 08:01 UTC 写切换完成后结束。
  • 永久修复：报告未说明是否回补数据。

6. 影响为何被扩大（Amplifiers）

  • 读切换是渐进的（06:55 开始，07:21 到 100%），随比例增加错误率上升到峰值 2.49%（推断：峰值与读比例相关，原文未写）。
  • 未检测到 → 无法提前中止或回退切换，影响窗口被拉长到整个写切换完成。

7. 既有防护与 SOP

| 防护 | 是否存在 | 本次表现 | |---|---|---| | 计划内迁移流程（gh-ost + 渐进读切换 + 写切换） | 有 | 有阶段，但没有以复制延迟为门禁 | | 定时清理任务 | 有 | 与迁移无协调，成为触发因素 | | 迁移期间监控 | 有（推断） | 未检测到 404 升高——失效/覆盖不足 | | 正式 runbook | 报告未说明 |

8. 后续改进措施（原文两项，已归类）

Prevent

  • 迁移前禁用该表上的重叠清理任务。
  • 复制延迟高时自动阻止读切换。

Detect / Mitigate / Process

  • 原文未列出。归档侧建议（非官方承诺）：迁移期间按错误码（含 404）对比基线设告警；切换过程中设自动回退阈值；建立"同表计划任务日历/锁"。
  • 原文无 owner/日期；改进项可执行性较好（具体、可验证）。

9. Lessons（归档侧解读）

  • 做得好：给出了精确的错误率倍数、删除行数、复制延迟；改进项直指两个控制缺口。
  • 做得差：两个计划内操作互不知情；切换不看复制延迟；404 未触发检测。
  • 运气：只影响约 1–2.5% 的 s2s 认证请求，且写切换完成后自行恢复。
  • 我们的建议（非官方承诺）：数据迁移的切换门禁至少包含"复制延迟 < 阈值"和"错误码分布与基线一致"两项；对 4xx 也要做基线异常检测，因为数据缺失往往表现为 404 而不是 500。
