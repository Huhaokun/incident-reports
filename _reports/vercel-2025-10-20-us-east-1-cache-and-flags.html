Vercel 双事故：AWS us-east-1 损失引发生产流量中断 + Feature Flag 级联打垮控制面（2025-10-20）

1. 影响（Impact）

官方拆成 两起相对独立的 Vercel 侧事故（均由 AWS us-east-1 事件触发/级联）：

事故 A — 生产流量

  • 直接连到 us-east-1 的用户曾短暂中断；07:15 起开始把流量从 iad1 迁走。
  • 07:45 UTC 级联导致一部分全球缓存基础设施丢失，静态文件服务失败峰值约 22% 流量；08:18 UTC 恢复——官方称此为全程最大冲击。
  • 仅配置 us-east-1 为唯一 Functions 区域、无备份区的客户：Functions 约至 09:21 UTC 恢复。
  • 有备份/次要区域的 Functions：07:25 起开始重路由后恢复。
  • DNS / Anycast CDN IP / L3–L5 / TLS / L7 Firewall / Response Cache：原文标为按预期工作。

事故 B — 控制面（不影响生产流量服务）

  • 约 19:20 UTC 起 Dashboard / API 失败、控制面容器剧烈重启；客户无法部署、回滚等管理操作。
  • Feature flag 不可用 → 主 Kubernetes 集群资源耗尽 → 处理延迟/失败。
  • Dashboard/API 约 10-21 03:30 UTC 完全恢复；Runtime Logs 约 06:21 UTC 完全恢复（部分区域曾有 5–6 小时积压）。

受影响客户绝对数 / 收入：报告未说明。数据丢失：报告未说明。

2. 导火索（Trigger）

  • 外部：AWS us-east-1 意外大范围故障（公开已知）。
  • Vercel 明确：对客户仍全权负责，不把责任推给厂商选型。
  • 本站归纳 trigger_types：硬件或外部依赖故障（本站归纳）。证据：原文“triggered by the unexpected outage of AWS us-east-1”；控制面为 flag 提供商受 us-east-1 下游影响后的级联。

3. 根因（详尽）

3.1 直接原因（Proximate）

事故 A

  1. us-east-1 损失导致该区服务栈与直连流量受损。
  2. 意外级联：全球 Regional Cache 一部分失效 → 静态服务错误升至约 22%。原文称“已经缓解该级联的根因”，但未在本篇解释级联的具体代码/数据路径机制（待后续详细技术复盘）。
  3. 单区域 Functions / Secure Compute / 依赖客户自有 us-east-1 资源的构建，恢复受 AWS API/EC2 容量持续抖动拖长。

事故 B

  1. 控制面虽在 us-west-1，但依赖的 feature flag 提供商在约 19:20 UTC 大面积故障（原文：likely 由更早 us-east-1 下游效应引起）。
  2. Flag 不可用 + 请求超时/代码模式 → 主 K8s 集群资源耗尽、容器剧烈重启、API 500。

3.2 促成因素（Contributing）

  1. Regional Cache / Routing Metadata 与 us-east-1 原点的耦合在极端场景下仍产生超预期爆炸半径（设计声称可单区存活，但出现级联）。
  2. 仅单区 Functions 的客户缺少自动多区冗余。
  3. 控制面对外部 flag 服务的同步依赖路径缺少足够隔离；超时处理模式成为资源耗尽放大器。
  4. 实验性缓解未一次覆盖 100% 服务，导致 10-21 00:20 控制面降级复发。
  5. 日志管线吞吐量在积压下不足（5–6 小时 backlog）。

3.3 Five Whys（归档侧整理；级联缓存部分受原文深度限制）

  1. 为何静态错误到 22%？→ 一部分全球缓存基础设施因级联失效。
  2. 为何单区损失会级联到全球缓存？→ 报告未说明具体机制（仅称已缓解并将写详细技术复盘）。
  3. 为何控制面在 us-west-1 仍垮？→ Flag 提供商超时 → 资源耗尽/容器重启。
  4. 为何 flag 故障会耗尽 K8s？→ 代码中对失败请求的超时/重试模式（原文称 code pattern leading to resource exhaustion；细节有限）。
  5. 为何复发？→ 实验性修复未先落地全部控制面服务。

  • 未知：级联缓存失败的精确根因；flag 厂商名；超时/耗尽的具体代码；客户侧错误码分布。

5. 止血（Mitigation）与修复（Fix）

生产流量

  • 07:15/07:20–07:44：将流量从 iad1 增量迁到邻区。
  • 07:25：为有备份区的客户重路由 Functions。
  • 07:35–07:40：构建机改到其他区域。
  • 级联缓存：08:18 服务恢复；根因称“已缓解”（细节待后续文）。
  • 后续 EC2 容量问题：削减 iad1 非关键供给、Functions 优先其他区域等。

控制面

  • 19:48：缩短超时、降低 flag 失败冲击（减重启，API 仍降级）。
  • 21:20–22:31：实验性修复分批推出。
  • 02:37：全部 flags 客户端改用实验修复。
  • 03:01 / 03:30 / 06:21：日志与 Dashboard/API 相继完全恢复。

6. 影响为何被扩大（Amplifiers）

  • 缓存级联把单区问题扩成全球静态流量约 22% 失败。
  • 单区 Functions / Secure Compute / 客户自有 us-east-1 依赖拉长尾部恢复。
  • Flag 超时模式把外部依赖故障放大成 K8s 资源耗尽与容器重启风暴。
  • 控制面修复未一次铺满 → 次日凌晨复发，拉长管理面不可用。
  • AWS API/EC2 容量在 us-east-1 内反复抖动，造成多次“小回潮”。

9. Lessons（归档侧解读）

  • 做得好：公开承担对客户责任；服务栈与控制面隔离避免管理面故障打生产；告警与 Panic 升级快；请求路径分步对照可读性强；给出 22% 等关键数字。
  • 做得差：单区存活设计仍被缓存级联打破；flag 同步依赖成为控制面单点；修复未一次覆盖导致复发。
  • 运气：大量前序路径（DNS/TLS/Firewall/Response Cache）未垮；“显著流量仍被服务”。
  • 我们的建议（非官方承诺）：外部 flag/配置服务必须 fail-open 或本地缓存兜底；区域缓存失效演练要包含“原点区全黑”假设；多区 Functions 应更接近默认而非可选。
