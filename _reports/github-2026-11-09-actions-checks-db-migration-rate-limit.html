3. 根因（详尽）

3.1 直接原因（Proximate）

  • Actions 在 18:07–18:59 UTC 性能降级，是因为核心 Actions 数据库按计划迁到新云区域并完成迁移后，Actions 服务流量被切到该区域，请求量超过了那里已配置的容量和限流，部分请求被拒绝，workflow 更新失败。部分客户因此看到 workflow runs 无法启动、无法更新，或状态无法正确上报；Webhooks、Pages 和 Copilot code review 出现次生影响。
  • 缓解方式是把部分流量切回原区域，使服务流量回到已配置的限额之内；随后提高新区域的容量和限流，再逐步把流量切回去。
  • 上述为官方对客户可见故障如何发生的直接表述。目标区域的具体容量与限流值、拒绝发生在哪一层、为何校验没有在切流前发现不足：报告未说明，不补写未给出的阈值或自动扩容细节。

3.2 促成因素（Contributing）

  1. 切流发生在迁移完成之后，且目标区域当时的容量和限流不足以承接被切过去的请求量（官方）：故障不是写在迁移拷贝数据的过程中，而是写在 “shifted Actions service traffic to the new region” 之后。切流幅度、是否一次切完：报告未说明。事后要在剩余迁移中改进切流前对容量和限额的校验，并分更小步切流，属由整改项回推：事发时的校验和切流步长，没有在客户受影响之前拦住这次超限。
  2. 部分请求被拒绝后，workflow 更新失败，并传导到依赖服务（官方）：官方明确写出 “a portion of requests were rejected and workflow updates failed”，以及 Webhooks、Pages、Copilot code review 的次生影响。依赖链如何从被拒绝的更新走到这些服务：报告未说明，不补写调用图。
  3. 服务恢复后仍有卡住的 run 占用并发（官方，残留影响而非起始原因）：官方写 “Once Actions services recovered, some jobs were left in a state that limited available concurrency until the runs were released.” 这不是超限本身的原因，但把影响延伸到官方窗口结束之后。卡住 run 的形成机制：报告未说明。事后要改进对此类 run 的检测与缓解，并准备面向客户的 API，属由整改项回推：事发时没有写出一套已生效的自动检测与释放手段。
  4. 此次迁移被写成该集群的一次性事件，且官方表明迁移现已完成（官方，范围限定）： “While this was a one-time migration event for this cluster that is now complete”。它限定了这次切流事件不会按原样重复发生在同一集群，但官方同时写还要进行 remaining migrations，因此切流前校验与分步切流仍然相关。其他集群的容量规划：报告未说明。

为何没挡住：目标区域在承接 Actions 流量之前，已配置的容量和限流低于切过去的请求量，切流后部分请求被直接拒绝。官方事后要改进的正是「在剩余迁移中、切流前校验容量和限额」以及「分更小步切流」，说明事发时缺少一次足以拦住超限的预校验或渐进切流。既有的容量预检、限流告警或自动回切是否存在、为何未在客户受影响前生效：报告未说明。
