背景知识

  • Actions Checks 数据：workflow 检查状态所用的存储。这里它是启动和更新 runs 的共享依赖，内存压力会同时影响新入队和进行中的 job。

1. 影响

部分客户无法启动 GitHub Actions 和 Checks 的 workflow，部分进行中的 runs 失败。峰值约 3% 的 workflow 无法入队，约 0.21% 的进行中 runs 失败。

2. 导火索

一阵高并发、大体积的读请求打到存储 Actions Checks 数据的数据库服务。未说明请求来源。原文并未把这阵流量写成外部攻击。

3. 根因

直接原因

这些大读让该数据库服务陷入内存压力，服务停滞并拒绝请求。

促成因素

当时没有限制大型查询的并发，所以一阵读请求就能把关键 workflow 路径打掉（事后才计划加这类限制）。

防护为何没挡住

内存容量不足以吸收这阵大读；也没有在内存压力出现时挡住大型只读并发。

4. 怎么发现

书面 RCA 未写内部检出渠道。状态页 16:50 UTC（00:50 Asia/Shanghai，11-06）创建，已在窗口开始后约 11 分钟。

5. 止血与修复

临时：对受影响的数据库主机做故障转移。

永久（官方）：已提高受影响数据库集群的内存容量；还将限制大型查询的并发，避免重读流量再次导致关键 workflow 大面积失败。后一项未写完成态。

6. 影响为何扩大

Checks 数据集是 Actions 启动和进行中 runs 的共享依赖，数据库一停滞，入队和已在跑的 job 都会失败。窗口短，但机制上没有读/写隔离。

7. 既有防护与 SOP

防护或 SOP是否存在本次表现
数据库主机故障转移存在（事中用了）生效，窗口约 18 分钟
数据库内存容量当时不足，事后已提高被大读打到停滞
大型只读查询并发限制事后计划当时没有

8. 后续改进措施

  • Prevent / Mitigate：已提高内存容量；将限制大型查询并发（进行中）。

9. 教训

  • 做得好：故障转移很快，窗口只有约 18 分钟。
  • 做得差：大型只读并发没有隔离，可以直接把 Checks 存储打到拒绝请求。
  • 运气：进行中 runs 的失败率只有约 0.21%，主要冲击在入队。
