  • 标题：Post-mortem: Errors for Users with Requests on their Watchlist
  • 事故日期：2026-11-03。部署 10:25 UTC（18:25 Asia/Shanghai）开始，约 11:36 UTC（19:36）应用崩溃停止，11:45 UTC（19:45）纠正迁移全部完成。官方写「大约一小时」。书面复盘于 2026-11-13 发布。
  • 原文：https://openbuildservice.org/2026/11/13/post-mortem/ （Open Build Service 团队官方博客，一手全文。）

  • 严重度/时长：受影响用户在访问该站点的每一个页面时遇到 500，大约一小时。用户数、请求数：报告未说明。

  • 导火索类型（主）：代码发布/升级。依据：一次同时带上 schema 迁移、数据迁移和新代码的部署。

背景知识

  • Open Build Service（OBS）参考服务器：openSUSE 运营的公共 OBS 实例，地址为 build.opensuse.org，用来构建和发布软件包。这次事故发生在这台参考服务器上。
  • Counter cache：把关联对象的数量缓存在父行上，避免每次现查。这次为 BsRequest 增加了「它有多少个 BsRequestAction」的计数缓存。schema 迁移把该计数默认成 0，回填要靠随后的数据迁移。
  • Watchlist 与 BsRequest / BsRequestAction：用户可以把 request 放进 watchlist。页面渲染会用到这些 request。当计数为 0 而代码假定至少有一个 action 时，watchlist 里带有这类 request 的用户，打开任何页面都会 500。

1. 影响

  • 官方事实：2026-11-03，build.opensuse.org 在一次部署之后出现服务退化。watchlist 里带有 request 的部分用户，访问任何页面都会遇到 500，大约一小时。
  • 官方用 certain users 描述范围，没有给出用户数或占总用户的比例。未受影响的用户、构建任务是否中断：报告未说明。
  • 不要把这次写成 openSUSE 或 OBS 的全局停服。

2. 导火索

  • 官方事实：10:25 UTC（18:25 Asia/Shanghai）开始部署 commit ac7108c317…5ddf74e398，10:27 UTC（18:27）执行其中的 schema 迁移。新代码随这次发布一起上线，并立刻依赖 counter cache 的回填结果。
  • 导火索类型：代码发布/升级（归类由本站根据分析归纳，非原报告表述）。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 这次部署同时引入 schema 迁移和数据迁移，为 BsRequest 与 BsRequestAction 的关联加上 counter cache。schema 把计数默认成 0，新代码却假定每条 BsRequest 至少有一个 BsRequestAction。默认值还没被数据迁移纠正之前，相关代码路径会崩溃。
  • 崩溃出现在「request + watchlist」组合上。团队从堆栈看到这一点，并在一个用户账号上清空 watchlist 里的 request 后，该用户立即不再报错，从而确认了范围。

3.2 促成因素（Contributing）

  1. 新代码先于回填上线（官方）：新代码在数据迁移完成前就上线，中间状态（计数为 0）是非法的，但运行时没有把它当成可恢复状态。
  2. 数据迁移要扫表（官方）：数据迁移要扫过受影响的表。官方事后提醒要考虑表的大小，并建议把这类发布放到维护窗口。表有多大、迁移预计要多久：报告未说明。
  3. 事中停掉了数据迁移（官方）：10:32 UTC 已启动数据迁移，10:46 UTC 又因怀疑它造成退化而停掉，根因到 11:20 UTC 才定位。停错方向让窗口拉长了大约半小时。这是事中判断，不是「迁移本身有额外缺陷」的证据。

3.3 为何没挡住

代码假定「每个 request 至少有一个 action」，与 schema 默认 0 直接冲突。只要数据迁移还没跑完，这个假定就会在生产里被打脸。原文没有写预发或分批发布是否覆盖了「watchlist 中含 request、且计数仍为 0」的路径。

3.4 证据与未知

  • 已知（官方）：部署与迁移时间线、默认 0 与代码假定冲突、用清空 watchlist 验证、纠正迁移后崩溃停止，均来自 11-13 官方复盘。
  • 未知（报告未说明）：具体异常类型与代码位置、受影响用户和行数、表大小、为何决定先停数据迁移、除教训以外的后续代码或发布流程改动。

根因类别：软件缺陷（主）。导火索类型：代码发布/升级。归类由本站根据分析归纳，非原报告表述。

4. 检测

  • 部署后不久，团队自己先在页面上遇到 500；错误跟踪系统也开始收到其他用户的同类错误。首次异常在 10:31 UTC（18:31），距 schema 迁移 4 分钟，距部署开始 6 分钟。
  • 堆栈指向 request 与 watchlist 的组合；清空一名用户 watchlist 里的 request 后错误立即消失，作为确认手段。

5. 止血与修复

  • 临时止血 / 永久修复（官方）：在这次是同一件事：运行（调整后的）数据迁移，按实际数据重算每条 BsRequest 的 BsRequestAction 数量。
  • 过程不是一次做对：10:32 已启动数据迁移，10:46 因怀疑它造成退化而停止；11:20 定位为数据状态与新代码不匹配，11:26 开始手动执行调整后的迁移，11:36 崩溃在参考服务器上停止，11:45 迁移全部完成，事故关闭。
  • 调整了什么、与自动迁移的差异：报告未说明。
  • 官方教训是：发布「立刻依赖数据迁移完成」的代码时要特别小心，应考虑维护窗口，并了解受影响表的大小。原文没有列出除此之外的已落地代码改动或日期。

6. 影响为何扩大

  • 计数为 0 时，受影响用户打开任何页面都会 500，而不是只在某一张与 request 直接相关的页面失败。
  • 先把正在跑的数据迁移停掉，使本可用来回填计数的动作中断约 40 分钟，窗口被拉长。这是对时间线的归纳，原文把它写进时间线，没有单独写成扩大因素。

7. 既有防护与 SOP

8. 后续改进措施

原文只写了一条教训，没有 Prevent / Detect 清单，也没有给出完成日期或代码改动。

Process

  • 官方：对「立刻依赖数据迁移完成」的发布要特别小心，应考虑维护窗口，并了解受影响表的大小。

Prevent

  • 原文未写是否会改默认值、先回填再切代码、或在代码里容忍计数为 0。
  • 我们的建议（非官方承诺）：这类 counter cache 应先回填再让新代码依赖它，或让代码把 0 当成「尚未回填」而不是假定至少有一个 action。这不是官方承诺。

9. Lessons

官方以一条 Lessons Learned 写出部署与数据迁移的顺序问题。以下分栏为归档侧解读。

  • 做得好：几分钟内从自己遇到的 500 和错误跟踪里发现问题；用堆栈和「清空 watchlist 即恢复」迅速缩到具体组合；最终用纠正迁移而不是长期关功能来恢复。
  • 做得差：新代码在数据回填完成前上线；schema 默认 0 与「至少有一个 action」的假定冲突；事中先停掉数据迁移，延长了恢复。
  • 运气：只有 watchlist 里带有 request 的用户走这条崩溃路径，不是参考服务器上的全部用户。错误跟踪在部署后很快就有信号。
