Buildkite · 2026-11-11 · Increased error rates on Agent API｜事故复盘

元信息

  • 公司：Buildkite
  • 标题：Increased error rates on Agent API
  • 事故日期：2026-11-11 18:40–20:02 UTC（2026-11-12 02:40–04:02 Asia/Shanghai），约 1 小时 22 分。书面事后说明于 2026-11-24 07:35 UTC（15:35 Asia/Shanghai）发布。
  • 原文：https://www.buildkitestatus.com/incidents/vm95hj4pycv7 （Buildkite Status 事故页上的 Postmortem 及事中更新。不是独立博客长文。）
  • 类别：事故复盘
  • 严重度/时长：共享同一数据库集群的一部分客户受到影响。官方窗口约 1 小时 22 分。受影响集群上完成的 Buildkite jobs 比前一周低 50–75%；构建更慢，需要人工重试。入站 webhook 没有丢失。
  • 原文完整度：高。写清了 Skip Intermediate Builds 的触发、PostgreSQL 统计低估与部分索引、跳过构建 worker 的并发放大、时间点和两项改进。未给出受影响客户数量、集群规模、以及 hint 具体加在哪一条 SQL 上。
  • 时区说明：原文时间为 UTC，按 UTC+8 换算为 Asia/Shanghai。事故发生在 11-11 傍晚 UTC，对应 11-12 凌晨。
  • 根因类别（主）：软件缺陷。依据：按主键加当前状态更新时，规划器在统计低估下选了部分索引；跳过构建的 worker 还会并发叠加，查询近似平方增长。
  • 根因类别（附加）：容量/资源耗尽、数据库/存储。依据：这些查询在 15–20 分钟内几乎占满可用数据库资源；机制落在 PostgreSQL 统计与查询规划。
  • 导火索类型（主）：配置推送。依据：一名客户为积压了数千条 scheduled 构建的 pipeline 打开了 Skip Intermediate Builds。
  • 导火索类型（附加）：潜伏缺陷被条件触发。依据：统计低估和并发 worker 事先存在，在这次积压上才把共享库打满。
  • 归类说明：以上类别由本站根据分析归纳，非原报告表述。

背景知识

  • Skip Intermediate Builds：Buildkite 的一项 pipeline 功能。打开后，每当有新构建被创建，就会入队后台任务，把该 pipeline 里已有的 scheduled 构建逐条改成 skipped。这次是一名客户在已有数千条 scheduled 构建的 pipeline 上打开了它。
  • 部分索引（partial index）与统计低估：PostgreSQL 会按表里各状态的采样频率估计行数。scheduled 行平时很少，采样很可能估成只有 1 行。此时规划器在主键全量索引和按状态的部分索引之间，会因为两边都估成 1 行而选部分索引。实际有数千行匹配时，这条路径比走主键慢得多。
  • 共享数据库集群租户：Agent API 的请求落在共享集群上。这次查询把该集群的数据库资源几乎占满，同一集群上的其他客户也会看到 Agent 请求变慢或失败。

1. 影响

  • 官方事实：2026-11-11 18:40–20:02 UTC（11-12 02:40–04:02 Asia/Shanghai），共享同一数据库集群的一部分客户，Agent 请求变慢或失败，agent 无法推进 jobs。
  • 入站 webhook 没有丢失。受影响集群上完成的 jobs 比前一周低 50–75%；构建更慢，需要人工重试。
  • 受影响客户数、pipeline 数、集群规模：报告未说明。

2. 导火索

  • 官方事实：11-11 18:25 UTC（11-12 02:25 Asia/Shanghai），一名客户为积压了数千条 scheduled 构建的 pipeline 打开了 Skip Intermediate Builds。之后每有新构建，就会入队后台任务，把已有 scheduled 构建逐条改为 skipped。
  • 官方窗口从 18:40 UTC 起算，距该操作约 15 分钟，与文中「15–20 分钟内占满数据库资源」相符。
  • 导火索类型：配置推送（主），附加潜伏缺陷被条件触发（归类由本站根据分析归纳，非原报告表述）。
    • 依据：触发是客户打开该项功能；查询规划和并发 worker 是事先存在的条件。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 跳过构建的 SQL 按「主键 ID + 当前状态」更新行。PostgreSQL 统计把 scheduled 行数估成 1，规划器因此选了按状态的部分索引，而不是主键索引。该 pipeline 实际有数千条 scheduled 构建，查询从通常约 20ms 变成超过 1 秒。按这个速度，跳完所有构建大约要 2.5 小时。
  • 跳过构建的 worker 还会并发拉起新的尝试，去跳过同一批尚未跳过的构建，查询数量近似平方增长。15–20 分钟内，这些查询几乎占满可用数据库资源，同一集群上的其他数据库请求被拖慢或排队。

3.2 促成因素（Contributing）

  1. 统计低估（官方）：scheduled 行平时很少，统计采样很容易低估，这是代码里常见的「主键 + 状态」更新模式在这种数据分布下的后果。
  2. worker 不互斥（官方）：新的跳过任务不会先停掉旧 worker，多路并发扫同一批行。
  3. 共享集群（官方）：该数据库集群被多个客户共享，一条 pipeline 上的后台查询可以拖慢同集群其他租户的 Agent API。
  4. 过重查询的隔离（由整改项回推）：官方没有写是否已有按查询耗时或后台任务资源占用的自动隔离。事后改进才提到要做隔离工具。

3.3 为何没挡住

打开该功能本身是预期操作。拦住这次的应是：规划器在统计不准时仍走主键，或后台 worker 不要并发放大，或过重的后台查询能被隔离开。这三项在事发时都没有把共享库保住。隔离能力是由整改项回推的，原文没有写事发时是否已有雏形。由整改项回推

3.4 证据与未知

  • 已知（官方）：触发时刻、机制、18:44 的 p90、18:50 告警、19:27 定位、19:50 开始发布 hint、20:02 恢复，以及两项改进，均来自 11-24 的 Postmortem。事中更新只用于对外通报时间。
  • 未知（报告未说明）：受影响客户和集群规模、hint 加在哪一条语句上、该功能打开前 scheduled 构建为何积压到数千条。

根因类别：软件缺陷（主），附加容量/资源耗尽、数据库/存储。归类由本站根据分析归纳，非原报告表述。

4. 检测

  • 18:44 UTC（11-12 02:44），p90 延迟超过 45 秒。18:50 UTC（02:50）告警触发并呼叫 on-call。距官方窗口起点 18:40 约 10 分钟，距打开该功能约 25 分钟。
  • 状态页 Investigating 出现在 19:12 UTC（03:12），晚于内部告警，不能当成 MTTD。

5. 止血与修复

  • 临时止血（官方）：19:27 UTC（03:27）定位到低效查询计划，开始准备给规划器加 hint，让它优先走主键索引。19:50（03:50）开始发布，20:02（04:02）服务恢复。状态页 20:07 进入 monitoring，20:15 关闭。
  • 已落地（官方）：跳过构建的 worker 已改为：有新 worker 入队时，抢占（pre-empt）旧 worker，避免多个 worker 同时跳过同一批构建。
  • 进行中（官方计划，不是本站建议）：改进工具，以便更快响应后续事故，例如手动或自动隔离占用过多数据库资源的后台任务。完成日期：报告未说明。

6. 影响为何扩大

  • 查询变慢之后，worker 并发使查询量近似平方增长，15–20 分钟内占满共享库。
  • 同一集群上的其他客户因此一起看到 Agent 请求超时，jobs 无法推进。
  • 构建需要人工重试，完成量比前一周低 50–75%。Webhook 没有丢，影响主要在执行进度，而不是接收入口。

9. Lessons

官方未使用 well / poorly / lucky 分栏。以下为归档侧解读。

  • 做得好：书面说明把触发、统计低估、错误索引和并发放大写成一条完整因果链，并给出 p90、告警和发布 hint 的时刻。止血针对规划器，而不是只重启或扩容。
  • 做得差：常见的「主键 + 状态」更新模式，在 scheduled 行数被低估时会选错索引；worker 又允许并发放大。隔离过重后台任务的能力是事后才计划补上的。
  • 运气：入站 webhook 没有丢失。影响限制在共享该集群的一部分客户，而不是全部 Agent API。
