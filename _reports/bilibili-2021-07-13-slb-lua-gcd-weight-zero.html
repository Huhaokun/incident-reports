2021.07.13 我们是这样崩的

元信息

  • 公司: B站（哔哩哔哩）
  • 标题: 2021.07.13 我们是这样崩的
  • 日期: 2021-07-13（文章 2022-07-12）
  • URL: https://www.bilibili.com/opus/681869046739632212
  • 原文路径: raw/bilibili-2021-07-13-slb-lua-gcd-weight-zero.md
  • 严重度 / 时长: 全站级不可用；约 22:52 至次日约 01:50 主路径恢复，根因治理延续次日白天
  • 原文完整度: 高（时间线、机制、放大器、改进极完整）

1. 影响（Impact）

接入层不可用，APP/网页无法打开；登上热搜。多活业务约 23:23 起核心功能部分恢复；非多活更晚。精确用户%：报告未量化。

2. 导火索（Trigger）

某服务特殊发布模式使容器实例权重短暂为字符串 "0"，进入 SLB lua-resty-balancer 选路。

3. 根因（详尽）

3.1 直接原因

_gcd 未校验类型；对 "0" 算术产生 nan，陷入死循环 → OpenResty worker CPU 100%，无法处理请求。

3.2 促成因素

  • 动态调权需求上线后，生产低频发布模式未在灰度触发。
  • 内网鉴权 Cookie 域名经用户侧 SLB → 故障时远程同学无法登录排查。
  • 多活 SLB 因 CDN/用户重试过载（流量×4+、连接×100）；容量 buffer 不足。
  • 团队规模小，回滚与新建源站难并行；跨团队新建源站缺全链路演练。

3.3 为何防护没挡住

输入未做类型/权重合法性校验；发布模式可产生 weight=0；办公网与用户链路未隔离。

3.4 证据与未知

官方火焰图/_gcd/nan 机制清楚；JIT 关闭事后证明非根治，诱因消失才是当晚恢复关键。

4. 检测（Detection）

22:52 SRE 大量接入层报警；客服与内部反馈。

5. 止血（Mitigation）与修复（Fix）

  • 临时：Reload/冷重启无效 → 依赖多活部分恢复 → 新建 SLB 集群切 CDN → 诱因发布结束后重启恢复。
  • 永久：禁止该发布模式；SLB 忽略注册中心权重；多活平台化；SLB 拆分与演练等。

6. 影响为何被扩大（Amplifiers）

办公网依赖用户链路；多活过载；单机房统一 SLB 故障域过大；新建源站慢。

7. 既有防护与 SOP

  • 存在的控制: 多活（部分生效）；报警；部分预案（机器初始化演练过）。
  • 缺口: 多活元信息无平台、切量依赖人工 CDN；无故障指挥官；SLB 异常输入测试不足。SOP 部分存在但跨团队联动失效。

8. 后续改进措施（Action Items）

Prevent

  • 禁止危险发布模式；SLB 强制权重；Lua 类型校验与开源库 review；引入组件测试。
  • SLB 按业务拆分集群缩小故障域。

Mitigate

  • 多活基架与一键切量平台；扩容降低 CPU 水位；优化 CDN 回源超时。

Detect / Process

  • 平台/组件事件分析；故障指挥官与通告平台；机房级故障演练。

9. Lessons

  • 做得好: 多活证明可快速止损；事后机制级复盘公开。
  • 做得差: 动态权重输入校验；办公网耦合；演练与并行能力不足。
  • 运气: 诱因发布结束使重启后恢复（否则关 JIT 仍不够）。

10. 时间线（摘要）

22:52 报警 → 22:57 确认 SLB CPU100% → 23:23 多活核心恢复 → 01:50 新集群切量基本恢复 → 次日定位 weight=0/_gcd 并全量修复。
