GitHub · 2026-11-08 · Increase in timeouts for some unauthenticated users｜事故复盘

元信息

  • 公司：GitHub
  • 标题：Increase in timeouts for some unauthenticated users
  • 事故日期：官方窗口 2026-11-08 08:43–12:29 UTC（16:43–20:29 Asia/Shanghai），约 3 小时 46 分。书面 RCA 随状态页 resolved 更新于当日 12:32 UTC；条目在 11-16 仍有更新。
  • 原文：https://www.githubstatus.com/incidents/pyynvrm1vskw （GitHub Status 事故页上的书面 RCA 及事中更新。不是独立博客长文。）
  • 类别：事故复盘。主要影响未认证的 github.com 网页和 REST API 请求，以及 Release 资源下载。官方写明认证请求大体未受影响。
  • 严重度/时长：状态页 impact=minor。窗口内 11.3% 的未认证请求失败，46.1% 的 Release 资源下载请求失败。
  • 原文完整度：中高。写清了未认证后端先出错、随后的流量高峰打满缓存层 CPU、部分服务器在高峰结束后仍不健康从而拖长中断，以及重启缓存软件和受影响服务器后恢复。未说明流量高峰的来源、缓存软件名称、有多少台机器未自愈、内部检出时刻，以及为何这些服务器不能自动恢复。
  • 时区说明：原文时间为 UTC，按 UTC+8 换算为 Asia/Shanghai。
  • 根因类别（主）：容量/资源耗尽。依据：流量高峰导致缓存层服务器 CPU 升高，未认证请求和 Release 下载大量失败。
  • 根因类别（附加）：软件缺陷。依据：高峰结束后部分服务器仍不健康，不能自动恢复，需要重启缓存软件和机器。
  • 导火索类型（主）：流量突增/攻击。依据：官方写明随后出现流量高峰打高了缓存层 CPU；未将其定性为安全攻击。
  • 导火索类型（附加）：潜伏缺陷被条件触发。依据：缓存层在过载后无法自愈是事先存在的缺口，在高峰过后才把中断拉长。
  • 归类说明：以上类别由本站根据分析归纳，非原报告表述。

背景知识

  • 未认证请求：未登录或未带有效凭证的网页和 REST API 访问，包括很多人下载 Release 附件的路径。这次失败主要集中在这条路径，认证请求大体正常。
  • 缓存层：位于客户端与后端服务之间、用于承受重复读请求的一层服务器。这次流量高峰先打高了这些机器的 CPU；高峰结束后它们没有自己恢复。
  • 不自愈的过载：负载降下来之后，进程或机器仍可能停在坏状态（例如打满的连接、卡住的工作线程）。这次必须重启缓存软件和服务器，说明故障没有随流量一起消失。

1. 影响

  • 官方事实：未认证请求访问 github.com 和 GitHub REST API 的错误率升高：11.3% 失败。Release 资源下载更重：46.1% 失败。认证请求大体未受影响。
  • 受影响的仓库、用户或下载次数：报告未说明。

2. 导火索

  • 官方事实：最初的错误出现在处理未认证 Web 流量的后端服务。随后出现一次流量高峰，把缓存层服务器的 CPU 打高。
  • 官方没有把高峰的来源写成发布或内部变更，也没有给出是爬虫、下载风暴还是其他自动化流量。
  • 导火索类型：流量突增/攻击（主），附加潜伏缺陷被条件触发（归类由本站根据分析归纳，非原报告表述）。
    • 依据：官方写明随后出现流量高峰打高了缓存层 CPU，未将其定性为安全攻击。缓存层在过载后无法自愈是事先存在的缺口，在高峰过后才把中断拉长。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 处理未认证 Web 流量的后端服务先出现错误。
  • 随后的流量高峰导致缓存层服务器 CPU 升高。
  • 高峰结束后，部分服务器仍不健康，中断被拉长。恢复手段是重启缓存软件并重启受影响的服务器。

3.2 促成因素（Contributing）

  1. 未认证路径与认证路径分开（官方）：网页、REST API，尤其是 Release 下载，走未认证路径，所以认证用户大体无感。未认证路径上的缓存层成为瓶颈，Release 下载失败率远高于整体未认证请求。
  2. 过载后不能自愈（官方，原因未写）：缓存层在过载后不能自动回到健康状态。官方把「调查为何受影响服务器没有自动恢复」和「检视缓存行为，以便在故障期间更好地保护后端」列为事后工作。

3.3 根因机制

未认证流量路径上，先是后端出错，再是缓存层被流量高峰打高 CPU。按常理，高峰过去之后错误率应回落；这次部分缓存服务器留在不健康状态，需要重启软件和机器才恢复。于是一次流量冲击变成了近四小时的持续失败，Release 下载首当其冲。关键点不只是「来了很多未认证流量」，而是过载后的缓存层不会自己好。

3.4 为何没挡住

缓存层没能在流量高峰下把后端保护住，过载后也不能自己恢复，最后靠重启缓存软件和机器止血。监测也没有早到能在客户看到大量失败之前拦住——官方将改进监测，以便更早发现这类失败。由整改项回推

3.5 证据与未知

  • 已知（官方）：11.3% 的未认证请求失败，46.1% 的 Release 下载失败。认证请求大体未受影响。高峰结束后部分服务器仍不健康。重启缓存软件和受影响服务器后恢复。
  • 未知（报告未说明）：流量高峰的来源、缓存软件名称、有多少台机器未自愈、内部检出时刻、为何这些服务器不能自动恢复。11:50 UTC 的重新部署与最终 RCA 中的重启是否为同一动作，报告没有对照说明。

根因类别：容量/资源耗尽（主），附加软件缺陷。归类由本站根据分析归纳，非原报告表述。

4. 检测

  • 书面 RCA 未写内部首次检出渠道和时刻。MTTD：报告未说明。
  • 状态页第一条在 10:36 UTC（18:36 Asia/Shanghai），距官方窗口起点约 1 小时 53 分，文案是正在调查部分服务。不能据此写成已证实的 MTTD。11:16 UTC 才写明主要影响未认证用户。

5. 止血与修复

  • 临时止血（官方）：重启缓存软件，并重启受影响的服务器。12:29 UTC 窗口结束并进入 monitoring，12:32 UTC 关闭并发布书面说明。重启是在全部不健康机器上一次性完成，还是分批：报告未说明。
  • 11:50 UTC 事中更新写过「已识别出有问题的组件，正在重新部署」，与最终 RCA 中的重启是否为同一动作，报告没有对照说明。
  • 进行中（官方计划，不是本站建议）：改进监测，更早发现这类失败；调查受影响服务器为何没有自动恢复；检视缓存行为，以便在故障期间更好地保护后端服务。完成时间：报告未说明。

6. 影响为何扩大

  • 高峰结束后服务器仍不健康，把一次流量冲击拉成近四小时。
  • Release 资源下载失败率 46.1%，明显高于整体未认证请求的 11.3%，说明这条路径更依赖或更暴露于该缓存/后端。
  • 对外点名未认证用户偏晚，但不清楚这是否拖慢了缓解。

  • 我们的建议（非官方承诺）：应把「高峰结束后仍不健康」当成独立缺陷跟踪（例如连接耗尽、事件循环卡住、健康检查过宽），并给 Release 下载这条更脆弱的路径单独的过载保护。这不是官方承诺。

  • 做得差：缓存层过载后不能自愈，中断被明显拉长；监测和对外说明都偏慢；流量来源和未自愈原因仍未公开。
