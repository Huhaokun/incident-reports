背景知识

  • 搜索代理（search proxy）：位于客户端与搜索集群之间，负责把请求路由到搜索集群。这次过载发生在代理上，是建立加密连接时的 CPU 打满；搜索集群本身保持健康。
  • 超时重试放大：请求在代理过载后超时，客户端或上层再次发起，反而给已经耗尽 CPU 的代理加码，使过载不能靠自身消退。GitHub 事后计划让搜索重试可以在事故中不发版就能调整。

1. 影响

  • 官方事实：10-22 14:55–17:28 UTC（22:55–10-23 01:28 Asia/Shanghai），GitHub.com 搜索退化。依赖搜索的 Issues、Pull Requests、Projects、Actions、Packages 以及部分 REST API 返回错误或不完整结果。搜索请求平均失败 21%，峰值 52%。
  • 正在运行的 Actions workflow、包的上传下载、Git 操作未受影响。
  • 搜索在 17:28 UTC 恢复后，GitHub Projects 的更新（新加项、issue 与 PR 的变更）仍有积压，事中更新一直报到 10-23 00:55 UTC 前后。书面 RCA 没有单独解释这段积压的机制，只把官方窗口写到搜索恢复。
  • 受影响用户数：报告未说明。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 把请求路由到搜索集群的代理，在建立加密连接时耗尽了 CPU。搜索集群本身保持健康。
  • 超时的请求被重试，额外负载让代理保持过载。

3.2 促成因素（Contributing）

  1. 加密连接的 CPU 成本（官方）：建立加密连接的 CPU 成本足够高，能在代理层单独形成瓶颈，而不需要搜索集群先出问题。
  2. 重试不能在事故中随时调整（由整改项回推）：重试在事故中不能随时关掉或调低，所以放大一直持续到扩容生效。这是由「计划让搜索重试可在事故中不发版就调整」回推的，原文没有写事发时重试配置的具体值。
  3. Projects 积压（官方，机制未知）：Projects 等搜索支撑功能在前端恢复后，还要消化积压的更新，对外影响比搜索窗口更长。积压的内部结构：报告未说明。

3.3 为何没挡住

搜索集群健康并不能保住服务：瓶颈在前面的代理。事发时也没有足够早的搜索失败告警——这项是事后计划补上的，由整改项回推。扩容是事后加上去的容量，不是事先把代理的加密连接 CPU 成本降下来。由整改项回推

  • 已知（官方）：失败比例、代理 CPU、重试放大、搜索集群健康、17:28 扩容后搜索恢复，以及三项改进，以 11-16 更新后的 Resolved 说明为准。事中更新用于时间线和 Projects 长尾。
  • 未知（报告未说明）：过载的直接触发条件、代理规模与加密实现、内部检出时刻、Projects 积压的单独机制。

6. 影响为何扩大

  • 超时重试给已经打满 CPU 的代理加码，过载不能自行消退。
  • 搜索是 Issues、PR、Projects、Actions、Packages 和部分 REST API 的共用依赖，代理一层过载会同时打到这些面。正在运行的 workflow、包传输和 Git 操作不走这条路径，所以还能用。
  • Projects 在搜索恢复后仍要消化积压，对外持续时间长于 2 小时 33 分的官方搜索窗口。

9. Lessons

官方未使用 well / poorly / lucky 分栏。以下为归档侧解读。

  • 做得好：书面 RCA 把故障点写在代理而不是搜索集群，并指出重试放大。止血是加代理容量，搜索窗口有明确的恢复时刻。
  • 做得差：加密连接的 CPU 成本足以单独打满代理；重试在过载时变成加速器；搜索失败告警和可调重试都是事后才补。
  • 运气：正在运行的 Actions workflow、包传输和 Git 操作未受影响。搜索集群本身保持健康，恢复不需要重建索引或集群。

学习价值：搜索集群健康不等于搜索可用。前面的代理如果在建立加密连接时就把 CPU 打满，超时重试会把过载锁死，Issues、PR、Projects 等共用搜索的功能会一起失败。正在运行的 workflow 和 Git 操作可以不受影响。扩容能止血；要缩短下次的发现和恢复时间，需要更早的搜索失败告警，以及事故中不发版就能把重试降下来。
