背景知识

  • 数据库连接层：位于应用与数据库之间、负责分配和等待连接的那一层。这里的要点是：即便热点争用已经结束，堆积的等待请求仍可能把这一层压死，需要故障转移才能恢复。
  • 热点记录争用：大量事务同时更新同一行，持有锁或占住连接，拖垮整池连接。

1. 影响

写路径首先受伤。峰值时约 20% 的 PR 写操作（合并、评论、评审）失败，约 10% 的 Issue 创建和编辑失败，10%–15% 的 Project 条目编辑失败。SSH 上的 git push、REST/GraphQL、code scanning 上传、Release 和 Package 操作也受影响；约 1% 的 Actions 运行延迟超过 5 分钟或无法启动。GitHub.com 全部请求在最坏时近 4% 失败。读操作大体不受影响，失败后稍后重试通常能成功。

2. 导火索

官方只写事故由「对同一条数据库记录的一阵并发更新」触发。未说明这阵更新来自发布、作业、用户行为还是别的流量。

3. 根因

直接原因

对同一条数据库记录的并发更新占满了某台主库的全部可用连接。

促成因素

争用本身随后清掉了，但已经排队的请求继续压着数据库连接层，连接层不能自行恢复，必须把主库故障转移到新主机。

防护为何没挡住

当时没有及时发现这类连接层过载的告警，也没有在连接层自己恢复不了时尽快故障转移的现成程序（事后才写要改进这两项）。

4. 怎么发现

书面 RCA 未写内部检出渠道。状态页 09:49:55 UTC（17:49 Asia/Shanghai）以 Investigating 创建，已在官方窗口开始后约 15 分钟。

5. 止血与修复

临时：故障转移到新的主库主机。多数服务 11:31 UTC 恢复，Actions 11:43 UTC 恢复。

永久（官方已做）：关掉触发争用的代码路径；连接层处理能力提高 50%；增加这类过载的告警。还在改进类似情况下更早故障转移的程序。

6. 影响为何扩大

争用解除后系统仍不恢复，说明排队本身会把连接层锁死。写路径共享这套主库连接，所以 PR、Issue、Git、API、Actions 一起受影响；读路径基本幸免。

7. 既有防护与 SOP

防护或 SOP是否存在本次表现
主库故障转移存在（事中用了）生效，但是事后才切，连接层已无法自愈
连接层过载告警事后新增，事发时未写已有未能早发现

8. 后续改进措施

  • Prevent：关掉触发争用的代码路径（已做）。
  • Detect：增加这类过载告警（已做）。
  • Mitigate：连接层容量提高 50%（已做）；改进程序以便更早故障转移（进行中）。

以上均为官方措施。

9. 教训

  • 做得好：读路径基本独立；给出了写路径的量化失败率；事后同时补了代码路径、容量和告警。
  • 做得差：连接层在争用消失后仍不能自愈，说明过载恢复没有自成回路。
