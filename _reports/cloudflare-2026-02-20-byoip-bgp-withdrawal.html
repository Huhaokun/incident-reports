背景知识

术语说明
BYOIP（Bring Your Own IP）客户把自己持有的 IP 前缀带到 Cloudflare，由 Cloudflare 向互联网宣告并提供 CDN、Spectrum、Magic Transit 等产品。本次受影响的是使用该服务的一部分客户，而不是 Cloudflare 自有地址的全部宣告。
BGP 宣告 / 撤回（advertisement / withdrawal）通过边界网关协议向对等体宣布或撤销到达某前缀的路由。前缀被撤回后，互联网上不再有通往该地址的有效路径，连接会在路径狩猎后超时失败。
BGP Path Hunting（路径狩猎）前缀刚被撤回时，终端连接仍会在各网络间尝试寻找通往目的 IP 的路由，直到连接超时失败。官方称这是受影响客户首先看到的行为，并会持续到该前缀在某处重新宣告为止。
Addressing APICloudflare 网络上地址的权威数据源。客户经公开 API 或 BGP Control 发出宣告/撤回后，API 通知机器更新前缀宣告；足够多的机器收到通知后，路由器上的 BGP 才会更新。官方写明对该数据集的变更会立即传播到全球边缘。
Service binding（服务绑定）把 CDN、Spectrum、Magic Transit 等产品绑定到某条 BYOIP 地址段。清理任务在撤回前缀的同时删除了部分或全部依赖对象（含绑定），使一部分客户无法在控制台重新宣告。
pending_delete 查询参数清理子任务请求“待删除前缀”时使用的 API 标志。客户端传了无值的 ?pending_delete，服务端用“值非空”才走待删除表；空字符串未命中该分支，返回了全部前缀。
Code Orange: Fail SmallCloudflare 旨在提高代码与配置韧性的计划，分三块：配置变更必须受控发布；改进 break-glass、去掉环形依赖；审查并测试流量系统在异常状态下的既定行为。本次变更属于第一块（把有风险的人工操作改成安全、由健康指标介导的自动配置更新），但配套的快照回滚等能力当时尚未进入 Production。

1. 影响

  • 官方事实（时间与范围）：2026-02-20 17:48 UTC 开篇称发生服务中断；时间线将 IMPACT STARTS 标在 17:56 UTC、IMPACT ENDS 标在 23:03 UTC（= 02-21 01:56–07:03 Asia/Shanghai）。向某一 BGP 邻居宣告的前缀共 6,500 条，其中 4,306 条为 BYOIP，且这些 BYOIP 前缀会向每个对等体宣告、代表全球宣告的全部 BYOIP 前缀。17:56–18:46 UTC，6,500 条中有 1,100 条被撤回，相当于约 25% 的 BYOIP 前缀被非预期撤回。变更是迭代而非一次性应用到全部 BYOIP 客户，因此并非所有 BYOIP 客户都受影响；发现问题后变更被回滚，避免了其余客户被波及。
  • 用户可见症状：部分 BYOIP 客户的服务与应用从互联网不可达，连接超时或失败。受影响客户首先经历 BGP Path Hunting：连接在各网络间寻找路由，直到超时。凡使用 BYOIP 向互联网宣告的产品都会进入这种“循环直至失败”的模式。
  • one.one.one.one：Cloudflare 递归 DNS 解析器网站出现 HTTP 403 与 “Edge IP Restricted” 错误。1.1.1.1 Public Resolver 上的 DNS 解析（含 DNS over HTTPS）未受影响。
  • 恢复过程中的残留影响：一部分客户无法在控制台切换前缀来自助恢复。工程师开始重新宣告这些前缀时，客户仍可能看到延迟升高和失败——因为部分用户的 addressing 设置因软件问题从边缘服务器上被删除，状态必须重新传播回边缘。
  • 官方称总时长 6 hours and 7 minutes，且大部分时间用于恢复前缀配置。按时间线 17:56–23:03 UTC 计算为 5 小时 7 分钟；从开篇 17:48 UTC 起算为 5 小时 15 分钟。差值原因报告未说明，本分析同时保留官方时长表述与时间线时刻。
  • 受影响客户数、请求量、收入或 SLA 影响、是否有数据丢失或错误计费：报告未说明。
  • 数据面内容被改写：不适用——原文描述的是路由撤回导致的不可达、超时，以及网站 403，未提到载荷被篡改。
  • 官方明确：本次不是网络攻击或任何恶意活动直接或间接造成的。

分产品影响（官方表格）：

产品影响

2. 导火索

  • 官方事实：问题由 Cloudflare 对“经 BYOIP 管道接入的地址如何被网络管理”所做的一次变更引起，非预期地撤回了客户前缀。该变更试图把目前仍需人工完成的“把前缀从 BYOIP 服务中移除”自动化，作为 Code Orange: Fail Small 的一部分，用安全的自动工作流替换紧邻 Production 的人工操作。实现方式是一个定期运行的清理子任务：检查应被移除的 BYOIP 前缀并删除它们。
  • 时间线：2026-02-05 21:53 UTC（= 02-06 05:53 Asia/Shanghai）含缺陷的子进程合入代码库；2026-02-20 17:46 UTC（= 02-21 01:46 Asia/Shanghai）带该子进程的 Addressing API 发布完成；17:56 UTC 该子进程开始执行，前缀宣告更新开始传播，影响开始。
  • 导火索类型：代码发布/升级（归类由本站根据分析归纳，非原报告表述）。依据：时间线将触发节点写成 “Address API release with broken sub-process completes”，官方亦把原因写成 “a change that Cloudflare made”。
  • 次要标签：自动化/定时任务（同样为本站归纳）。依据：缺陷是在 regularly running sub-task / cleanup sub-task 里被执行的；影响开始的时刻是子进程开始运行、系统性地删除返回的前缀，而不是发布完成那一刻本身。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 清理子任务向 Addressing API 发出了有缺陷的查询：GET /v1/prefixes?pending_delete（参数存在但没有值）。
  • 服务端判断是 if v := req.URL.Query().Get("pending_delete"); v != ""，只有值非空才从 ip_prefixes_deleted 表取“待删除”前缀（FetchPrefixesPendingDeletion）。无值时 Get 的结果是空字符串 ""，条件不成立，请求落到默认逻辑，返回全部 BYOIP 前缀，而不是待删除子集。
  • 系统把返回的全部前缀当成已进入删除队列，新的清理子任务开始系统性地删除这些前缀及其依赖对象（含 service bindings），直到有人发现影响、定位到该子任务并关掉它。在被叫停前，约 1,100 条 BYOIP 前缀已从 Cloudflare 网络撤回。

3.2 促成因素（Contributing）

  1. API 契约把标志当成字符串（官方）：pending_delete 被当作字符串解释，客户端与服务端都难以对这个标志的值形成一致理解。客户端以“带参数、无值”表示过滤待删除项，服务端以“值非空”才过滤，空字符串被当成“不要这条过滤”。事后整改的第一项就是 API schema 标准化，以便测试和系统校验调用是否形态正确。
  2. 清理任务把列表结果直接当成待删集合（归档侧整理，依据原文）：官方写 “The system interpreted this as all returned prefixes being queued for deletion”，随后开始系统性删除。原文没有描述该任务是否另有二次确认、数量上限或“待删集合过大则中止”的保护。
  3. Addressing API 变更立即传到全球边缘（官方）：权威数据库的变更会立刻反映到全球网络。错误删除一旦写入，就会变成边缘上的宣告撤回，以及（对部分前缀）绑定被去掉。
  4. 预发与测试没有覆盖到这次路径（官方）：预发数据尽可能接近生产，但本次不够用，用来模拟后果的 mock 数据不足。已有功能测试，但覆盖不完整：初期测试与代码审查聚焦 BYOIP 自助 API 旅程并认为通过；工程师测的是客户会走的流程，没有覆盖 task-runner 在没有显式输入的情况下独立改写用户数据。
  5. 配置态与运行态共用同一权威库，且快照式健康介导回滚尚未上生产（官方）：客户对 addressing schema 的修改与运维动作落在同一数据库，人工回滚要靠数据库快照，而不是对比“期望态 / 实际态”。Code Orange 正在做的“对读出并应用到 Production 的数据做快照、按健康指标介导发布、异常可迅速滚回”当时不在 Production。这使恢复不能“近乎瞬时切回已知好状态”，而必须按受损状态分路修复。
  6. 大范围、过快的撤回没有熔断（由整改项回推）：事后计划监测撤回/删除 BGP 前缀过快或过宽并禁用快照发布，作为 circuit breaker。说明此次清理任务能在约 50 分钟内撤回约 1,100 条前缀，中间没有这类自动刹车（原文未直接说“当时完全没有相关监控”，只把该项列为将做的改进）。
  7. 依赖对象被一并删除，造成更难恢复的状态（官方）：不只是宣告被撤回，部分前缀的 service bindings 也被去掉，控制台无法再切换宣告，必须向每台边缘机器重新下发全局配置。

3.3 因果链 / Five Whys（归档侧整理，依据原文）

  1. 为何部分客户的服务在互联网上不可达？→ 其 BYOIP 前缀的 BGP 路由被从 Cloudflare 网络撤回，连接在 Path Hunting 后超时失败。
  2. 为何前缀会被撤回？→ 定期清理子任务把它们当成“待从 BYOIP 服务移除”的对象，系统性地删除前缀及依赖对象，宣告随之更新。
  3. 为何不该删的前缀会出现在待删集合里？→ 子任务查询 ?pending_delete 未带值，服务端“非空才过滤”的判断未命中，API 返回了全部 BYOIP 前缀；系统把返回结果当成已排队删除。
  4. 为何这种空值/标志契约问题能进到 Production？→ 测试与审查覆盖的是客户自助 API 路径，没有覆盖 task-runner 独立改写用户数据；预发与 mock 数据不足以暴露该场景。
  5. 为何一写进权威库，影响就会马上变成全球不可达？→ Addressing API 是地址的权威数据源，变更会立即传播到边缘；BGP 在足够多机器收到通知后更新。同时，配置与运维共用同一数据库，且健康介导的快照回滚尚未上线，无法迅速把状态切回变更前。
  6. 为何叫停清理任务后仍要数小时才能恢复？→ 前缀处在三种不同受损状态（仅撤回 / 部分绑定被删 / 全部绑定被删），后两种不能只靠控制台重新宣告，必须做数据库恢复并把服务绑定重新推到每一台边缘机器。

3.4 证据与未知

  • 证据：官方给出了开篇时刻、完整 UTC 时间线、向单个对等体宣告的 6,500 / 4,306 / 1,100 / 25% 等数字、约 800 条先恢复与约 300 条需人工恢复、分产品影响、pending_delete 客户端查询与服务端 v != "" 判断的代码、预发与测试缺口、三种受损状态、Code Orange 三项工作流，以及 schema 标准化、配置/运行态分离与快照回滚、大范围撤回熔断三项整改方向。官方否定了网络攻击或恶意活动。
  • 未知（报告未说明）：受影响客户数与比例（只给出前缀比例）；三种受损状态各自的精确前缀数量（仅对无法控制台恢复的给出约 300）；合法的“待删除”前缀本来应有多少；one.one.one.one 网站 403 的具体地址/绑定路径；首次发现是内部监控还是外部报告；发布本身是否做了金丝雀或分阶段（只写配置变更是迭代应用到客户的）；预发数据与 mock 不足的具体差异。

根因类别：软件缺陷（主）。归类由本站根据分析归纳，非原报告表述。依据：官方把直接机制写成清理子任务“queried the API with a bug”，核心是 pending_delete 空值未通过服务端非空判断，导致返回全量前缀并被当成待删除；后文亦称部分前缀的服务配置因 “a software bug” 从边缘被移除。这次“变更”是导火索（发布了带缺陷子进程的 Addressing API），不是把根因写成一次配错了某条前缀。配套的测试缺口、立即传播和缺少快照回滚是促成因素，不另标成根因主类。

4. 检测

  • 官方写：在 one.one.one.one 上检测到影响，并在更多前缀被波及之前回滚了造成影响的变更。时间线：17:56 UTC 影响开始；18:13 UTC（= 02-21 02:13 Asia/Shanghai）因 one.one.one.one 故障而接入（Cloudflare engaged），距影响开始 17 分钟；18:18 UTC 宣布内部事故；18:21 UTC 呼叫 Addressing API 团队并开始排障；18:46 UTC 定位问题，工程师终止该子进程并禁用常规执行，距影响开始 50 分钟，同时 17:56–18:46 UTC 的撤回窗口结束。
  • 发现渠道的具体来源（网站合成监测、客户报障、流量/BGP 告警或其他）以及官方是否使用 MTTD 一词：报告未说明。原文只写因 one.one.one.one 的 failures 而 engaged，以及“detect impact on one.one.one.one”。

5. 止血与修复

  • 临时止血（官方）：
  1. 观察到失败后回滚该变更，前缀停止继续被撤回。时间线上对应 18:46 UTC 终止子进程并禁用其定期执行（在此之前约 1,100 条前缀已被撤回）。
  2. 19:11 UTC 开始恢复：一部分人处理仅被撤回的前缀，另一部分人处理已被移除的前缀。
  3. 19:19 UTC 向客户发布指引：可在 Cloudflare 控制台重新宣告前缀以自助恢复；时间线将此时标为 IMPACT DOWNGRADE。部分客户由此恢复。
  4. 19:44 UTC 开始对已被移除的前缀做数据库恢复。
  5. 正文写约 20:20 UTC 回滚了其中许多宣告变更，约 800 条前缀恢复；时间线在 20:30 UTC 写“完成发布，以恢复仍保有 service bindings、仅被撤回的前缀”，并再次标 IMPACT DOWNGRADE。约 20:20 与 20:30 两处时刻并存于原文，本分析不作强制合并。
  6. 仍有约 300 条前缀因边缘上的服务配置被软件缺陷移除，无法通过控制台修复，需由工程师处理。21:08 UTC 开始向全球机器滚动下发配置，以恢复此前未能自助或未能被前几轮修复覆盖的前缀（第三次 IMPACT DOWNGRADE）。23:03 UTC 该全局配置部署完成，剩余前缀恢复，IMPACT ENDS。
  • 分状态恢复路径（官方，说明为何不能一键立刻恢复）：
  • 大多数受影响客户：仅前缀被撤回，可在控制台切换宣告以恢复。
  • 一部分客户：前缀被撤回且部分 bindings 被删除，处于部分可恢复状态，只能切换其中一部分前缀。
  • 一部分客户：前缀被撤回且全部 service bindings 被删除，控制台因没有绑定到 Magic Transit / Spectrum / CDN 而无法切换；需要发起全局配置更新，把这些客户的绑定重新应用到 Cloudflare 边缘的每一台机器。这批花的时间最长。
  • 永久修复：原文将 schema 标准化、配置态与运行态分离及快照回滚、大范围撤回熔断列为将要做的改进（见第 8 节），未写这些项在事故当中已经上线。缺陷代码是否以正式发布回滚之外的方式被永久删除或改写：报告未说明（只写子进程被终止且常规执行被禁用）。
  • Owner、完成日期、变更单：报告未说明。

6. 影响为何扩大

  • 立即全局传播（官方）：Addressing API 是权威数据源，变更会立即反映到全球网络。错误的“待删除”结果一旦被写入，就会变成边缘撤回与绑定删除，而不是先停在控制面。
  • 依赖对象被连带删除（官方）：清理不仅撤回宣告，还删除相关 service bindings，把一部分前缀推进无法自助恢复的状态；即使后来重新宣告，也要等 addressing 设置传播回边缘，期间仍可能有高延迟和失败。
  • 缺少可迅速滚回的运行快照（官方）：健康介导的操作状态快照当时不在 Production，无法把个体或全部客户近乎瞬时切回已知好状态。官方写恢复不能立即完成，正是因为前缀处于不同受损状态，需要更重的数据恢复步骤。
  • 大范围撤回未被自动刹住（由整改项回推）：从 17:56 到 18:46 UTC 约 50 分钟内撤回约 1,100 条前缀；circuit breaker 是事后计划，不是本次已发挥作用的控制。
  • 官方已说明的限幅因素：变更是迭代应用的，且在 one.one.one.one 上发现影响后及时终止了子任务，因此只波及约 25% 的 BYOIP 前缀，而非全部 4,306 条。官方亦强调这次中断本身不是全球性的，但爆炸半径仍大到不可接受。
  • 受影响前缀在客户/产品上的分布是否更集中、Path Hunting 是否拉长了故障体感：除机制说明外，报告未给出额外量化。

8. 后续改进措施

原文在 “Remediation and follow-up steps” 下列出三项，并分别对应 Code Orange 工作流。以下类型标签由本站归类，非原报告标签。这些项在文中均为将要做的工作（“We will …”），不是事故响应中已经完成的永久修复。

Prevent

  • API schema 标准化（计划中）：pending_delete 被当成字符串，客户端与服务端难以对标志取值形成一致理解。将改进 schema、提高标准化程度，使测试和系统更容易校验 API 调用是否形态正确。对应 Code Orange 第三项（异常条件下的既定行为）。
  • 更好分离运行态与配置态（计划中）：重新设计回滚机制与数据库配置，在客户配置与 Production 之间增加层次，避免运维动作与权威配置写在同一库里、回滚只能靠数据库快照。对应第一、二项（受控发布与快速回滚）。

Detect

  • 约束大范围撤回（计划中）：改进监测，以便在变更过快或过宽时（例如快速撤回或删除 BGP 前缀）发现，并禁用快照发布。这将成为一种 circuit breaker，阻止失控进程以本次这种规模操作数据库。
  • 用客户服务健康信号参与熔断（进行中的工作）：另有工作直接监测客户所运行服务是否行为正常，这些信号也可用来触发熔断，在有时间调查之前先挡住可能危险的变更。与上一项一并对应 Code Orange 第一项。具体指标名与阈值：报告未说明。

Mitigate / Blast-radius

  • 对即将应用到 Production 的数据做快照，并以与其他 Production 变更相同的方式、由健康指标介导地发布（计划中）：指标异常可自动停止发布；下次数据库被改成坏状态时，可以近乎瞬时地把单个客户或全部客户滚回到先前可用版本。官方指出，这会在事故期间暂时阻止客户经 API 做直接更新，但可以在修复数据库的同时继续承载他们的流量，而不是在这段时间里不可用。

Process

  • 官方把本次变更放在 Code Orange: Fail Small 第一项下，并重申：任何进入 Production 的变更都要受控发布，直到“对网络的所有变更都尽可能渐进”重新建立起信心。对 Addressing API 配置变更的分阶段测试介导与正确性检查，事故前已在并行推进，但 “preventative measures weren't fully deployed before the outage”。
  • Owner、截止日期、具体里程碑：报告未说明。
  • 我们的建议（非官方承诺）：对会删除或撤回生产资源的任务，把“结果集大小/比例异常则拒绝执行”做成硬门禁，而不是只靠事后熔断；API 布尔/过滤标志应使用真正的布尔或存在性检查，并在契约测试里覆盖“参数存在但值为空”；任何会立即推到全球边缘的权威控制面，应默认先写到可回滚的快照层，再由健康指标介导下发；预发与审查清单应把“无人工触发的定期任务改用户数据”列为必测路径，而不是只测同步的用户自助 API。

9. Lessons

官方未使用 well / poorly / lucky 分栏。以下为归档侧解读。

  • 做得好：公开了客户端查询与服务端判断的关键代码，机制可独立验证；用前缀数量和 25% 比例量化影响，并说明迭代发布限制了波及面；发现 one.one.one.one 异常后在约 50 分钟内终止了清理任务，避免其余约 75% 的 BYOIP 前缀被撤回；19:19 即向客户给出控制台自助宣告的指引；按三种受损状态解释为何不能立刻恢复；清楚区分“已在并行推进但未上线的防护”与事后将做的三项改进，并承认爆炸半径不可接受。
  • 做得差：以定期任务删除生产前缀的路径上，一个空查询参数就能把全量列表当成待删集合；该控制面会立即传遍边缘，且当时没有可用的快照式快速回滚；测试通过的是客户自助旅程，放过了 task-runner 静默改数据；绑定被连带删除后，约 300 条前缀失去自助恢复能力，全局配置下发把总恢复时间拉到数小时。用来降低人工操作风险的自动化，在配套的 schema 校验、熔断和健康介导发布尚未就绪时先上了 Production。
  • 运气：报告未把结果写成运气。迭代推进与及时叫停是设计/响应上的限幅，不是偶然免于全量撤回。1.1.1.1 的 DNS 解析（含 DoH）本身未受影响，只有解析器网站出现 403，减轻了对公共 DNS 的连带伤害；原文未解释网站为何会以 403 而不是超时的形式出现，也未把这写成运气。
  • 我们的建议（非官方承诺）：见第 8 节。关键迁移点是：自动化若没有比人工更强的安全边界，就只是把“紧邻 Production 的风险”放大成可系统执行的全量删除。

学习价值：定期清理任务用无值的 ?pending_delete 去拉“待删除”前缀，而服务端只在参数非空时才过滤，结果把全量 BYOIP 前缀当成待删对象，再经会立即传遍边缘的 Addressing API 系统撤回 BGP 宣告。迭代发布加上及时叫停把撤回限制在约 25%，但配置态与运行态共用同一数据库、又没有健康指标介导的快照回滚，服务绑定被连带删除后约 300 条前缀无法自助恢复，大部分时间耗在把状态重新推到每台边缘机器。用来消灭高风险人工操作的自动化，如果没有 schema 校验、大范围撤回熔断和可瞬时回滚的配置快照，本身就会变成更大的爆破半径。
