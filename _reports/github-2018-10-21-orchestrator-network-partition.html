October 21 post-incident analysis

元信息

  • 公司: GitHub
  • 标题: October 21 post-incident analysis
  • 日期: 2018-10-21（持续至 2018-10-22；复盘发布 2018-10-30）
  • URL: https://github.blog/news-insights/company-news/oct21-post-incident-analysis/
  • 原文路径: raw/github-2018-10-21-orchestrator-network-partition.md
  • 严重度 / 时长: 降级服务约 24 小时 11 分；无用户数据永久丢失
  • 原文完整度: 中高（决策与后续步骤清楚；首次发现渠道略缺）

1. 影响（Impact）

  • 约 24h11m 降级服务；暂停 webhooks/Pages。
  • 无用户数据永久丢失；部分写入需对账。
  • 展示数据可能陈旧/不一致（完整性优先策略的代价）。
  • 用户数/%：报告未量化。

2. 导火索（Trigger）

光学维护期间出现的 43 秒网络分区。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • Orchestrator（Raft）将 MySQL 主库 跨区域自动提升到 US West。
  • 应用向西岸写入；东岸仍有 未复制的数秒写入 → 分叉 / 脑裂风险。

3.2 促成因素（Contributing）

  • 团队选择 数据完整性优先于快速回切：从备份恢复、fail-forward，接受长时间降级。
  • 跨区域自动提升与应用延迟/一致性模型不对齐。
  • 状态页粒度粗糙，沟通面受限。

3.3 为何防护没挡住 / 为何潜伏

  • 自动故障转移在跨区域场景产生有害拓扑变化——自动化按设计运行，但设计假设与一致性模型冲突。
  • 短暂分区即可触发长恢复（备份重建 RTO）。

3.4 证据与未知

  • 证据：43 秒分区、Orchestrator 跨区提升、完整性优先决策、24h11m、四条 next steps。
  • 未知：首次发现是监控还是 Orchestrator 事件本身触发。

4. 检测（Detection）

  • 报告围绕 Orchestrator 自动提升与后续决策展开。
  • 首次发现方式：报告未说明。

5. 止血（Mitigation）与修复（Fix）

  • 临时止血 / 事故响应: 数据完整性优先——从备份恢复、fail-forward；暂停 webhooks/Pages；接受约 24h11m 降级。
  • 永久修复: Orchestrator 禁止跨区域主库提升；更丰富多组件状态页；加速 active/active；混沌测试。

6. 影响为何被扩大（Amplifiers）

  • 跨区域自动提升扩大拓扑变化代价。
  • 短分区触发长恢复（备份重建）。
  • 状态页粒度粗糙影响沟通。

7. 既有防护与 SOP

  • 存在的控制: Orchestrator 自动主库提升（设计内故障转移）；「完整性优先」是明确响应取向。
  • 缺口或失效模式: 跨区域自动提升在该场景 设计有害（控制本身成放大器）；事后禁止。完整 runbook 全文：报告未展开。

8. 后续改进措施（Action Items）

（原文未标 Type/Owner；归档侧归类，owner：原文未指定）

Prevent

  • Orchestrator：禁止跨区域主库提升。
  • 加速 active/active 多活数据中心。

Detect / Process

  • 更丰富的多组件状态页。
  • 加强主动故障注入 / 混沌测试。

Mitigate

  • （事故中）完整性优先 + 暂停 webhooks/Pages 已是 mitigations；长期 mitigate 与 active/active 重叠。

9. 教训（Lessons）

报告未正式分栏，但决策叙述清晰：

  • Well: 选择数据完整性、无永久用户数据丢失。
  • Poorly: 跨区域自动提升与应用模型不对齐；短分区可触发长恢复；状态页不足。
  • Lucky: 报告未明确写运气因素。
