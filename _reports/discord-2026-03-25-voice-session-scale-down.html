背景知识

  • Sessions / sessions service：Discord 实时基础设施的核心。每台已连接设备在集群里对应一个 session 进程；聊天消息、presence 更新，以及经 websocket 推到客户端的内容都经过它。本次作为常规调优的一部分，对该服务做了减副本、加单 pod 资源的配置变更；第一个 zone 中 50% 的 pod 被非优雅终止后，全站约 17% 的 session 一次性丢失。
  • Kubernetes 缩容、replica count 与 termination grace period：把工作负载的期望副本数调低后，Kubernetes 会终止多余的 pod。被终止的 pod 先收到信号，并在 grace period 内做清理；到期后会被强制杀掉。本次正是降低 replica count 触发了第一 zone 50% pod 被终止，而交接没能在 grace period 内开始。
  • 进程交接（handoff）与 entity count / safety check：有状态的 Elixir 系统在主机下线前，必须把进程数据交到其他节点。部署侧会监控每台服务器上的 entity count，设计上要等该计数到零才终止 pod。作为 backstop，服务在收到 Kubernetes 信号后也会尝试交接。本次一道为等待其他进行中事件完成而设的 safety check，使交接在宽限期结束前仍未开始。
  • GenServer 与 process mailbox：Elixir 里的通用服务进程（可按 actor 理解）。每个实例一次只处理邮箱（mailbox）里的一条消息。邮箱积压时，热路径会变慢甚至赶不上新消息。本次语音故障的核心瓶颈，就是两个负责建连/取连接的 supervisor 邮箱被撑满。
  • **Process.monitor 与 :DOWN 消息**：通过 Process.monitor（或更可扩展的 ZenMonitor），被监控进程无论因何退出，监控方都会在邮箱里收到 {:DOWN, …}。17% 的 session 同时退出后，依赖它们的 guild、gateway、通话所属服务都会收到这类消息，从而启动重连和语音状态更新。
  • Gateway：所有 websocket 流量的出入点。客户端启动时连到 gateway，由它向 sessions service 创建 session，并维持长连接向客户端分发消息。Gateway 会监控用户 session，异常时立刻让客户端重连，并乐观地尝试在同一 zone 恢复原 session；session 已不在则新建。本次受影响 session 都在 us-east1-b，对应 gateway 也大多同区，重连洪峰先打在这一 zone。
  • Voice syncers 与 voice state：每个已加入通话的 session 都有 voice state，由 discord_guilds 或 discord_calls 等 call-owning 服务转到 voice syncers。Voice syncers 评估活跃 voice state，决定通话放置，并持续向全球逾 25,000 个外部 Selective Forwarding Unit（SFU）发 RPC。SFU 在参与者之间代理端到端加密媒体。本次被压垮的就是这层控制面，用户因此长时间停在 “Awaiting Endpoint”。
  • Holster.Pool、gun 与 supervisor 的 selective receive：Voice syncers 经内部库 Holster，用 Erlang HTTP 客户端 gun 做连接池。新建连接要经过两个会成为瓶颈的 Erlang supervisor：一个服务所有 Holster.Pool 使用者，另一个服务所有 gun 连接。它们都是单线程 GenServer，在 spawn 子进程时做 selective receive（扫描邮箱等待子进程 ACK）。事后测试：邮箱约 10 万时，spawn 约增加 1ms；若邮箱到 100 万、每秒 100 次 spawn 且每次有 1ms 延迟，就无法赶上。Gun supervisor 积压会挡住新连接；Holster.Pool DynamicSupervisor 积压会挡住从池中取出已有和新的连接。
  • etcd 与 consistent hash ring：Elixir 服务发现由 etcd（分布式键值存储）支撑，实例按一致性哈希环放置进程；每个实体有 primary、secondary、tertiary 三个实例。实例定期向 etcd 报告健康，TTL 为 60 秒。本次 etcd 连接也走上述瓶颈 supervisor，续约被堵住后实例从哈希环掉出，剩余健康实例还要承接 failover 流量。

1. 影响

  • 官方事实：2026-03-25 12:13–15:30 PDT（2026-03-26 03:13–06:30 Asia/Shanghai），Discord 的 voice and video 出现 major degradation，约 3 小时 17 分钟。在此期间，用户大多无法发起或加入通话，呼叫状态显示 “Awaiting Endpoint”。
  • 直接触发面：一次常规配置更新导致大量 session 管理服务器同时关闭，全站 17% 的 session 一次性丢失。Session 是实时基础设施的心跳，每个已连接设备维持一个；丢失 17% 后，影响级联到多个下游系统，最终压垮负责把语音和视频通话路由到全球正确服务器的服务（voice syncers）。
  • A/V 影响从 12:13 PDT 就开始：全部 15 个 voice syncers 的聚合进程邮箱长度开始增长，发往 SFU 的 RPC 随之急剧下降。官方后文写，因所有主机从哈希环掉出、不再承接新 syncer、也无法再发 RPC，可以 reasonably certain 当时所有实例上的 Holster.Pool DynamicSupervisor 都已积压。
  • 与语音并行，gateway 在 us-east1-b 出现内存打满并重启：该 zone 剩余用户的 gateway 连接被终止，但他们的 session 按设计仍在。这些用户与已丢失 session 的用户一起再次重连，failover 到 us-east1-c 和 us-east1-d。仍有 session 的用户被重新挂上并立即恢复在线，没有 session 的用户则开始重建 session。聊天、presence 等非语音功能因此受到何种量化影响：报告未说明；官方对客户可见故障的概括，集中在语音和视频与 “Awaiting Endpoint”。
  • 恢复过程中，13:05 PDT 的全量重启曾让部分通话离开 “Awaiting Endpoint”，但到 13:09 PDT 邮箱再次持续增长。14:26 PDT（05:26 Asia/Shanghai）翻倍后的集群达到 fully healthy state；官方把降级窗口写到 15:30 PDT（06:30 Asia/Shanghai）。这约 64 分钟的差距里发生了什么：报告未说明，不以 14:26 替换官方结束时刻。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 配置更新降低了 session 管理服务的 replica count。Kubernetes 在第一个 zone 终止了 50% 的 pod。服务在收到 Kubernetes 信号后本应交接进程，但一道用于等待其他进行中事件完成的 safety check，使 Kubernetes 的 termination grace period 在交接开始前就已经耗尽。Session 服务跑在三个均衡的 zone 上，因此全站 17% 的 session 被非优雅停止。
  • 这些 session 全部位于 us-east1-b，其 gateway 连接也大多同区。监控进程向依赖方发送大量 :DOWN 消息：gateway 驱使用户重连；通话所属服务向 voice syncers 发送断开的 voice state。Voice syncers 随即向全球 SFU 舰队发出大量停止、重建和再连接的 HTTPS RPC。这些出站连接都要经过 Holster.Pool 与 gun 两个单线程 supervisor，邮箱被打满后，新连接和池内取连接都在超时时间内无法完成；同一条路径还堵住了 etcd 续约，实例在 60 秒 TTL 到期后从哈希环掉出，无法再承接或管理通话。用户因此大多停在 “Awaiting Endpoint”。
  • 上述为官方对客户可见语音故障如何发生的直接表述。为何缩容时交接没开始、为何下游一个连接池就能卡住控制面，见 3.2。

3.2 促成因素（Contributing）

  1. Safety check 与 termination grace period 的交互（官方）：部署设计是监控 entity count、到零才终止；另有收到信号后开始交接的 backstop。本次 safety check 要等待其他 in-progress events 完成，结果宽限期结束时交接仍未开始，pod 被非优雅杀掉。该 check 当时在等待什么、宽限期是多少秒：报告未说明。事后引入 validating admissions webhook，在 pod 成功交接前拒绝缩容更新，属由整改项回推：事发时缩容请求可以先被 Kubernetes 应用，再在已被终止的 pod 上尝试交接。
  2. 三个均衡 zone 把单区 50% 浓缩成全站 17%（官方）：官方在同一段写明，因为 session 服务跑在三个均衡 zone，所以 17% 的 session 被非优雅停止。17% 仍足以触发后续级联。
  3. 受影响 session 与 gateway 同区（官方）：全部受影响 session 在 us-east1-b，gateway 连接也大多同区，17% 的恢复/重建请求首先打在同一 zone 的 gateway 上。
  4. Session 创建限流未随 Kubernetes 迁移重调（官方）：Gateway 上已有 start session rate limit，用于在请求洪峰时提供反压，但迁移后尚未重调。当时 pod 数量高于先前的 VM 架构，按 host 的限流放行了更多容量，加重了并发 session 启动的序列化，us-east1-b 全部 gateway 节点内存打满并重启，把该 zone 剩余用户也卷入重连。
  5. Voice syncers 出站连接的双 supervisor 瓶颈（官方）：新建 HTTPS 连接要经过 Holster.Pool 与 gun 两个 supervisor；它们在 spawn 时做 selective receive。事后测试给出约 10 万邮箱增加约 1ms spawn、以及 100 万邮箱配每秒 100 次 spawn 便无法赶上的量级。Gun supervisor 积压会挡住新连接；Holster.Pool DynamicSupervisor 积压会挡住从池中取连接。Recon 按邮箱长度排序后，第一名是 Holster pool 的 DynamicSupervisor。
  6. etcd 续约与出站 RPC 共用同一瓶颈（官方）：服务发现所用的 etcd 连接也走这两个 supervisor。邮箱增长后，健康续约同样被堵住，60 秒 TTL 到期即从哈希环掉出。掉出的实例不再承接新 syncer，但仍持有冲击前的大部分进程；剩余健康实例还要作为 secondary / tertiary 承接额外流量，自身也再次被打满。
  7. 上游创建限流过时、未设置，且 guilds 只限制 coordinator（官方）：Call owner 侧已有 voice syncer 创建限流，但响应中发现它在各 call owner 服务上已经过时或未设置。Guilds 上的限流尤其无效：它只限制每个 guild 的 “coordinator” voice syncer 创建，却允许该 guild 下每个语音频道无限制地创建 child syncer，而每个 child 至少要选一个 SFU 并建连。
  8. Voice syncers 仍跑在需手工扩容的 VM 上（官方）：在 A/V 基础设施走完 Realtime 团队的 Kubernetes 迁移之前，扩容是较慢的手工过程：实例位于 Terraform 定义的 GCP VM 上，由 Salt 配置，还要手工加入 etcd 的 ring candidates。事中新增 15 个实例（使容量翻倍）需要等待 Salt 完成供给，拉长了恢复。
  9. 过早重启造成的冷启动冲击（官方，亦属恢复路径上的促成）：单实例重启和 13:05 的全量重启都曾短暂恢复，随即因健康实例承接 failover、或 “quickly re-creates millions of active calls” 的 thundering herd，邮箱再次持续增长。这不是起始根因，但使 “Awaiting Endpoint” 被延长。

为何没挡住：entity count 到零才终止、收到信号后交接，这两道设计都没能在 grace period 内完成 drain；缩容请求在交接完成前就被 Kubernetes 应用。Gateway 的 session 创建限流、voice syncers 上游创建限流本应提供反压，但前者迁移后未重调，后者过时或未设置。连接池与 etcd 共用 supervisor，使数据面洪峰可以直接把实例从服务发现里打掉。这些是原文写明或由整改项可回推的控制失效，不是 “有人操作失误”。

3.3 因果链 / Five Whys（归档侧整理，依据原文）

  1. 为何用户大多无法发起或加入通话，并看到 “Awaiting Endpoint”？→ Voice syncers 无法再向 SFU 可靠地发送放置与管理通话的 RPC；A/V 影响从 12:13 PDT 起，15 个实例的聚合邮箱开始增长，RPC 急剧下降。
  2. 为何 RPC 发不出去，实例还会从哈希环掉出？→ 出站 HTTPS 都要经过 Holster.Pool 与 gun 两个 supervisor；邮箱积压后，新建连接和从池取连接都在超时前无法完成。etcd 续约走同一路径，60 秒 TTL 到期后实例掉出哈希环，不再承接新 syncer。
  3. 为何这两个 supervisor 会被打满？→ 17% 的 session 被非优雅停止后，通话所属服务发出大量断开 voice state；空通话被停止，重连时又要重建通话并把 session 接回去，形成面向全球逾 25,000 个 SFU 的出站连接洪峰。单线程 supervisor 上的 selective receive 使积压一旦形成就难以赶上。
  4. 为何会一次性非优雅失去 17% 的 session？→ 一次降低 replica count 的配置更新在第一个 zone 终止了 50% 的 pod；safety check 使交接在 Kubernetes grace period 耗尽前仍未开始。三个均衡 zone 把这一区的 50% 变成全站约 17%。
  5. 为何语音恢复用了约 3 小时，而不是在 gateway failover 后很快结束？→ 同区 gateway 还因限流未重调而 OOM，加重重连。Voice syncers 侧，单实例与全量重启都触发了 failover 或冷启动冲击；上游限流当时过时或未设置；扩容仍依赖手工供给 VM。直到 13:43 PDT 下调 spawn 限流、随后成功做针对性重启，并在 14:15–14:26 PDT 把新增 15 个实例接入、完成最后一次重启后，翻倍后的集群才完全健康。

6. 影响为何扩大

  • 一次性丢失 17% session，且集中在同一 zone（官方）：缩容在第一 zone 杀掉 50% 的 pod，交接又没开始，三个均衡 zone 把冲击变成全站 17%。受影响 session 都在 us-east1-b，gateway 也大多同区，重连没有被打散。
  • 已有限流在迁移后失效，把 gateway 也卷进去（官方）：start session rate limit 未重调，按 host 放行了更多容量，us-east1-b 的 gateway 内存打满并重启，该 zone 剩余用户（session 其实还在）也被终止连接并加入重连，failover 到 c/d。这扩大了瞬时冲击，尽管官方说仍有 session 的用户被挂回后立即恢复在线。
  • 语音控制面的连接池与服务发现耦合（官方）：出站 RPC 洪峰打满 Holster.Pool / gun supervisor 后，etcd 续约一并被堵，实例从哈希环掉出。设计上每个实体有 primary/secondary/tertiary，单一健康实例可承 3/15 的全局流量（实例 2-8 一度赶上并带来 endpoint selection / RPC 成功的尖峰），但多数实例掉出后，健康实例被 failover 流量再次打满，针对性重启因此失败。
  • 上游限流缺口与手工扩容慢（官方）：call owner 限流过时或未设置，guilds 还允许无界 child syncer，恢复阶段的重建请求没有被有效节流。Voice syncers 仍在 VM 上，新增 15 个实例要等 Terraform/Salt/手工加入 etcd，供给本身成为恢复路径上的慢环节。
  • 恢复动作一度放大负载（官方）：全量重启会迅速重建数百万活跃通话；在限流生效和容量翻倍之前，冷启动 thundering herd 使集群再次回到邮箱持续增长。影响被延长到小时级，而不是在定位到 Holster 瓶颈后立刻结束。
  • 用户数、失败比例、文本聊天是否同步不可用：报告未说明，不臆测为全站会话级中断。

9. Lessons

官方未使用 well / poorly / lucky 分栏，但文末 “Guided by Constraints” 给出了可迁移教训。以下为归档侧解读，其中 “lucky” 一词来自官方对实例 2-8 的表述。

  • 做得好：长文把缩容、17% session 丢失、gateway 同区重连、再到 voice syncers 连接池与 etcd 掉环的级联写清楚，而不是停在 “语音挂了”。事中用 Recon 迅速定位到 Holster.Pool DynamicSupervisor 邮箱最长；在全量重启失败后改走 “降需求（限流）+ 增供给（翻倍扩容）” 两条并行线，并根据 13:43 后 “积压从 Holster.Pool 变为 gun supervisor、仍能取到池内旧连接” 这一差别，重新做针对性重启，最终在 14:26 把集群恢复健康。4 月 29 日发布的这篇复盘里，改进覆盖了缩容准入、连接池并行化、去掉共用 gun supervisor、上下游限流和更细的邮箱/RPC/服务发现观测，而不是只写 “以后小心缩容”。官方写：以往大负载事故的瓶颈往往在各类 ScyllaDB、并限制恢复；去年他们为过载的 API 增加了可自动、定向降低需求的 circuit breaking。本次则是 “our databases performed admirably; the bottleneck shifted to our voice services”——官方把这写成约束转移到了语音服务，而不是底层存储出了问题。
  • 做得差：有状态服务的缩容在交接完成前就被 Kubernetes 应用；safety check 与 grace period 不同步，使 “到零才杀” 和 “收到信号再交接” 都没有生效。Gateway 限流未随迁移重调，把单 zone 的 session 丢失扩大成该 zone gateway OOM。Voice syncers 的出站连接与 etcd 续约共用会积压的 supervisor；上游限流过时或未设置，guilds 还留下无界 child syncer。控制面仍靠手工供给 VM，扩容本身很慢。前几轮重启在限流和容量到位前放大了冷启动冲击，使 “Awaiting Endpoint” 持续到小时级。
  • 运气：官方写实例 2-8 “was lucky enough to catch back up”，独自清掉邮箱并重新加入 etcd，带来 endpoint selection 和 RPC 成功的尖峰；但官方同时写明，仍需进一步干预才能恢复全部全球流量。14:03 之后针对性重启开始持久成功，官方也归因于限流、非高峰/事故导致的全局 syncer 减少，以及集群更健康后更少的 failover 放置——后两项不完全受响应人员控制。原文没有把整段恢复称为运气。
  • 我们的建议（非官方承诺）：见第 8 节。缩容准入、宽限期与 safety check 的时序、连接池与服务发现解耦、迁移后重调限流，应成为有状态实时系统的硬门禁。这些不是官方承诺。
