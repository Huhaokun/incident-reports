背景知识

  • 事件流平台：把 PR、webhook、Actions、审计日志等变更以事件形式异步分发出去的内部总线。这次是总线服务器内存耗尽，下游表现为延迟而不是同步 API 立即失败。
  • 重连退避：客户端重连时拉长间隔并加抖动，避免所有客户端同时打到已受损的服务器。

1. 影响

内部事件流平台降级，导致多条下游延迟。PR 更新、push webhook、由 push 触发的 Actions，最多延迟 33 分钟（至 15:36 UTC）；Actions 状态更新最多延迟 33 分钟（至 16:16 UTC），拖慢了等待检查的合并和部署；webhook 投递和实时更新最多延迟 25 分钟（至 16:52 UTC）；审计日志最多延迟约 2 小时。

2. 导火索

官方未写引起这轮客户端重连的起始事件。

3. 根因

直接原因

事件流平台的服务器因客户端重连缺少足够的重试退避，内存耗尽。

促成因素

连接没有在各服务器之间自动再平衡；平台也没有拆成更小的隔离集群，故障域偏大（这两项是事后才规划的）。

防护为何没挡住

重连缺少退避，内存被打满后平台失去处理能力；事中只能靠把最忙的负载迁到较空闲的服务器并增加容量。

4. 怎么发现

书面 RCA 未写内部检出渠道。状态页 14:52 UTC（22:52 Asia/Shanghai）创建，已在窗口开始后约 1.5 小时。检测偏慢，但官方未解释原因。

5. 止血与修复

临时：把最忙的负载迁到较空闲的服务器，并增加容量。

永久（官方）：已经加上重连退避并增加了服务器容量。正在做连接自动再平衡，以及把平台拆成更小、相互隔离的集群，以缩小爆炸半径、缩短缓解时间。后两项未写完成态。

6. 影响为何扩大

同一事件流平台同时服务 PR 更新、webhook、Actions 和审计日志。审计日志积压最久。状态页创建距影响开始约 90 分钟，放大了对外可见的持续时间。

7. 既有防护与 SOP

防护或 SOP是否存在本次表现
重连退避当时不足，事后已加重连把服务器内存打满
把负载迁到较空闲的服务器 / 加容量存在（事中用了）生效
连接自动再平衡、更小隔离集群事后规划当时没有，爆炸半径偏大

8. 后续改进措施

  • Prevent：已加重连退避和容量。
  • Mitigate：建设连接自动再平衡，拆成更小隔离集群（进行中）。

9. 教训

  • 做得好：分项给出了各子系统的延迟上限和恢复时刻；事后先补了退避和容量。
  • 做得差：共享事件总线在重连没有退避时会全线延迟；状态页创建明显晚于影响开始。
