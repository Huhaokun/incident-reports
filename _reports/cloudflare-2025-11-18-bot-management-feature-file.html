Cloudflare outage on November 18, 2025

元信息

  • 公司: Cloudflare
  • 标题: Cloudflare outage on November 18, 2025
  • 日期: 2025-11-18
  • URL: https://blog.cloudflare.com/18-november-2025-outage/
  • 原文路径: raw/cloudflare-2025-11-18-bot-management-feature-file.md
  • 严重度 / 时长: 核心流量约 11:20–14:30 UTC 大面积失败；全部系统约 17:06 正常。非网络攻击
  • 原文完整度: 中（根因与改进方向清楚；即时止血步骤与 SOP 细节缺失）

1. 影响（Impact）

  • 11:20 UTC 起 Cloudflare 网络无法正常投递核心流量；用户看到 Cloudflare 错误页。
  • 核心流量约 14:30 大体恢复；全部系统约 17:06 正常。
  • 状态页也恰巧故障。官方明确：非网络攻击。

2. 导火索（Trigger）

当日 11:05 对 ClickHouse 的数据库访问控制（权限）变更。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 权限变更使底层 r0 schema 元数据对生成查询可见。
  • Bot Management「特征文件」生成查询读取 system.columns，缺少按数据库名过滤，重复列出现 → 特征文件约翻倍。
  • 代理对特征数有硬上限（约 200，预分配内存）；超限导致 FL2 panic → HTTP 5xx。

3.2 促成因素（Contributing）

  • 特征文件约每 5 分钟向代理传播；好坏文件交替，表现为抖动失败。
  • 失败模式是整代理 panic，而非关停 Bot Management 单模块后继续转发。
  • 初期症状像 DDoS；状态页故障加重判断成本。

3.3 为何防护没挡住 / 为何潜伏

  • 平台自生成配置被当作可信输入：生成查询缺库名约束；摄入侧缺少大小/形状校验与硬上限保护。
  • 核心代理对配置异常选择崩溃而非降级。
  • 报告未给出完整 5 Whys。

3.4 证据与未知

  • 证据：权限变更时间、特征文件翻倍机制、~200 特征硬上限、FL2 panic、恢复时间点。
  • 未知：即时止血具体操作；首条内部告警来源；既有 SOP 文本。

4. 检测（Detection）

  • 用户侧可见错误页；11:20 UTC 起核心流量失败。
  • 好坏文件抖动初期像 DDoS。
  • 首条内部告警来源、是否客户先报：报告未说明。

5. 止血（Mitigation）与修复（Fix）

  • 临时止血: 报告未说明即时止血的具体操作步骤（仅给出约 14:30 / 17:06 恢复时间线）。
  • 永久修复: 见第 8 节加固项（摄入加固、kill switch、失败模式审查等）。

6. 影响为何被扩大（Amplifiers）

  • 超限配置导致核心代理直接 panic（非模块级降级）。
  • 特征文件周期性传播扩大面。
  • 好坏文件抖动误导归因；状态页同时故障。

7. 既有防护与 SOP

  • 存在的控制: 报告提到特征文件传播与代理硬上限（硬上限本身成了崩溃触发器）。
  • 缺口或失效模式: 缺库名过滤；缺配置摄入校验；缺功能级全局 kill switch（事后提出）；失败模式为整代理崩溃。正式 SOP 有无：报告未说明。

8. 后续改进措施（Action Items）

（原文未标 Type/Owner；归档侧归类，owner：原文未指定）

Prevent

  • 将 Cloudflare 自生成配置的摄入按用户输入同等加固。
  • 全面审查核心代理各模块的失败模式。

Mitigate / Blast-radius

  • 增加更多功能级全局 kill switch。
  • 防止错误转储打满资源。

Detect / Process

  • 报告未单列独立 detect/process 条目。

9. 教训（Lessons）

报告未按 well / poorly / lucky 分项：

  • Poorly（归档摘要）: 平台自生成配置与用户配置同等危险；硬上限应失败为降级而非拖垮整代理；症状抖动强烈干扰归因。
  • Well / Lucky: 报告未分项说明。

10. 关键时间线（摘要）

  • 11:05 UTC — ClickHouse 权限变更
  • 11:20 UTC — 核心流量开始失败
  • ~每 5 分钟 — 特征文件传播；好坏文件交替
  • ~14:30 UTC — 核心流量大体恢复
  • 17:06 UTC — 全部系统正常
