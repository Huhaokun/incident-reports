背景知识

术语说明
Routing layer（路由层）位于客户端与模型推理之间的请求分发层。本次官方将故障定位在该层节点：内存触顶、未通过就绪检查后退出服务。
Readiness check（就绪检查）编排系统用来判断节点能否继续接流量的探活。未通过则节点被移出服务池。本次节点因内存超限未通过检查。
responseBuffer路由层处理响应时使用的缓冲区。官方称缺陷是在循环中不断新分配 buffer、没有复用，导致垃圾回收（GC）在高请求量下落后。
GC（垃圾回收）自动回收不再使用的内存。分配速度超过回收速度时，进程内存会持续上涨直至触达限制。
Completions模型补全/生成请求。官方称事发当天 completions 数量远超此前任何一天，并相信这是压垮服务的 tipping point。
Load shed（减载/弃载）主动限制或丢弃部分入站流量，以免剩余实例被过载拖死。本次止血包含限制入站流量；事后又补了一系列限流控制。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 路由层节点内存触及上限，就绪检查失败。
  • 足够多的节点因此退出服务后，剩余容量无法承接入站流量，服务也无法自行恢复。
  • 上述两句均为官方对 outage 发生机制的直接表述。

3.2 促成因素（Contributing）

  1. 软件缺陷（官方）：持续在循环中分配新的 responseBuffer 而不是复用，使 GC 在高请求量下落后，造成慢性内存问题。修复是预分配并复用 buffer；上线后官方称内存与 CPU 均有 3 倍改善。
  2. 容量头寸不足（官方）：事后调整了内存限制以提供 significant available headroom，并作为额外预防增加了该服务容量——说明事发时限制与容量余量不够（归档侧根据整改项回推，官方未给出事发时的具体限制值）。
  3. 自动扩缩此前无法启用（官方）：过去给该服务加容量会负面影响某个上游服务，因此不能开自动扩缩。底层问题修复后，官方才计划配置自动扩缩。
  4. 优雅减载不足（由整改项回推）：止血时需要限制入站流量；事后才 implemented a series of rate limit controls to more gracefully load shed。事故前是否已有任何限流：报告未说明具体设计，只知道响应中新做了一系列限流控制。
  5. 就绪检查在内存压力下的正反馈（归档侧推断）：节点因内存失败被摘除，剩余节点承担更多请求，更容易再触顶。官方写 was unable to recover，与该正反馈相符，但原文没有逐步画出这条反馈环，故标为推断。

3.3 因果链 / Five Whys（归档侧整理，依据原文）

  1. 为何大量请求返回 502/503？→ 路由层没有足够健康节点承接流量。
  2. 为何健康节点不够？→ 节点因内存触顶未通过就绪检查，退出服务池。
  3. 为何内存触顶且无法自愈？→ 高负载下慢性内存问题使节点持续变少，剩余容量不够，服务无法恢复。
  4. 为何会有慢性内存问题？→ 循环中不断新分配 responseBuffer 而非复用，GC 落后。
  5. 为何在这一刻爆发？→ 当天 completions 远超历史，成为 tipping point。为何平时没爆：缺陷是负载相关的慢性问题，低流量时 GC 跟得上（归档侧推断；缺陷引入时间报告未说明）。
  6. 为何不能靠自动加节点自愈？→ 过去扩容会伤害上游，自动扩缩未启用。

根因类别：软件缺陷（主）+ 容量/资源耗尽（次）。归类由本站根据分析归纳，非原报告表述。依据：官方把 underlying issue 明确写成 responseBuffer 循环分配导致 GC 落后；同时把用户可见故障写成节点内存触顶、就绪检查失败后容量不足以承接流量且无法恢复。软件缺陷是可修复的干预点，容量耗尽是它在高峰流量下的直接后果，故不把容量当作唯一根因，也不把流量本身当作根因。

9. Lessons

官方未使用 well / poorly / lucky 分栏。以下为归档侧解读。

  • 做得好：写出了 responseBuffer / GC 这一可验证机制，而不只说内存不够；区分了已实施与计划项；止血组合（限流、重部署、慢速回灌）符合过载类故障的经典减压路径；坦承此类中断对客户业务的伤害。
  • 做得差：共享路由层在高峰下无法自愈，打到所有模型与 API 端点；自动扩缩因上游耦合长期关着；内存行为显然未能在升级前被发现（由计划中的告警反推）。
  • 运气：报告未说明是否有更糟的持久损坏或数据问题。影响窗口约 94 分钟后恢复，但原文未把这写成运气。
  • 我们的建议（非官方承诺）：对分配热点做对象池/复用应有负载测试与内存回归门槛；就绪检查失败率上升应自动触发减载，而不是只摘节点；任何不能自动扩容、因为会打到上游的服务都需要单独的容量防御（硬限流、隔离队列、上游保护）。
