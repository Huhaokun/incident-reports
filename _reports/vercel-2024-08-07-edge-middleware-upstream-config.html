Vercel Edge Middleware / Edge Functions 上游全局错误配置导致调用失败（2024-08-07）

元信息

  • 公司：Vercel
  • 标题：Update regarding Vercel service disruption on August 7, 2024
  • 事故日期：2024-08-07 19:13–19:23 UTC 与 19:26–19:42 UTC（= 2024-08-08 03:13–03:23 与 03:26–03:42 Asia/Shanghai）；合计约 26 分钟
  • 原文：https://vercel.com/blog/update-regarding-vercel-service-disruption-on-august-7-2024
  • 原文路径：raw/vercel-2024-08-07-edge-middleware-upstream-config.md（同名 .html 为完整源页面）
  • 发现线索：用户要求收录 Vercel 故障；官方 Field Engineering 博文（Guillermo Rauch，2024-08-09）
  • 类别：事故复盘
  • 严重度/时长：官方未给严重级别；活跃中断约 26 分钟（两段）；约 61% 调用受影响
  • 原文完整度：中高（有影响数字、时间窗、止血动作与三项改进方向；缺上游厂商名、错误配置机制细节、分钟级内部排查图）

背景知识（术语）

术语说明
Edge Middleware / Edge FunctionsVercel 在边缘侧执行的中间件与函数；本次依赖专用上游计算提供商
Serverless Functions / Static / ISR平台上其他路径；未经 Edge Middleware 前置时本次未受影响
staggered rolloutsVercel 自述对代码与配置做分阶段发布的常规做法
config override事故中对上游发起的配置覆盖，用于解除对其流量的错误拦截

1. 影响（Impact）

  • Edge Middleware 与 Edge Functions 出现高错误率；官方称影响约 61% 的全部调用（invocations）。
  • 活跃中断合计约 26 分钟，分两段：19:13–19:23 UTC 与 19:26–19:42 UTC。
  • 影响因项目用法与客户端 user-agent 而异（原文）。
  • 未经 Edge Middleware 前置的 Serverless Functions、Static Files、ISR 未受影响。
  • 受影响客户数 / 收入 / 支持工单：报告未说明。

2. 导火索（Trigger）

  • 上游专用计算提供商进入全局错误配置状态，未按约定尊重 Vercel 的全球流量配置，从而意外拦截大部分 Vercel 请求。
  • 本站归纳 trigger_types：硬件或外部依赖故障 + 配置推送（厂商侧；本站归纳）。证据：原文“upstream provider … globally erroneous configuration state”“failed to respect our global traffic configurations”。
  • Vercel 侧是否有当日变更：runbook 结论为 Vercel 环境无服务/配置变更（原文）。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 边缘计算路径依赖的专用上游，在错误全局配置下拦截/阻断大部分 Vercel 流量 → Edge Middleware / Edge Functions 调用高错误。
  • 该计算栈与平台其他服务不同源，故故障面主要落在边缘计算路径。

3.2 促成因素（Contributing）

  1. 对单一专用上游的依赖：边缘 Middleware/Functions 当时无等价备份算力（改进项“backup option”即证）。
  2. 厂商 fail-safe / 默认流量限额与 Vercel 规模不匹配：原文称触发中断的默认流量限制已被调整。
  3. 虽有区域故障转移设计，仍无法抵消上游全局错误配置：原文强调平台设计避免单点，但本次是提供商全局配置错误，区域 failover 不够。
  4. 厂商错误配置的具体字段/发布链路：报告未说明。

3.3 Five Whys（归档侧整理）

  1. 为何 Edge 调用失败？→ 上游拦截了大部分 Vercel 请求。
  2. 为何会拦截？→ 上游进入全局错误配置，未尊重 Vercel 全球流量配置。
  3. 为何该错误能全局生效？→ 报告未说明厂商变更控制细节；结果是全局状态错误。
  4. 为何平台未能自动绕过？→ 边缘计算依赖该专用提供商，当时缺少备份算力路径。
  5. 为何默认限额会触发？→ 厂商 fail-safe/默认流量限制未按 Vercel 规模正确配置（原文改进方向）。

3.4 证据与未知

  • 证据：26 分钟两段时间窗、61% invocations、未受影响路径清单、19:41 config override 止血、三项后续举措。
  • 未知（报告未说明）：上游厂商名称；错误配置具体内容；19:23–19:26 短暂恢复原因；客户侧错误码分布。

本站归纳 root_categories：依赖故障（主）+ 配置/变更错误（厂商全局配置；本站归纳）。证据：上游全局错误配置导致拦截；Vercel 自述非己方变更。

4. 检测（Detection）

  • Vercel 监控系统发现错误升高并告警，团队立即开启最高优先级内部调查。
  • 是否有客户先报：报告未说明。
  • MTTD：报告未给出自首错到告警的秒级数字。

5. 止血（Mitigation）与修复（Fix）

  • 临时止血：完成 runbook 后确认 Vercel 侧无变更 → 联系上游排查 → 19:41 UTC 发起 config override，将厂商系统重置为不拦截 Vercel 流量；19:42 恢复期望状态，上游为 Vercel 流量实施适配规模的 fail-safe。
  • 永久修复：调整触发中断的默认流量限制；推进备份算力与统一计算子系统（见改进）。

6. 影响为何被扩大（Amplifiers）

  • 上游配置错误是全局的，区域 failover 设计无法隔离。
  • 边缘计算路径对专用上游的单路径依赖使故障直接打满 Middleware/Functions。
  • 影响面随项目是否使用 Edge Middleware/Functions 与 user-agent 变化；放大器的量化：报告未再展开。

7. 既有防护与 SOP

防护或SOP是否存在本次表现
代码/配置 staggered rollouts有（Vercel 自述常规）本次根因在上游，非 Vercel 自身发布
区域自动 failover / 避免单点有（设计目标）不足以对抗上游全局错误配置
监控告警 + 最高优先级响应有有效检出并启动调查
Runbook（确认己方无变更）有按设计执行，帮助快速转向上游
边缘计算备份提供商无/建设中缺失导致无法就地绕过
厂商 fail-safe 按规模配置当时不足默认限额触发中断；事后已调整

8. 后续改进措施（Action Items）

Prevent

  • 与计算提供商协作，确保 fail-safe 正确配置；触发中断的默认流量限制已按规模调整。
  • 长期：统一 Edge Middleware / Edge Functions / Serverless Functions 的计算子系统，降低对单一提供商依赖。

Mitigate / Blast-radius

  • 加速为 Edge Middleware / Edge Functions 开发备份算力选项（原文称此前已在进行）。

Detect / Process

  • 原文未单列新的检测项；owner/截止日期：报告未说明。

9. Lessons（归档侧解读）

  • 做得好：监控快速告警；runbook 先排除己方变更；config override 在约半小时窗口内止血；公开承认影响比例。
  • 做得差：边缘路径对专用上游缺少可立即切换的备份；厂商默认限额与规模不匹配。
  • 运气：Serverless/Static/ISR 未绑同一上游，故障面未扩至全平台。
  • 我们的建议（非官方承诺）：把“上游全局错误配置/错误拦截”纳入演练与自动切备；对关键上游配置漂移做独立监测。

10. 关键时间线（Asia/Shanghai；原文 UTC）

  • 08-07 夜间（UTC）上游进入全局错误配置（精确引入时刻：报告未说明）

  • 08-08 03:26–03:42 — 第二段高错误窗口（合计约 26 分钟）
  • 监控告警 → 最高优先级调查 → runbook 确认 Vercel 无变更 → 联系上游
  • 08-08 03:41 — 发起 config override，停止主动拦截
  • 08-08 03:42 — 恢复期望状态；上游实施适配 fail-safe

学习价值：区域 failover 挡不住上游全局错误配置；边缘专用算力若无热备，厂商一次限额/拦截即可打掉整条产品路径。
