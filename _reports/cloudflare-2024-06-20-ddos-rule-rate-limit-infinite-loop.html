Cloudflare incident on June 20, 2024

元信息

  • 公司: Cloudflare
  • 标题: Cloudflare incident on June 20, 2024
  • 日期: 2024-06-20（复盘发布 2024-06-26）
  • URL: https://blog.cloudflare.com/cloudflare-incident-on-june-20-2024/
  • 原文路径: raw/cloudflare-2024-06-20-ddos-rule-rate-limit-infinite-loop.md
  • 严重度 / 时长: 约 114 分钟延迟与错误升高；峰值约 30 分钟内 1.4–2.1% CDN HTTP 请求返回通用错误页，p99 TTFB 约升 3 倍
  • 原文完整度: 高（机制、时间窗、止血与改进均有较完整描述）

1. 影响（Impact）

  • 约 114 分钟：Internet properties 与 Cloudflare 服务延迟与错误率升高。
  • 峰值约 30 分钟：1.4–2.1% 指向 CDN 的 HTTP 请求收到通用错误页；p99 TTFB 约 3 倍。
  • 两起独立事件叠加在同一时段。

2. 导火索（Trigger）

14:14–17:06 UTC 部署的新 DDoS 缓解机制；随后带「混合有效/无效 cookie」的 HTTP 请求命中限流死循环路径（主影响窗口约 17:47–19:27 UTC）。同期自动化网络重路由约 17:33 起加重骨干拥塞（独立事件）。

3. 根因（详尽）

3.1 直接原因（Proximate）

请求路径：

  • 新 DDoS 规则把 cookies + rate limits 接到遗留限流组件。
  • 同一请求混合有效/无效 cookie 时，损坏的校验函数与先前校验对多 cookie 请求意见相左，导致 cookie 键生成器递归调用自身。
  • 递归走 Lua proper tail call：栈不增长、不崩溃，进程 永久 100% CPU（process poisoning），该请求处理进程对后续流量失效。

网络面（同期独立）：

  • 自动化网络监控检测到性能下降后按设计次优重路由，约 17:33–17:50 UTC 造成骨干拥塞。

3.2 促成因素（Contributing）

  • 遗留限流组件存在长期潜伏缺陷，与新安全规则耦合。
  • 尾调用优化把「卡死」伪装成「忙但活着」，缺少崩溃信号。
  • Unimog / Traffic Manager 假定「把流量挪到更健康站点」恒安全，未区分会毒化进程的请求。
  • 规则在少数机房验证后数小时内全球铺开，未能在生产规模暴露该路径。

3.3 为何防护没挡住 / 为何潜伏

  • 预发与分阶段发布未覆盖「混合有效/无效 cookie」路径上的尾调用死循环。
  • 自动化重路由按设计运行，却把中毒请求扩散到健康站点。
  • 报告未给出更细的 5 Whys 文本；以上机制来自官方技术说明。

3.4 证据与未知

  • 证据：官方给出时间窗、百分比错误、Lua 尾调用与 Unimog/Traffic Manager 行为描述。
  • 未知：报告未单独说明人工告警渠道名称；未给出完整分钟级时间线全文。

4. 检测（Detection）

  • 自动化网络监控先发现性能下降并触发重路由。
  • 随后 CDN HTTP 错误率与延迟上升可见。
  • 是否客户先报、MTTD 精确值：报告未说明。

5. 止血（Mitigation）与修复（Fix）

  • 临时止血: 大规模滚动重启，清掉已中毒进程、暂时恢复容量。
  • 永久修复（事故中/后）: 完全回滚该 DDoS 规则，规则在 cookie 校验修复前保持关闭；后续迁离遗留限流、限制无限尾调用、带执行时间上限的请求服务等（见第 8 节）。

6. 影响为何被扩大（Amplifiers）

  • 流量调度把含中毒请求的流量挪到健康站点，故障扩散。
  • 同期骨干拥塞干扰排查。
  • 全球快速铺开放大暴露面。

7. 既有防护与 SOP

  • 存在的控制: 分阶段/预发与发布流程；自动化流量调度与监控重路由。
  • 缺口或失效模式: 预发未在生产规模抓住混合 cookie + 尾调用路径；自动化重路由按设计运行却成为放大器（设计不足以挡「进程中毒」类故障）；报告未描述针对 process poisoning 的专门 runbook。

8. 后续改进措施（Action Items）

  • 迁离遗留限流组件。
  • 探索限制无限尾调用循环。
  • 用带执行时间上限的请求服务替换现有请求服务。
  • 修复 cookie 校验（规则回滚直至修复）。

9. 教训（Lessons）

报告未按 well / poorly / lucky 分项；归档侧摘要（非官方分栏）：

  • Well（推断，弱）: 最终通过回滚规则与滚动重启恢复——报告未显式写「做得好」。
  • Poorly: 安全/防护类变更仍需渐进发布；自愈调度可放大故障；尾调用使「卡死不崩溃」难隔离。
  • Lucky: 报告未说明。
