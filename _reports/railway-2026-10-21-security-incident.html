背景知识

  • 多租户构建机与文件系统隔离：事发时，Railway 的构建基础设施把多个构建放在同一台虚拟机上，并依赖彼此之间的隔离。本次攻击者利用此前未知的漏洞，部分逃逸文件系统隔离，读到宿主机上的部分文件，并取得构建服务器用来向一部分内部系统认证的凭证（包括构建完成后推送镜像）。
  • 构建凭证与自建 Temporal 集群：该凭证本应只授权完成构建所需的工作，例如向 registry 推送镜像。Railway 用自建 Temporal 集群调度并运行异步任务，构建流程的一部分由该集群驱动；Temporal 任务里包含构建产物信息，例如限定单个仓库、只读的 GitHub App token，以及传入构建的环境变量和密钥。本次该集群把上述构建凭证当作受信任客户端接受，攻击者得以调用本应给 Temporal 客户端使用的 API，并读取一部分其他构建的存储历史。
  • OIDC binding（错误配置的那一处）：内部 CI/CD 可获取指向生产基础设施的短时云凭证，用于自动部署。攻击者在拿到 Railway 自身 monorepo 后，发现其中一个云环境里“错误定义”的 OIDC 绑定配置，并在 10-21 03:26 UTC 换取到这类短时云凭证。这是官方所称的第二条进入路径。
  • 信封加密（envelope encryption）与每环境 DEK：环境变量使用信封加密：每个环境用自己的数据加密密钥（DEK）加密变量，DEK 再由上游云厂商 KMS 中的根密钥加密。官方写明根密钥不能离开 KMS，设计目标是“一把被盗密钥不能暴露整个平台”。本次攻击者是在拿到编排机上较长生命周期的解密凭证，并具备通往存储信封的生产数据库所在 VPC 的访问后，才解密了部分已取回的信封。
  • Sealed variables 与关联账户令牌：构建历史中包含 sealed variables。攻击者还解密了 1,852 名用户的 linked-account tokens，官方括号中写明是 BYOK agent keys 和 GitHub OAuth tokens。这些是本次除 workspace 环境变量之外，官方单独给出数量的一类凭据。
  • “abliterated models”与 “a harness similar to ARTEX”：官方用于描述攻击方自动化工具的用语，并写明部分描述据 Wiz。原文未展开其技术定义，本分析不另作解释，也不把 Wiz 的 “Black October” 研究当作对本事件的独立归因。

1. 影响

2. 导火索

  • 官方事实：这是一起大规模恶意攻击。攻击者自 10-18 起注册并旋转多种傀儡账户，初期探测均未成功，官方称更早的攻击被自动化系统挡住。10-20 06:50 UTC（14:50 Asia/Shanghai）开始探测构建基础设施；07:28 UTC（15:28 Asia/Shanghai）利用此前未知的构建隔离漏洞，部分逃逸文件系统隔离。这是第一条进入路径的起始事件。
  • 官方强调这不是“一次入侵、一次修复”：攻击者并行探测多条路径，Railway 也并行加固；局面演变成官方所说的 “contest of agent speed”。官方并写明，这是在抵御 “abliterated models and a harness similar to ARTEX, according to Wiz”；后文又称，事中证据表明攻击者使用 “abliterated models with no safeguards”，能够快速连续执行升级动作。以上为官方／据 Wiz 的表述，本分析不另作技术解释，也不把 Wiz 的 “Black October” 研究当作对本事件的独立归因。攻击者在取得 monorepo 后，还探测了已废弃、系统中已无在用引用的端点，并找到错误配置的 OIDC 绑定作为第二条进入路径。
  • 导火索类型：流量突增/攻击（归类由本站根据分析归纳，非原报告表述）。
    • 依据：原文开篇即写 “Railway suffered a security incident from a large-scale malicious attack”，时间线以攻击者探测并利用构建隔离漏洞为起点。分类名中的「攻击」与官方认定一致。
  • 不以「人工操作/命令」或「代码发布/升级」为导火索：触发链的起点是外部攻击者的探测与利用，而不是一次内部发布。错误的 OIDC 绑定和隔离缺陷是被利用的既有条件，放在根因里，不把它们写成当天的导火索。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 攻击者利用构建基础设施中此前未知的漏洞，部分逃逸多租户虚拟机上的文件系统隔离，读到宿主机上的部分文件，并取得构建服务器用于访问一部分内部系统的凭证。
  • 该凭证本应只用于完成构建所需的工作（例如 registry 推送），但用于构建的自建 Temporal 集群把它当作受信任客户端接受。攻击者因此能调用本应给 Temporal 客户端使用的 API，读取一部分其他构建的存储历史（含环境变量、密钥和限定单仓的 GitHub App token），并取到 Railway 内部 monorepo 的快照。
  • 在第一条路径被认为已遏制、构建一度恢复之后，攻击者凭借对代码库的了解（事中 Railway 当时还不知道对方已有代码副本），找到其中一个云环境里错误定义的 OIDC 绑定，换取短时云凭证，再取到内部较长生命周期凭证和用于向一组机器推送二进制的 SSH 私钥，SSH 登录到编排机。该机器磁盘上有用于解密信封加密变量的较长生命周期凭证，并能够访问存储这些信封的生产数据库所在 VPC。攻击者据此取回加密信封并解密了其中一部分。
  • 上述为官方对“攻击者如何实际取得并解密部分客户变量”的直接表述。各环节为何能串起来，见 3.2。

3.2 促成因素（Contributing）

  1. 多租户构建隔离可被部分逃逸（官方）：同一虚拟机上跑多个构建，隔离是核心前提。官方写的是 previously unknown vulnerability，部分逃逸后即可读宿主机上的部分文件。这是第一条进入路径。
  2. 构建凭证被 Temporal 等内部系统过度信任（官方）：凭证的预期范围只是构建工作；架构却允许持有该凭证的人在别处调用 Temporal 客户端 API，从而读到其他构建的历史（含密钥）并拉取用于缓存的仓库快照。这把一次隔离逃逸放大成内部系统与源码的暴露。
  3. 内部 monorepo 快照可被构建凭证取出（官方）：许多 Railway 服务（官方举例 support 平台 station.railway.com）从内部 monorepo 构建并部署在 Railway 上。攻击者取到 monorepo 后，对系统如何运作有了特权视角，能够做 agent fanout、寻找可利用点并快速横向移动。官方写明，他们当时并不知道对方已有代码副本，是在看到对方探测已废弃端点时才意识到。
  4. 错误定义的 OIDC 绑定（官方）：CI/CD 本就可获取短时云凭证以部署生产基础设施。其中一个云环境的 OIDC 绑定配置被错误定义，成为攻击者扫描代码后找到的立足点，也是官方所称的第二条进入路径。没有这次换票，后续取内部凭证、SSH 进入编排机、解密环境变量的链不会按原文发生。
  5. 云环境中可被短时凭证取出的较长生命周期内部凭证（官方）：相关的有两份——一份较长生命周期凭证，在结合内部 VPC 访问后可从生产数据库读取加密的环境变量；一份 CD 用来向特定机器推送二进制的 SSH 私钥，这些机器部分连接到该内部 VPC。短时云凭证足以把它们取出来。
  6. 编排机磁盘上留有较长生命周期的解密凭证，且该机可进入存储信封的 VPC（官方）：这台机器需要这份凭证，以便把客户工作负载开通到集群中的其他节点。它使攻击者能够向 KMS 认证并解密已取回的部分信封。官方同时强调信封加密的设计限制了爆炸半径：每环境一把 DEK，根密钥留在上游 KMS、不能离开；一把被盗密钥不能暴露整个平台。即便如此，磁盘上的解密凭证加上 VPC 通路，仍足以解密查询命中的那一部分。
  7. 查询专门瞄准高价值目标（官方）：数据库日志显示，攻击者按自己提供的正则匹配变量名，优先 AI 提供商密钥，并专门针对环境中变量数量很多的客户。这不创造进入路径，但决定了被解密子集的优先顺序。
  8. 第一次遏制后恢复了构建，当时尚未知对方已有代码副本（官方）：10-20 17:28 UTC 吊销并替换了构建凭证，限制构建服务器可访问的服务，并在认为已堵住升级路径后恢复构建。攻击者再次尝试逃逸构建隔离未成功，但转而用代码里的线索找新入口。这不是第一段进入的原因，但使攻击在次日以第二条路径继续。

3.3 因果链 / Five Whys（归档侧整理，依据原文）

  1. 为何至多约 1.85% 的 workspace 可能有环境变量被解密，且另有构建历史和关联账户令牌暴露？→ 攻击者在 10-21 04:42 起用编排机上的较长生命周期凭证，向 KMS 认证并解密了部分先前取回的信封；此前还通过 Temporal 读过 353 份构建历史。
  2. 为何攻击者能取回信封并调用解密？→ 他们用错误配置的 OIDC 绑定换到短时云凭证，取出内部较长生命周期凭证和 CD 的 SSH 私钥，登录到同时具备磁盘解密凭证和相关 VPC 访问的编排机，于 04:07–05:21 UTC 从生产数据库取回加密信封。
  3. 为何他们能发现并利用这条 OIDC 路径？→ 构建凭证被 Temporal 接受后，他们取到了 Railway 内部 monorepo 快照，从而能根据代码里的线索探测已废弃端点和错误配置；事中 Railway 当时还不知道对方已有代码。
  4. 为何构建凭证足以走到这一步？→ 攻击者先利用多租户构建机上此前未知的隔离漏洞，部分逃逸文件系统，读到宿主机上的构建凭证；该凭证的预期范围被内部系统（至少包括自建 Temporal 集群）超出原意地信任。
  5. 为何爆炸半径没有变成“全平台密钥皆可解密”？→ 官方设计是每环境独立 DEK、根密钥留在上游 KMS 且不能离开，一把被盗密钥不能暴露整个平台；加之 07:14 UTC 禁用了全部有效云凭证、吊销静态凭证并关闭密钥解密服务。上界因此停在日志所能证明的 workspace / environment 范围。取证公司调查仍在进行，IOC 尚未公开。

3.4 证据与未知

6. 影响为何扩大

  • 隔离逃逸后的信任边界过宽（官方）：本应只用于推镜像的构建凭证，被 Temporal 当作受信任客户端，直接打开了其他构建的历史（含密钥）和 monorepo 快照。爆炸半径从“一台多租户构建机上的部分文件”扩大到内部调度系统和源码。
  • 源码暴露加速了第二条路径（官方）：有了 monorepo，攻击者能快速寻找可利用点，并探测已废弃端点。错误配置的 OIDC 绑定因此被找到；短时云凭证又通向较长生命周期内部凭证、SSH 私钥、编排机磁盘上的解密凭证和相关 VPC。客户环境变量的解密发生在这条第二路径上，而不是第一次隔离逃逸当场完成。
  • 磁盘上的长生命周期解密凭证与 VPC 通路（官方）：即便信封加密限制了“一把密钥打开整个平台”，编排机为开通客户工作负载而本地保存的解密凭证，仍使攻击者能在两个时间窗口内解密已取回的部分信封，并按正则优先挑选 AI 密钥和变量很多的客户。
  • 第一次遏制并不完整（官方）：17:28 UTC 吊销构建凭证并限制网络后，构建被恢复；当时还不知道对方已有代码副本。攻击者对构建隔离的再逃逸失败了，但次日仍通过 OIDC 路径继续升级。官方自己把全过程写成并行的攻防，而不是单点修复。
  • 为加固而加速切换新构建系统，放大了可用性影响（官方）：补丁后一小时内内部团队又推出额外利用，促使其放弃渐进发布、立即全量切换，容量一度接近两个数量级高于基线；存储带宽至少 10 倍基线又造成部分构建变慢或失败。构建暂停本身不打断既有部署，但凭证吊销加上无法重新部署，使部分客户的运行中服务出问题。广泛通知带来的流量，官方也写成会再使恢复延迟 1–2 个数量级，这是他们推迟广泛通知的理由之一。
  • 通知顺序与延迟（官方自述）：先通知下游提供商、再完整了解对用户的影响；广泛通知前要先向受影响用户做定向验证，以便他们有时间轮换，并避免在攻击者可能仍在系统内时把密钥轮换后再被盗。官方承认“can always be faster”，并因此更新事件响应 runbook，设定一个时限，到期后无论影响是否完全查清都要做广泛通知。这是官方对沟通延迟的解释，不把它改写成已经证实的技术扩大机制。

9. Lessons

官方未使用 well / poorly / lucky 分栏。以下为归档侧解读。

  • 做得好：在取证尚未结束的前提下，仍给出了两条进入路径、可核对的时间线、影响上界（并标明日志只到 environment）、353 份构建历史和 1,852 名用户令牌等可验证数字，以及“无客户仓库下载迹象 / 无客户库访问迹象 / 无用失窃凭证登录 Railway 账户”的边界；信封加密的设计主张写得很清楚，没有把上界说成精确失窃条数；13:58 的 registry 告警启动了响应，随后对攻击者保持观察；07:14 关闭解密服务、作废会话，并向提供商提交全部密钥哈希以先收缩爆炸半径；补丁后一小时内，内部负责加固原构建器的团队又由原向量推导出额外利用，据此放弃渐进发布、切换到双层隔离的新构建系统；整改覆盖隔离、CI、服务账户、密钥解密路径和通知 runbook；退款方针按厂商分开写，并承认 Anthropic 仍在讨论、OpenRouter 不退则自行承担；对广泛通知延迟有反思，而不是只解释理由。
  • 做得差：多租户构建隔离可被部分逃逸，且逃逸后得到的凭证能被 Temporal 过度信任，直接通向其他构建密钥和自身 monorepo；错误的 OIDC 绑定加上磁盘上的长生命周期解密凭证，使第二条路径能解出客户环境变量；第一次以为已经遏制并恢复构建时，还不知道对方已有代码；从首次利用到告警约 6.5 小时，从换取云凭证到关闭解密服务又过去数小时；广泛用户通知偏晚，官方自己也承认应当更快，并用 runbook 时限来补；加速切换新构建系统后，容量和存储带宽问题又造成构建变慢或失败，凭证吊销加上无法重新部署使部分运行中服务出问题。
  • 运气：10-18 的早期探测被自动化系统挡住，使成功利用推迟到 10-20；信封加密和“根密钥不能离开 KMS”的设计，被官方用来说明不是全平台一把钥匙打开。这两点是既有控制的效果，原文没有称为运气。取证仍未结束，不能把“上界 1.85%”理解成最终精确损失已经锁死。
  • 我们的建议（非官方承诺）：见第 8 节。信任边界应按凭证的最小用途来实施，而不是按“这是内部系统”来默认信任；通知时限应事前写死。这些不是官方承诺。
