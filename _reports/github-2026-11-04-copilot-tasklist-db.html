  • 根因类别（主）：容量/资源耗尽。依据：任务列表流量升高加上昂贵查询，耗尽了共享数据库容量。

  • 归类说明：以上类别由本站根据分析归纳，非原报告表述。

背景知识

  • Copilot Mission Control / agent 任务列表：Copilot agent 用来列出和创建任务的管理界面与 API。这次失败的是这条任务路径，不是代码补全模型本身。
  • 共享数据库容量：多个功能共用一套数据库资源。一条昂贵的任务列表查询可以在流量升高时把整库容量吃掉，让不相干的请求也开始被节流。
  • 客户端实验：向部分客户端版本或用户打开的功能或行为变更。这次关闭该实验是主要止血手段之一，但报告没有写它如何改变了查询或请求量。

1. 影响

  • 官方事实：部分 Copilot agent 用户在列出和创建任务时出错。平均 1.22% 的请求失败，十分钟峰值 2.68%。
  • 事中 08:47 UTC 的更新曾给出约 2.5% 的即时错误率，并提到上游数据库节流。这是事中数字，平均 1.22% 与峰值 2.68% 以书面 RCA 为准。
  • 受影响用户数、任务数：报告未说明。任务列表请求在 10:01 之后仍被限制，直到 11-06 才取消一刀切限制。

2. 导火索

  • 官方事实：任务列表流量升高，叠加昂贵查询，把共享数据库容量耗尽。止血时关闭了一个客户端实验，并临时限制来自受影响客户端的任务列表请求，说明这次升高和某个客户端实验有关。
  • 实验何时打开、是否在 03:40 前后放量、查询昂贵是新引入还是原先就有：报告未说明。不宜把导火索写成一次已证实的「当天发布」，只能写成流量与昂贵查询在共享库上碰头，且与该客户端实验相关。
  • 导火索类型：潜伏缺陷被条件触发（主，归类由本站根据分析归纳，非原报告表述）。
    • 依据：昂贵查询和共享容量缺口事先存在，在任务列表流量升高（并与一个客户端实验相关）时才把库打满。报告未写明该实验的开始时刻，因此不以「配置推送」做主标签。

3. 根因（详尽）

3.1 直接原因（Proximate）

  • 任务列表相关的昂贵查询，在流量升高后耗尽了共享数据库的容量，列出和创建任务的请求失败。事中观察是上游数据库开始节流。

3.2 促成因素（Contributing）

  1. 查询成本高（官方）：任务列表查询在流量起来后不成比例地消耗共享库。「昂贵」的定量标准：报告未说明。
  2. 共享容量没有隔离（官方）：该工作负载和可能不相干的其他负载共用数据库容量，没有足够的隔离或独立限流。官方事后把限流迁到单独的基础设施，并改进任务列表查询。
  3. 客户端实验（官方，机制未写）：一个客户端实验增加了压力。具体是请求频率、查询形态还是用户范围：报告未说明。
  4. 恢复后仍不信任当时的保护（官方）：服务恢复后仍对任务列表请求保留一刀切限制，直到 11-06 才逐步放开，并在扩大放量前增加容量校验。

3.3 根因机制

Copilot Mission Control 的任务列表/创建路径会打到共享数据库。流量升高后，昂贵查询把共享容量吃光，数据库开始节流，于是列出和创建任务失败。关闭客户端实验、限制受影响客户端的任务列表请求后，更广服务恢复；但任务列表本身还被限制了两天，期间他们改进查询、把限流挪到独立基础设施，并加上容量监测，再逐步放开。根因是昂贵查询和共享容量之间缺少隔离，而不是 Copilot 模型或前端本身故障。

3.4 为何没挡住

共享库上的任务列表路径缺少有效的查询成本和流量隔离。数据库节流是过载后的保护，它把影响表现成错误率，但没能在耗尽共享容量之前把这份工作负载挡住。客户端实验的放量前容量校验，是事后才加上的。由整改项回推

3.5 证据与未知

  • 已知（官方）：平均 1.22%，十分钟峰值 2.68%。上游数据库节流。关闭一个客户端实验并临时限制任务列表请求后，更广服务恢复。任务列表限制保留到 11-06。随后改进查询、把限流迁到单独基础设施、增加容量监测，并在扩大放量前校验容量。
  • 未知（报告未说明）：昂贵的定量标准、共享库名称和规模、客户端实验是什么以及何时开始、内部检出时刻、03:40 窗口起点如何确定、共享库上其他功能是否被定量拖累。

根因类别：容量/资源耗尽（主），附加软件缺陷。归类由本站根据分析归纳，非原报告表述。

4. 检测

  • 书面 RCA 未写内部首次检出渠道和时刻。MTTD：报告未说明。
  • 状态页第一条在 08:45 UTC（16:45 Asia/Shanghai），距官方窗口起点约 5 小时 5 分。08:47 UTC 已能指出任务列表/创建错误率约 2.5%，原因是上游数据库节流，并在评估两种缓解。不能把 08:45 当成 MTTD，只能说对外公布偏晚，内部何时看到节流未知。

5. 止血与修复

  • 临时止血（官方）：关闭一个客户端实验；临时限制来自受影响客户端的任务列表请求。09:11 UTC 称已定位到特定客户端版本并开始部署缓解，部分恢复；09:50 UTC 随放量继续恢复；10:01 UTC 进入 monitoring 并发布书面说明。
  • 更广服务恢复后，任务列表请求的一刀切限制仍保留，11-06 才取消，之后继续渐进放开。
  • 已做或进行中（官方，不是本站建议）：改进任务列表查询；把限流迁到单独的基础设施；增加容量监测；继续减少不必要的客户端请求，并在扩大放量前先校验容量。完成日期除 11-06 取消一刀切限制外，其余报告未说明。

6. 影响为何扩大

  • 工作负载打在共享数据库上，昂贵查询可以抢走其他用法所需的容量。书面 RCA 没有定量写出共享库上其他功能是否被拖累，只写「更广影响」靠关闭实验和限制任务列表来缓解，说明风险至少被他们当成跨功能的。
  • 对外公布比官方窗口起点晚约五小时，窗口被写到 10:01，部分是因为限制还在。
  • 一刀切限制保护了数据库，也让任务列表能力在 11-06 之前继续降级。

9. Lessons

官方未使用 well / poorly / lucky 分栏。以下为归档侧解读。

  • 做得好：定位到任务列表查询和共享库节流后，用关闭实验加临时限流把更广影响先按住；恢复后没有立刻取消限制，而是先改查询、迁限流、加监测再渐进放开；书面 RCA 把「限制保留到 11-06」写清楚了。
  • 做得差：昂贵查询可以耗尽共享库；实验放量前的容量校验不够；对外说明比官方窗口起点晚约五小时。
  • 运气：平均错误率停在约 1.22%、峰值 2.68%，没有变成共享库上的全面不可用。这是结果，不是已证实的隔离能力。
